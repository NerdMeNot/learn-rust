Rust and C can call each other because they share one thing, the C calling convention, which `extern "C"` selects. Everything else is a convention you keep by hand: struct layout, who frees a pointer, what happens on failure. This page builds a small Rust library, `bridge`, and calls it from C and C++ (and from [five other languages](#the-same-library-from-other-languages)). Then it goes the other way: Rust calling a C library through `bindgen`, and a C++ class through `cxx`.

Everything not marked "not run" ran in the image behind this site (Linux ARM64, Rust 1.99.1, GCC 14.2; `.a`, `.so` and `LD_LIBRARY_PATH` are Linux names). The image has no cbindgen or libclang, so the runs install them; steps that need the network say so, and versions are pinned.

<Remember>The compiler cannot check the other side of the boundary or what a raw pointer points to, so each `unsafe` block is a promise you write down: who owns the memory, what the layout is, and that nothing unwinds across it.</Remember>

Four things make a Rust function callable from C. `extern "C"` picks the C calling convention. `#[unsafe(no_mangle)]` keeps the symbol name as written, so the linker finds `point_distance`. `#[repr(C)]` gives a struct the layout a C compiler would. And the signature uses types C has: integers, floats, pointers, `repr(C)` structs. Dereferencing a raw pointer is `unsafe` ([the unsafe lesson](/learn/unsafe/)), so each block carries a `// SAFETY:` comment and each function a `# Safety` section for its caller.

The three `crate-type` values build `libbridge.a` (static), `libbridge.so` (shared) and an `rlib` for Rust users ([linkage](https://doc.rust-lang.org/reference/linkage.html)).

## Who frees what

Rust allocated the string `greeting` returns, so Rust must free it: `greeting_free` takes it back with `CString::from_raw`. `Accumulator` follows the same rule with `Box::into_raw` and `Box::from_raw`. The docs for [`CString::from_raw`](https://doc.rust-lang.org/std/ffi/struct.CString.html#method.from_raw) warn that taking ownership of a string "allocated by foreign code" is "likely to lead to undefined behavior or allocator corruption". The rule runs both ways: the [cgo docs](https://pkg.go.dev/cmd/cgo) say a `C.CString` "is allocated in the C heap using malloc" and "it is the caller's responsibility to arrange for it to be freed". Give a pointer back to the code that made it.

## A panic must not cross the boundary

`explode(1)` panics inside an `extern "C"` function. The Reference's [table on unwinding](https://doc.rust-lang.org/reference/items/functions.html#unwinding) says that with `panic=unwind`, a panic that reaches a non-unwinding ABI such as `"C"` aborts. The C program saw this (backtrace frames, which start with spaces, are left out, and the thread number changes between runs):

<Session guide="interop-c-cpp" run="panic" only={[4]} />

A library can call [`catch_unwind`](https://doc.rust-lang.org/std/panic/fn.catch_unwind.html) at each entry point and return an error code. `checked_div` does; the panic hook still prints its message first:

<Session guide="interop-c-cpp" run="panic" only={[5]} />

The Reference describes `extern "C-unwind"` as identical to `"C"` "but with different behavior when the callee unwinds (by panicking or throwing a C++ style exception)". `explode_unwind` is declared that way, so its panic may leave the function. This C++ program catches it with `catch (...)` and does not rethrow:

<Files guide="interop-c-cpp" dir="rust" files={["cpp/unwind.cpp"]} lang="cpp" />

<Session guide="interop-c-cpp" run="panic" only={[6]} />

The C++ handler ran, and then Rust aborted the process. That is consistent with the [Reference](https://doc.rust-lang.org/reference/panic.html#unwinding-across-ffi-boundaries), which gives no guarantee here: "an unwind originated from a Rust runtime must either lead to termination of the process or be caught by the same runtime." Try it yourself 2 shows `panic = "abort"` defeating `catch_unwind`.

## C called from Rust: bindgen

This direction needs a Rust declaration for every C function. The [`bindgen`](https://rust-lang.github.io/rust-bindgen/) crate writes them from a header in `build.rs`, and the `cc` crate compiles the C file:

bindgen reads headers with libclang, which the image lacks. The session shows the failed build, the install (Debian's `libclang-dev`; the [requirements](https://rust-lang.github.io/rust-bindgen/requirements.html) ask for "Clang 9.0 or greater"), then the program and the file bindgen wrote:

<Session guide="interop-c-cpp" run="bindgen" />

The bindings include compile-time checks of the size and each field offset, and every function sits in an `unsafe extern "C"` block, so each call needs `unsafe`. The safe `compute` wrapper keeps the promises: valid pointers in, and a result that is only borrowed, because the header comment says the library owns it.

## C++: cxx

C++ classes, templates and exceptions have no C equivalent, so a C-style header cannot describe them. The [cxx](https://cxx.rs/) crate takes another route: you describe the boundary once in a `#[cxx::bridge]` module, and `cxx-build` generates the C++ side. The `Stats` struct is declared once and used by both languages. `String` in the bridge is `rust::String`, and `std::string` is `CxxString` ([type table](https://cxx.rs/bindings.html)). A C++ function that can throw is declared `-> Result<i32>` and its exception arrives as an `Err` ([docs](https://cxx.rs/binding/result.html)).

<Files guide="interop-c-cpp" dir="cxx" files={["src/main.rs", "src/counter.h", "src/counter.cc", "build.rs"]} />

<Session guide="interop-c-cpp" run="cxx" />

The `Counter` lives in a `UniquePtr` owned by Rust, and dropping it ran the C++ destructor. `print_report` is C++ calling back into Rust's `describe`. `main.rs` has no `unsafe` block; the `unsafe extern "C++"` line is the claim, which the [cxx docs](https://cxx.rs/extern-c++.html) call "an item level unsafe block to indicate that an unchecked safety claim is being made about the contents of the block".

## Try it yourself

1. **Remove `#[repr(C)]` from `Reading`.** Rust builds it without a warning, and its size drops from 24 to 16, with `value` first. The regenerated header no longer lets C see inside `Reading`, so gcc rejects `c/main.c`:

   <Session guide="interop-c-cpp" run="try-repr-c" only={[2, 3, 4]} />

2. **Add `panic = "abort"` to the dev profile.** `catch_unwind` cannot catch an abort: `checked_div(1, 0)` no longer returns -1.

   <Session guide="interop-c-cpp" run="try-abort" only={[3]} />

3. **Run `c/main.c` under AddressSanitizer** (the first ownership run above). It printed the same lines as the plain build and no report. Then run `c/leak.c`, a smaller program that never calls `greeting_free` (the leak run above).
