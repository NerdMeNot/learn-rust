## Errors become exceptions

<Files guide="interop-python" dir="rust" files={["py/mistakes.py"]} lang="python" />

<Session guide="interop-python" run="build" only={[6]} />

The first five failures happen while PyO3 converts an argument, before the body of the function runs. A number too big for `i64` is an `OverflowError`, and a `str` where an `int` belongs is a `TypeError`. A `str` is refused as a `Vec` although it is iterable. A lone surrogate such as `"\ud800"` is a valid Python string but not valid UTF-8, so it cannot become a `&str`.

For your own failures, return a `PyResult`. `parse_pair` builds a `ValueError` itself for `'34'`. For `'3,x'` the `?` converted a `ParseIntError`: PyO3 accepts any error type with `From<E> for PyErr`, and that one has it ([PyO3: error handling](https://pyo3.rs/v0.30.1/function/error-handling.html); [Errors](/learn/errors/#when-the-error-types-differ) covers `From` and `?` in plain Rust).

A panic is a different case. `explode` calls `unwrap` on a failed parse:

<Session guide="interop-python" run="build" only={[7]} />

Rust's panic hook printed the message, and Python received a `PanicException`. It derives from `BaseException`, so `except Exception` did not catch it; the [PyO3 docs](https://docs.rs/pyo3/0.30.1/pyo3/panic/struct.PanicException.html) say this is "so that it will typically propagate all the way through the stack and cause the Python interpreter to exit". See [Errors](/learn/errors/#panics-when-the-thread-stops) for panics.

## A Rust struct as a Python class

`Counter` in the file above is a `#[pyclass]`, with a `#[new]` constructor, a `#[getter]` and a `__repr__`.

<Files guide="interop-python" dir="rust" files={["py/counter.py"]} lang="python" />

<Session guide="interop-python" run="build" only={[8]} />

`distinct` has a getter and no setter, so assigning to it is an `AttributeError`. The `RuntimeError` is the interesting line. `c.merge(c)` passes the same object as `&mut self` and as the `other` argument, which Rust's borrowing rules forbid. The compiler cannot see that call, so PyO3 checks the rule at run time, in a way its [guide](https://pyo3.rs/v0.30.1/class.html) calls "very similar to `std::cell::RefCell<T>`" ([`RefCell`](/learn/smart-pointers/#cell-and-refcell-change-it-through-a-shared-reference)). The same page says a `#[pyclass]` type must be `Send` and `Sync` ([Send and Sync](/learn/send-sync/)).

## Letting other Python threads run

The PyO3 guide says CPython "was limited by the global interpreter lock (GIL), which only allowed a single thread to drive the Python interpreter at a time" ([PyO3: parallelism](https://pyo3.rs/v0.30.1/parallelism.html)). While your Rust function runs, it holds that lock, and no other Python thread runs. `Python::detach` releases the lock for the length of a closure. Before 0.26.0 it was `allow_threads`, so older tutorials use the old name ([migration guide](https://pyo3.rs/v0.30.1/migration.html)).

The two `wait_*` functions at the end of `lib.rs` wait for a flag with a timeout, and differ only in `py.detach`. The script gives them 1,000 ms. A helper thread sets the flag after 0.1 seconds, and needs the lock to do so:

<Files guide="interop-python" dir="rust" files={["py/gil.py"]} lang="python" />

<Session guide="interop-python" run="build" only={[9]} />

With the lock held, the helper could not run, so the wait timed out and returned `False`. With `detach`, the helper ran in the meantime and the wait returned `True`. The result shows who could run, not how long anything took (it assumes an idle machine). The `versions` session above shows that this CPython has the GIL; I did not run a free-threaded build.

What may go into the closure is limited. A `Bound<PyList>` carries a `Python` token, which on this build stands for holding the lock, so it cannot cross:

The docs for [`detach`](https://docs.rs/pyo3/0.30.1/pyo3/marker/struct.Python.html) say "Only types that implement `Ungil` can cross the closure" (`Ungil` is the marker for types that may leave the lock behind). The fix is to copy the Python list into plain Rust data first, here a `Vec<String>` parameter, then move that into the closure:

## ctypes, cffi and Cython

A second route skips PyO3: export a plain C function and let Python call it:

<Files guide="interop-python" dir="cabi" files={["src/lib.rs"]} />

`#[unsafe(no_mangle)]` keeps the function's name in the library; the Rust Reference says that from the 2024 edition the attribute must be marked `unsafe` ([`no_mangle`](https://doc.rust-lang.org/reference/abi.html#the-no_mangle-attribute)); the [C and C++ page](/interop/c-cpp/) goes further. Two Python tools can load the resulting `libcabi.so`:

<Files guide="interop-python" dir="cabi" files={["py/use_ctypes.py", "py/use_cffi.py"]} lang="python" run="c-abi" />

| Tool | How it knows the signature | Run on this page |
| --- | --- | --- |
| PyO3 and maturin | The Rust types, checked by the compiler | Yes, above |
| `ctypes` (standard library) | You set `argtypes` and `restype` in Python | Yes |
| `cffi`, ABI mode | You write a `cdef` string in Python | Yes, installed with pip |
| `cffi`, API mode, and Cython | A C compiler builds a module against Python's headers | Not run |

The `ctypes` docs say "their value is masked to fit into the C type" and, without `argtypes`, "the number of arguments is not checked". So `2**40` was cut to 32 bits and the answer was `1`; once the signature was declared, it was right. The `cffi` run printed the full `1099511627777`, and rejected `2**63` with an `OverflowError`, since it checks values against the declared `int64_t`. The `cffi` docs say ABI mode "will crash if you call some function or access some fields of a structure that was slightly misdeclared in the cdef()". Its API mode and [Cython](https://cython.readthedocs.io/en/latest/src/quickstart/build.html) go through a C compiler, which needs `Python.h`, and the image has none.

With `ctypes` or `cffi` you describe the Rust function again in Python, and nothing checks that description against the Rust code (`ctypes` without `argtypes` cut `2**40` above). With PyO3 the signature is Rust code and the macro writes the conversions. The C-ABI route has upsides: the `cabi` crate built with plain `cargo build`, and its library does not name a Python version, while the PyO3 wheel is tagged `cp313` and the [PyO3 guide](https://pyo3.rs/v0.30.1/building-and-distribution.html) says modules by default "can only be used with the same Python version they were compiled against". ABI means application binary interface, the binary-level contract between compiled code. The same question for other targets has its own page: [Node](/interop/node/), [C and C++](/interop/c-cpp/) and [WebAssembly](/interop/wasm/).

## Try it yourself

All three ran in the image, in one session that builds the environment again (needs network).

1. **Release build.** Save the output of `py/calls.py` after `.venv/bin/maturin develop` and again after `maturin develop --release`, and `diff` them. The diff printed nothing and its exit code was 0, and `target` had both `debug` and `release` folders. This page makes no claim about speed.
2. **Return an `Option`.** Copy `try_option.rs` over `src/lib.rs`, run `.venv/bin/maturin develop`, then `print(wordstats.longest(['a', 'abc', 'ab']))` and `print(wordstats.longest([]))` in Python. The first printed `abc`, and the empty list gave `None`.
3. **Your own exception.** Copy `try_exception.rs` over `src/lib.rs`, run `.venv/bin/maturin develop`, then run `py/try_exception.py`. `create_exception!` makes `EmptyText`, a subclass of `ValueError`. Catching it by name worked, and `isinstance(e, ValueError)` was `True`.
