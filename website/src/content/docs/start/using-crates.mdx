A Rust library is called a **crate**. This page covers the whole journey: finding one, checking it's any good, adding it to your project, and using it in your code, including what that `use` line at the top really does.

<Remember>`cargo add` puts a crate in `Cargo.toml`. `use` gives you short names for what's inside it. You never need `mod` for a crate.</Remember>

## Where crates live

| Site | What it's for |
| --- | --- |
| [crates.io](https://crates.io) | The Rust community's package registry, and the one `cargo add` installs from unless you configure another. |
| [docs.rs](https://docs.rs) | Documentation for the crates on crates.io, built automatically when a version is published. |
| [lib.rs](https://lib.rs) | Another site for browsing crates. blessed.rs describes it as a semi-curated directory. |
| [blessed.rs](https://blessed.rs) | An unofficial, hand-curated guide to the ecosystem: for common jobs, which crates to look at. Start here when you don't know what to search for. |

Also see [The crates everyone uses](/build/crates-map/), which maps common jobs to the usual crate and to what you'd use in other languages.

The registry's ranking tells you which crates match your words, not which one to trust. A look at blessed.rs, lib.rs or a web search is a better start when you don't know the name.

## Is it any good?

Before you add a crate, take thirty seconds on its crates.io page:

- **Downloads**, especially recent ones. A crate many people use has had more eyes on its bugs, though a download count is not a quality score.
- **Last release.** Months is fine. Years can be fine for small, finished crates, but check the issues.
- **Documentation** on docs.rs, with examples.
- **Dependents**: how many other crates use it.
- **Version number.** Many well-known crates stay below 1.0 for years (`rand` was at 0.10 when this page was written). That's common in Rust, and it only means the authors haven't promised a stable API yet.

## Using it in your code

<Files guide="using-crates" dir="rust" files={["src/main.rs"]} run="run" />

That first line is the confusing one, because `UnicodeSegmentation` never appears again. Here it is piece by piece:

| Piece | What it is |
| --- | --- |
| `use` | "Let me refer to this by a short name." It doesn't load or install anything. |
| `unicode_segmentation` | The crate's name, with `-` turned into `_`. Every normal dependency in your `Cargo.toml` is available by name in every file. No `mod` line needed. |
| `::` | "Inside of", like `.` in a Java or Python import path. |
| `UnicodeSegmentation` | A **trait** inside the crate: a set of methods it adds to existing types. This one adds `.graphemes()` to every string. |

So the line doesn't give you a function to call. It switches on a method. In Rust, a trait's methods only work where the trait is in scope, which usually means imported with `use` in that file (or module). That's why you never write `UnicodeSegmentation` again: you just call `word.graphemes(true)`, and it works because the trait is in scope.

### If you've seen this before

C# works the same way: LINQ's `.Where()` and `.Select()` are extension methods, and only exist where `System.Linq` is imported (new projects import it for you). So do Kotlin extension functions from a library, which you import by name. Go, Java and Python don't have this: there, a method belongs to its type and is always there.

## How do I know what to import?

- **The crate's front page on docs.rs.** Almost every crate opens with an example, and the `use` lines at the top of it are what you need.
- **The "Traits" section on docs.rs.** If a crate adds methods to types you already have, they come from a trait listed there.
- **Your editor.** rust-analyzer has a setting, [`completion.autoimport.enable`](https://rust-analyzer.github.io/book/configuration.html) (on by default), for "completions that automatically add imports when completed". Your editor has to support it.
- **The `prelude` module.** Some big crates offer `use some_crate::prelude::*;`, which imports all their common traits at once.

- `cargo update` moves every crate to the newest version your `Cargo.toml` allows, and updates `Cargo.lock`. Add `--dry-run` to see what it would change.

## The lock file

`Cargo.toml` says which versions are acceptable. `Cargo.lock` records the exact versions Cargo picked, plus a checksum for each from the registry:

<Files guide="using-crates" dir="rust" files={["Cargo.lock"]} />

Cargo changes that file when `Cargo.toml` asks for something it doesn't cover, when you run `cargo update` or `cargo remove`, or when the package's own version changes. For a program like this one, commit `Cargo.lock`, so everyone (and your CI, the server that builds every change) builds with the same versions. The `--locked` flag makes that strict. Here `Cargo.toml` was edited by hand to add `itoa`, but `Cargo.lock` wasn't updated:

<Session guide="using-crates" run="locked" />

A CI job can pass `--locked` so that a build which would change the lock file fails instead.

## Security checks and bigger projects

`cargo audit` checks your `Cargo.lock` against the RustSec database of reported vulnerabilities. It is a separate tool (`cargo install cargo-audit`). I did not run it for this page, so there is no session for it.

When a project grows to several packages, a **workspace** lets them share one `Cargo.lock` and one `target/` folder, so they resolve versions together. [Modules and Visibility](/learn/modules/#packages-and-crates) explains packages and crates, and [Several programs](/start/several-programs/) builds a workspace step by step.

## The same thing in your language

| Language | Manifest | Lock file | Add a package | Registry |
| --- | --- | --- | --- | --- |
| Rust | `Cargo.toml` | `Cargo.lock` | `cargo add serde` | crates.io |
| Go | `go.mod` | `go.mod` records the versions; `go.sum` holds checksums | `go get example.com/pkg` | Go module proxy (by default) |
| Python | `pyproject.toml` | depends on the tool (`uv.lock`, `poetry.lock`) | `uv add requests` | PyPI |
| TypeScript | `package.json` | `package-lock.json` (npm), `bun.lock` | `npm install zod` | npm |
| Java | `pom.xml` or `build.gradle` | none by default | edit the build file | Maven Central |
| Kotlin | `build.gradle.kts` | none by default | edit the build file | Maven Central |
| C# | `.csproj` | `packages.lock.json`, opt-in | `dotnet add package Serilog` | NuGet |
| C | `CMakeLists.txt` plus a package manager such as vcpkg or Conan | per tool | `vcpkg add port zlib` | no single standard |
| C++ | `CMakeLists.txt` plus vcpkg or Conan | per tool | `vcpkg add port fmt` | no single standard |
