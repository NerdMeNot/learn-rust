Two little keywords trip up many newcomers: `mod` and `use`. They look related, but they do completely different jobs. Once you see which is which, splitting a program into files is easy.

<Remember>`mod` says "this file is part of my program", once, in the parent. `use` gives a short name to something, in any file that wants it.</Remember>

This page is the step-by-step. The [Modules lesson](/learn/modules/) is the reference: every `pub` form, re-exports, globs and the prelude.

## Two keywords, two jobs

|  | `mod pricing;` | `use crate::pricing::total;` |
| --- | --- | --- |
| What it means | "There's a module called `pricing`. Load it from `pricing.rs`." | "In this file, let me write `total` instead of `crate::pricing::total`." |
| Where you write it | Once, in the **parent** file (usually `main.rs`) | In **any** file that wants the short name |
| Loads a file? | Yes | Never |
| Needed for crates and std? | No | Optional: it's only a shortcut |
| Closest thing in Go | Nothing: the compiler takes the `.go` files of a package folder | `import` (of a whole package) |
| Closest thing in Python | `import pricing` does both jobs at once. Rust splits them in two. | `from pricing import total` |
| Closest thing in TypeScript | Nothing as a statement: a file joins when something imports it | `import { total } from "./pricing"`, which also loads the file |
| Closest thing in Java, Kotlin, C# | Nothing: the build gives the compiler its files | `import` (Java, Kotlin), `using` (C#) |
| Closest thing in C, C++ | Nothing in the code: the file is listed in the build | `using` in C++; C has none (`#include` pastes a header) |

## Where names come from

This explains why you see `use` lines with no `mod` lines in most files. Most names in your code come from one of three places, and only one of them needs `mod`:

| Where it comes from | Example | Needs `mod`? |
| --- | --- | --- |
| The standard library | `use std::collections::HashMap;` | No. `std` is available by name in every file. |
| A crate in `Cargo.toml` | `use serde::Deserialize;` | No. Every normal dependency is available by name in every file (a hyphen in its name becomes `_`). |
| Your own files | `use crate::models::Order;` | Yes, **once**, in the parent file. Then every file can `use` it. |

### Reading it file by file

1. **`main.rs`** is where Rust starts. Its two `mod` lines say "`models.rs` and `pricing.rs` are part of this program". Then `use models::Order;` lets it write `Order` instead of `models::Order`.
2. **`models.rs`** declares nothing. It doesn't need to: `main.rs` already declared it.
3. **`pricing.rs`** has one `mod` line, for its own child `discounts`. Because the parent is `pricing`, Rust looks for that file in a folder named after it: `src/pricing/discounts.rs`. It also *uses* `Order`, with no `mod models;`, because `main.rs` already declared `models`. `crate::` means "start from the top of this crate", and here the crate is the program ([crates and packages](/learn/modules/#packages-and-crates)).
4. **`discounts.rs`** declares nothing. Its parent, `pricing.rs`, declared it.

The `mod` lines build a tree of modules, starting at `main.rs`. The `use` lines just point into it:

```text title="The module tree"
crate                (src/main.rs)
├── models           (src/models.rs)
└── pricing          (src/pricing.rs)
    └── discounts    (src/pricing/discounts.rs)
```

To refer to something in this tree, start from the top with `crate::`, as in `crate::models::Order`, or one level up with `super::`, as in `super::models::Order` from inside `pricing`.

## Questions people ask

### Why do some files have `use` lines but no `mod` lines?

Because `mod` is written once, in the parent, and that's usually `main.rs` (or `lib.rs` for a library). Every other file just uses what's already been declared, plus things from std and your crates, which never need `mod` at all.

### What if I write `mod models;` in `pricing.rs` too?

Then you're declaring a *second*, different module called `models`, inside `pricing`. Rust looks for its file at `src/pricing/models.rs`, doesn't find it, and stops. The error's last line says what to do instead:

### Does `use` make code slower, or load anything?

No. `use` is resolved while compiling and loads nothing at run time. It only chooses how you spell a name: you can write the full path instead, like `models::Order::new(...)`. Try it #2 below does that and prints the same lines.

### What's `mod.rs`?

The older way to give a module a folder. `src/pricing/mod.rs` means the same as `src/pricing.rs` (Try it #3 moves the file to show it), and you'll see both in real projects. The Book calls the `pricing.rs` style more idiomatic and the other "still supported". Using both for one module is an error ([layouts compared](/learn/modules/#modules-inline-and-in-files)).

## Sharing: items are private until you say pub

- A function, struct, field or module is visible only inside its own module, and the modules inside that one, unless you mark it `pub` ([private by default](/learn/modules/#private-by-default)). Enum variants and trait methods are the exception: they take the visibility of their enum or trait ([fields and variants](/learn/modules/#fields-and-variants)).
- That's why `Order`'s fields are `pub`: `pricing.rs` reads `order.quantity`.
- `discounts` isn't `pub` in `pricing.rs`, so `main.rs` can't reach it, even though `bulk` inside it is `pub`. A module is only as visible as the path to it.
- `pub(crate)` means "visible anywhere in this crate, but not to other crates that use it as a library". Try it #1 below shows the `discounts` rule.

## How other languages decide what's in your program

| Language | A file joins your program when… | Import | Shared by default? |
| --- | --- | --- | --- |
| Rust | its parent declares it: `mod db;` | `use crate::db::User;` | No: add `pub` |
| Go | it sits in the package folder | `import "example.com/app/db"` | Other packages see only capitalised names |
| Python | something imports it | `from app.db import User` | Yes; `_name` is private by convention only |
| TypeScript | something imports it (or `tsconfig.json` includes it) | `import { User } from "./db"` | No: add `export` |
| Java | the build compiles it (a source folder, or the files `javac` is given) | `import com.app.db.User;` | Package only: add `public` |
| Kotlin | the build compiles it (a source folder, or the files `kotlinc` is given) | `import app.db.User` | Yes (`public` is the default); `internal` and `private` exist |
| C# | it is in the project | `using App.Db;` | Types: project only (`internal`); members: `private`. Add `public` |
| C | it is listed in the build | `#include "db.h"` | Yes (external linkage); `static` hides |
| C++ | it is listed in the build | `#include "db.h"` or `import db;` | Yes; `static` or an unnamed namespace hides |
