You already know how memory works. What changes is who checks the rules you keep in your head. This page takes ten habits and runs each one in the language it comes from, then in Rust. Each habit is labelled **C**, **C++** or **both**.

Everything was compiled and run in the same Linux ARM64 image as the rest of the course: gcc and g++ 14 with `-Wall -Wextra` (C++ with `-std=c++20`), and Rust 1.99.1. Where a habit is about undefined behaviour, the build adds AddressSanitizer (`-fsanitize=address`, "ASan") or UBSan (`-fsanitize=undefined`). Output with addresses or thread ids in it is marked as changing from run to run.

<Remember>Rust keeps your picture of memory and moves three rules out of your head and into the compiler: who frees, who may alias, and what may be missing.</Remember>

## What carries over

- **The memory model.** Locals live on the stack, `Box`, `Vec` and `String` own heap memory, and there is no garbage collector. [Stack and heap](/learn/stack-heap/) will mostly confirm what you know.
- **Destructors.** A type's `Drop` runs when its owner goes out of scope, which is what you use a C++ destructor for. Habit 1 prints it.
- **Templates become generics.** The compiler makes one copy of a generic function per type, as it does for a template ([One copy per type](/learn/generics/#one-copy-per-type)).
- **Layout and linking.** [`#[repr(C)]`](https://doc.rust-lang.org/reference/type-layout.html#the-c-representation) asks for a layout that interoperates with C, and `extern "C"` functions link with C code ([C and C++ interop](/interop/c-cpp/)).
- **Raw pointers exist.** Dereferencing one needs an `unsafe` block, and the compiler says so:

## Ten habits to unlearn

### 1. "I decide when to free" (both)

In C, copying a pointer copies the address, so two `free` calls on one block are easy to write. gcc 14 warned (`-Wuse-after-free`) and still built it; ASan stopped the program. In C++, a `new` with a `delete` on only some paths leaks on the others, and LeakSanitizer (part of ASan on Linux) reports it.

In Rust a value is dropped once, when its owner goes out of scope, on whichever path leaves the scope: `drop p` prints before `early: 1`. After `let b = a;` there is one owner, so the second `drop(a)` is error E0382.

### 2. "Indexing past the end is my problem" (both)

C and C++ do not check, and an out-of-range read is undefined behaviour. ASan named a `stack-buffer-overflow` for the C array and a `heap-buffer-overflow` for `v[i]`. In C++ `v.at(i)` is the checked form and throws.

In Rust `a[i]` is the checked form. It panics with the length and the index, and `a.get(i)` gives an `Option` instead. The release build panics too.

### 3. "A moved-from object is still there" (C++)

`std::move` is a cast, and the standard library leaves a moved-from object ["valid but unspecified"](https://en.cppreference.com/w/cpp/utility/move). libstdc++'s vector was empty in this run, and `push_back` on it was allowed. The worse case is a moved-from `unique_ptr`, which is null; dereferencing it crashed ([Smart pointers](/learn/smart-pointers/#translating-from-what-you-know)).

A Rust move copies the bytes and the compiler forgets the old name. Using `a` afterwards is E0382, so there is no moved-from state to inspect.

### 4. "A pointer into a container stays good" (both)

A `realloc` may move the block (C), and `push_back` may reallocate the vector (C++). The pointer or reference taken before is then dangling. gcc warned about the C case; both runs ended in ASan's `heap-use-after-free`.

Rust refuses at compile time: while `first` is alive, `v` may not be changed (E0502).

Why: Rust's rule is many readers or one writer, never both, and it is checked at compile time; `const T&` and `T&` do not enforce it. See [A reference into a list that moves](/learn/mutable-borrows/#a-reference-into-a-list-that-moves) and [Working with the Borrow Checker](/learn/borrow-checker/).

### 5. "A missing value is a null pointer" (C)

`strchr` returns `NULL` when there is no `=`, and `eq + 1` then does arithmetic on null. ASan reported a read at address `0x1`. C++'s `std::optional` is the same idea, but `*o` on an empty one is undefined behaviour ([cppreference](https://en.cppreference.com/w/cpp/utility/optional/operator*): until C++26, not run here); a Rust `Option` cannot be used as the value.

Rust's `find` returns an `Option<usize>`. You must handle it, and `eq + 1` is E0369.

### 6. "Declare it first, put it in a header" (both)

gcc 14 rejects a call to a function it has not seen ([GCC 14 porting guide](https://gcc.gnu.org/gcc-14/porting_to.html)), and g++ says `'square' was not declared in this scope`. Rust items can be used above their definition, and there are no prototypes, headers or include guards: `mod` names a node in a tree of code and does not paste text.

What you do have to write is `pub`. Items are private by default, so the `pub` keyword does the job of listing a function in a header (E0603 below).

### 7. "Variables change unless I write `const`" (both)

### 8. "A macro or a template will do" (C for macros, C++ for templates)

`MAX(i++, j)` pastes `i++` twice, so `i` ends at 7 and `m` is 6; gcc 14 said nothing. A C++ template is checked after the type is substituted, so the error for a `Point` with no `>` appears inside the function body, with "required from here" pointing back at the call.

Rust checks a generic body once, against its bound. Without `T: PartialOrd` the error (E0369) is at the definition, and an argument expression runs once: `i` and `m` are both 6.

Why: the bound is the contract. Reach for a macro when a generic function cannot do the job. See [Bounds: what `T` may do](/learn/generics/#bounds-what-t-may-do) and [Macros you'll read](/learn/reading-macros/).

### 9. "Integers convert and overflow quietly" (both)

In C and C++, `-1 < 1u` is false because the `int` is converted to unsigned (`-Wextra` warned). `uint8_t` arithmetic happens in `int`, so `200 + 100` is 300 and storing it back keeps 44. Signed overflow is undefined behaviour, and UBSan reported it.

Rust has no implicit numeric conversions (E0308), and the checked, wrapping and widening versions are separate methods. A debug build panics on overflow; the release run wrapped to 44. Cargo's [profile settings](https://doc.rust-lang.org/cargo/reference/profiles.html) list `overflow-checks` as on for `dev` and off for `release`.

### 10. "Errors are return codes or exceptions" (both)

C's `atoi("abc")` returns 0, the same as `atoi("0")`. C++'s `std::stoi` throws, and with no `catch` the program aborts. Nothing in either signature says so.

Rust's `parse` returns a `Result`. `?` passes the error up, and a `main` that returns `Err` prints it and exits with status 1 (task 3 below shows the code).

## What you will miss

These are limits you can show, not opinions.

- **Overloading.** Two functions with one name are E0428, and a call with the other argument list is E0061. Use different names, a trait, or a builder ([No default or named arguments, no overloading](/learn/what-rust-lacks/#no-default-or-named-arguments-no-function-overloading)).

<Session guide="for-c-cpp" run="miss-overload" />

- **Specialisation.** C++ lets you replace a template for one type. A Rust blanket `impl<T>` and an `impl` for `i32` overlap (E0119).

<Session guide="for-c-cpp" run="miss-specialise" />

- **Layout guarantees by default.** The Reference says the default representation makes [only the layout guarantees that soundness requires](https://doc.rust-lang.org/reference/type-layout.html#the-rust-representation), so a shared struct needs `#[repr(C)]`.
- **Allocators in the collections.** `std::vector` takes an allocator as a template parameter; `Vec::new_in` is behind an unstable feature on 1.99.1 (E0658).

<Session guide="for-c-cpp" run="miss-allocator" />

- **Correct code that the checker rejects.** This function returns a borrow from one branch and inserts in the other. It has the same shape as [problem case #3](https://rust-lang.github.io/rfcs/2094-nll.html) in the RFC that introduced non-lexical lifetimes, and it is E0502 on 1.99.1. The `entry` API is the usual rewrite.
