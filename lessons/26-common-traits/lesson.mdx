<p class="lr-layer">The toolkit</p>

Outputs on this page come from Linux on 64-bit ARM with Rust 1.99.1.

A **trait** is a named ability a type can have ([Traits](/learn/traits/) is the full story). A handful of standard traits sit behind everyday syntax: `==`, `{:?}`, `.clone()`, `.sort()`, `.into()`. The question is never "does my type work with `==`?" but "did I give it the trait behind `==`?" A new struct has none of them. `#[derive(...)]` asks the compiler to write the obvious version from the fields ([Structs](/learn/structs/#derive-asking-the-compiler-for-standard-behaviour) lists them); the rest you write by hand. Your language's equivalents follow the table.

## To do this, implement that

| You want | Implement |
|---|---|
| `{:?}` and `{:#?}`, and the message from `assert_eq!` | `Debug` |
| `{}` and `.to_string()` | `Display` |
| `.clone()` | `Clone` |
| `let b = a;` without moving `a` | `Copy` (needs `Clone`) |
| `==` and `!=` | `PartialEq` |
| `<`, `>`, `<=`, `>=` | `PartialOrd` (needs `PartialEq`) |
| `.sort()`, `a.max(b)`, `.min()`, a `BTreeMap` key | `Ord` (needs `Eq` and `PartialOrd`) |
| a `HashMap` key, a `HashSet` item | `Eq` and `Hash` |
| `T::default()`, `..Default::default()` | `Default` |
| `T::from(x)`, `x.into()` | `From` |
| `T::try_from(x)`, `x.try_into()` | `TryFrom` |
| `"text".parse::<T>()` | `FromStr` |
| `fn f(x: impl AsRef<str>)` | `AsRef` |
| `a + b`, `-a`, `a += b`, `a[i]` | `Add`, `Neg`, `AddAssign`, `Index` |
| `*x`, a `&String` where a `&str` is wanted | `Deref` |
| run code when a value goes out of scope | `Drop` |
| `for x in c` and `.next()` | `IntoIterator` and `Iterator` ([Iterators](/learn/iterators/)) |
| `?` into a `Box<dyn Error>` | `Error` ([Errors](/learn/errors/)) |

`derive` fails if a field lacks the trait, and `Display` has no derive at all: there is no obvious text for a struct, so you choose it. [Printing and Formatting](/learn/formatting/#width-is-your-job) shows how a `Display` you write should handle width.

## Your language's version

<ForLang only="go">

Go gives structs `==`, map keys and `%v` when the fields allow it; Rust makes each a trait.

| In Go | In Rust |
|---|---|
| `a == b` on a struct, `comparable`, `map[Version]T` | `#[derive(PartialEq, Eq, Hash)]`; a map key is `K: Eq + Hash` |
| `fmt.Println(v)`, `%v`, `%+v` | `{:?}` after `#[derive(Debug)]`: named fields keep their names, like `%+v`; a tuple struct prints `Cents(150)` |
| `String() string` (`fmt.Stringer`) | `impl Display` |
| `cmp.Compare(a, b)`, `cmp.Ordered`, `slices.SortFunc` | `a.cmp(&b)`, `T: Ord`, `v.sort()`, `v.sort_by(…)`; floats use `a.total_cmp(&b)` |
| `b := a` copies a struct | a move; `.clone()` copies; `Copy` types copy on assignment |
| `var v Version`, a zero value | `Version::default()` |

Floats are where the rows differ. `cmp.Compare` and `cmp.Ordered` accept `float64`, and `float64` is a legal map key (a NaN key goes in and is never found again). Rust's `f64` has no `Ord` and no `Hash`, and `a.cmp(&b)` on two `f64` does not compile. Go sorts NaN first; `total_cmp` puts a positive NaN last (below).

A `record`, `data class` or C# `record` writes the equality methods for you. In Rust that is a `derive` line, and the methods stay in step.

| In Java, Kotlin, C# | In Rust |
|---|---|
| `a.equals(b)`, Kotlin `a == b`, C# `a.Equals(b)` | `a == b`. `equals(Object)` takes anything and says false: `new Version(1, 2).equals("x")`. `PartialEq` is typed, and `v == "x"` does not compile |

| `Comparable<T>` (`IComparable<T>`) | `Ord` and `PartialOrd`. A `record` or `data class` is not `Comparable`; a derive makes the Rust struct `Ord` |
| `Comparator.comparing(…).thenComparing(…)`, `compareBy`/`thenBy`, `OrderBy`/`ThenBy` | `sort_by_key`, and `then_with` between two `cmp` results |
| `record`, `data class` | a struct with `#[derive(Debug, Clone, PartialEq, Eq, Hash, PartialOrd, Ord)]` |
| Kotlin `copy(minor = 5)`, C# `with { Minor = 5 }` | `Version { minor: 5, ..v }`. Java shares one immutable record by reference; `let b = a` moves in Rust, so `.clone()` is how you get a second value |
| `operator fun plus` (Kotlin), `operator +` (C#); Java has none | `impl Add` |
| `new T()`, `default(T)`, default arguments | `T::default()` and `..Default::default()`: Rust has no constructors and no default arguments |

Rust has no `hashCode()` that returns an int. `Hash::hash` returns nothing and writes the value into a hasher the map supplies ([below](#equality-order-and-hashing)).

## What the standard types have

Which standard types already have the traits you would want?

| Type | `Display` | `Copy` | `Eq` | `Ord` | `Hash` | `Default` |
|---|---|---|---|---|---|---|
| `f64` | yes | yes | **no** | **no** | **no** | yes |
| `String` | yes | no | yes | yes | yes | yes |
| `Vec<T>` | no | no | if `T` | if `T` | if `T` | yes |
| `HashMap<K, V>` | no | no | if parts | no | no | yes |

`i32`, `bool`, `char` and `&str` have all six. `Option<T>` and tuples have no `Display` and take `Copy`, `Eq`, `Ord` and `Hash` from their parts. All of them have `Debug`, `Clone` and `PartialEq` (when their parts do). A derive needs every field to have the trait, so `Vec<f64>`, `Option<f64>` and any struct with an `f64` field have no `Eq`, `Ord` or `Hash`.

When to derive, and when to write the `impl` yourself:

| Trait | Derive when | Write it by hand when |
|---|---|---|
| `Debug` | almost always | a field must not be printed, such as a password |
| `Clone` | each field's own clone is right | a copy should not copy everything, such as a cache |
| `PartialEq`, `Hash` | equal means every field is equal | equality ignores a field (and then `Hash` must ignore it too) |
| `PartialOrd`, `Ord` | field order is the order you want | the order is something else, such as most urgent first |
| `Default` | every field's default is a good start | zero is wrong, such as a port of 0 |

## Printing: `Debug` and `Display`

## `Clone` and `Copy`

`Clone` is an explicit copy that may run any code. `Copy` is a promise that copying the bits gives a whole new value, so the compiler does it silently on every assignment ([Ownership](/learn/ownership/#copy-types) has the table of which types are `Copy`).

<Snippet file="clone-count.rs" />

`.clone()` runs your code, a move runs nothing, and cloning a `Vec` calls `clone` once per item. `Copy` needs `Clone`, so derive both. A type with a destructor ([`Drop`](#drop-the-trait-behind-scope-exit)) can never be `Copy`:

## Equality, order and hashing

`PartialEq` gives `==`. `Eq` has no methods: it is the promise that `a == a` is always true. `f64` cannot make that promise, because `NaN` is not equal to itself. `PartialOrd` gives `<` and returns an `Option<Ordering>`, with `None` for values that cannot be compared. `Ord` is the full order that `sort`, `max`, `min` and `BTreeMap` need: `a.max(b)` on a type with only `PartialOrd` is a compile error (`f64` has a `max` of its own).

A struct with an `f64` field can derive `PartialOrd` but not `Ord`, so `sort()` is refused ([Vectors](/learn/vectors/#sorting-floats) shows a plain `Vec<f64>`):

<Snippet file="float-ord.fail.rs" />

`f64::total_cmp` is a full order that includes `NaN` (a positive `NaN` sorts last), so it works with `sort_by`:

<Snippet file="float-total.rs" />

A derived order compares fields in the order you wrote them, and enum variants by discriminant, which is declaration order unless you set the numbers. Moving a field changes the order, and nothing warns you. For another order, write `Ord` by hand: `cmp` returns an `Ordering`, and `then_with` breaks ties. `PartialOrd` just calls `cmp`.

<Snippet file="ordering.rs" />

`Hash` feeds a value into a **hasher**, an object the map supplies that mixes in what it is given and produces the number. `hash` returns nothing. A derive writes every field into the hasher. When your `==` ignores a field, write `Hash` by hand and feed the hasher only what `==` looks at, or two equal values hash differently and a map misplaces them:

<Snippet file="hash-eq.rs" />

The derived version is equal and hashes differently, so the set misses the equal ticket and holds both. The docs call breaking the rule a logic error: no memory is unsafe, the answers are wrong. The set has a fixed hasher so the output is the same on every run; a normal one is randomly seeded ([Maps](/learn/maps/#where-the-randomness-comes-from)). `rustc` says nothing about a derived `Hash` beside a hand-written `PartialEq`, but `cargo clippy` denies it (`derived_hash_with_manual_eq`, run on the derived half in the image, clippy 0.1.99). It cannot see two hand-written impls that disagree. A map key needs `Eq` and `Hash` ([Maps](/learn/maps/#keys-need-hash-and-eq)); the [gotcha](#gotcha) shows the error when they are missing.

## Converting between types

Pick the conversion trait by asking what can go wrong:

| The conversion | Trait | You call |
|---|---|---|
| cannot fail | `From<A> for B` (you get `Into` free) | `B::from(a)`, `a.into()` |
| can fail | `TryFrom<A> for B` | `B::try_from(a)`, `a.try_into()` |
| from text | `FromStr for B` | `text.parse::<B>()` |
| a cheap view of what you hold | `AsRef<B> for A` | `a.as_ref()` |

## Operators

An operator is a method call on a trait: `a + b` is `Add::add(a, b)`. Implement the trait and the operator works. `Output` is the result type, and the right side can differ (`Mul<f64>`).

<Snippet file="ops.rs" />

| Operator | Trait |
|---|---|
| `+` `-` `*` `/` `%` | `Add` `Sub` `Mul` `Div` `Rem` |
| `-x`, `!x` | `Neg`, `Not` |
| `&` `\|` `^` `<<` `>>` | `BitAnd` `BitOr` `BitXor` `Shl` `Shr` |
| `+=` and the rest | `AddAssign` and one per operator |
| `a[i]` reads, `a[i] = x` writes | `Index`, `IndexMut` |

The arithmetic and bit operators take their operands **by value**, so `a + b` moves non-`Copy` operands. `Vec2` is `Copy`, which is why `a` still works above. `==`, `<` and `a[i]` borrow, and `+=` takes `&mut self`.

## The rules between traits

Some traits depend on each other, and the compiler cannot check some rules.

| If you implement | You must also have | And you promise |
|---|---|---|
| `Copy` | `Clone` | copying the bits gives a complete new value |
| `Eq` | `PartialEq` | `a == a` |
| `PartialOrd` | `PartialEq` | `<` agrees with `==` |
| `Ord` | `PartialOrd` and `Eq` | `partial_cmp` is `Some(cmp)` |
| `Hash` with `Eq` | | `a == b` means the same hash |

`From` gives you `Into`, and `Display` gives you `ToString`, through **blanket impls**: one `impl` in std that covers every type meeting a bound (`impl<T: Display> ToString for T`; [Generics](/learn/generics/) shows the syntax).

## `Deref`: one reference becomes another

`String` implements `Deref<Target = str>`, and `Vec<T>` implements `Deref<Target = [T]>`. When a function wants a `&str` and you hold a `&String`, the compiler calls `deref` for you. It is a **deref coercion**. A method of the target works on the outer type too, so `v.first()` is a slice method called on a `Vec`.

## `Drop`: the trait behind scope exit

`Drop` runs code when a value goes out of scope: closing a file, releasing a lock ([guards](/learn/idioms/#guards-cleanup-tied-to-a-scope)). [Ownership](/learn/ownership/#scopes-drop-order-and-let-_) covers the order for locals, list items and fields, and `let _`. Three more facts:

<Snippet file="drop-order.rs" />

- A type's own `drop` runs first, then its fields are dropped. The fields are still there inside `drop`.
- A value is dropped at the end of its **scope**, so a loop drops once per pass.
- Shadowing a name does not drop the old value.
