<p class="lr-layer">The toolkit</p>

`match` compares one value with a list of **arms**, each written `pattern => result` ([the shape](/learn/rust-at-a-glance/#the-program-token-by-token)), from the top. A **pattern** is a shape a value can have, and the first pattern that fits runs its arm. Three things set it apart from a classic C-style `switch`: it produces a value, it must cover every possible value (the compiler calls that **exhaustive**), and a pattern can take a value apart (a tuple, a list, a range) as well as compare it. This page is about what patterns can do. Outputs come from Linux on 64-bit ARM with Rust 1.99.1.

## `match` is an expression

The arm that fits gives the whole `match` its value, so it can sit on the right of a `let` or be the tail of a function ([Statements and expressions](/learn/statements-expressions/)). `_` fits anything, so it goes last: the first arm that fits wins.

<Snippet file="value.rs" />

An arm that needs several steps uses a block, whose tail expression (its last line, with no `;`) is the arm's value. The comma after a block arm is optional.

## The patterns

| Pattern | Fits | Example |
|---|---|---|
| `5`, `'a'`, `"go"`, `true` | that exact value | `5 => …` |
| `1..=5` | 1 to 5, both ends included; also for `char` | `'a'..='z' => …` |
| `1..5` | 1 to 4: the end is left out | `0..10 => …` |
| `10..` and `..=0` | 10 or more; 0 or less | `100.. => …` |
| `1 \| 2` | either | `'y' \| 'Y' => …` |
| `_` | anything, and the value is ignored | `_ => …` |
| `n` | anything; a **new variable** `n` holds the value | `n => n * 2` |
| `n @ 1..=5` | a value in the range, and `n` holds it | `n @ 1..=9 => …` |
| `(0, _)`, `((a, _), b)` | a tuple, piece by piece, nested as deep as you like | `(0, y) => …` |
| `[]`, `[first, .., last]`, `[head, rest @ ..]` | a list, by its shape | `[a, b] => …` |
| `Some(n)`, `Point { x: 0, .. }` | an enum variant or a struct, by its shape | `Some(0) => …` |
| `&x` | a reference; `x` is the value behind it | `&5 => …` |
| `pattern if test` | the pattern, and the extra test (a **guard**) is true | `n if n < 0 => …` |

The next sections show each family. Every Rust cell in these tables is run.

## Names, `@` and guards

A bare name fits anything and **binds**: it makes a new variable for that arm. That is how the last arm below gets the number of minutes. `@` binds a name and tests a pattern in one go: `m @ 1..=59` fits only 1 to 59, and `m` is the value.

<Snippet file="binding.rs" />

A **guard** is `if` and a condition after the pattern. The arm is used only when the pattern fits and the condition is true. The condition can be any `bool` expression and can use variables from outside the `match`. Arms are still tried from the top:

<Snippet file="guards.rs" />

## A name in a pattern binds, it does not compare

Patterns can compare with literals, not with variables. A name in a pattern is a new variable (unless it names a constant, below), and it shadows any outer variable of the same name. This program meant "is `n` equal to `limit`?" and compiles, with warnings:

<Snippet file="shadow-trap.rs" />

Every `n` takes the first arm, and the `_` arm can never run. The compiler that checks coverage also counts the values an arm can still receive, and warns when that is none, so a specific arm belongs before a wide one. The first line below, `#![deny(unreachable_patterns)]`, is an [attribute](/learn/macros-attributes-naming/#attributes-) that turns the warning into an error, and the message even names the shadowed variable:

There are two fixes. A `const` is compared, because it is a fixed value known when the program is built. For a value that is only known when the program runs, use a guard:

## Lists: slice patterns

A pattern can describe a list by its shape: how many items, and which ones you name. `..` stands for any number of items you do not name, and `rest @ ..` names them. These patterns work on arrays and on **slices** (`&[i32]` is a borrowed view of a list; [Vectors](/learn/vectors/) and [Borrowing](/learn/borrowing/) cover them). The compiler checks the lengths: `[]`, one item, two, and "first and last" together cover every list.

<Snippet file="slices.rs" />

Literals can sit inside a slice pattern, so `["add", a, b]` is a command with two arguments. `[head, rest @ ..]` is the shape of recursion over a list:

<Snippet file="slice-rest.rs" />

A `Vec` is not a slice, so a slice pattern does not fit it directly. The `help:` shows the fix: match on a slice of it, `v[..]` or `v.as_slice()`.

<Snippet file="vec-slice.fail.rs" />

## Structs, enums, references

The same patterns take apart a struct (`Point { x: 0, .. }`, where `..` skips the other fields) and an enum, such as `Option`'s `Some(n)` ([Structs](/learn/structs/), [Enums](/learn/enums/), [Option](/learn/option/)). A `&` in a pattern looks through a reference, and what a pattern does to a value it takes (copy, move or borrow) is part of [Ownership](/learn/ownership/) and [Borrowing](/learn/borrowing/). Every rule above still applies.

## Arms must agree, or not return

Every arm gives the `match` its value, so the arms need the same type:

This is how a loop skips input it cannot use. (`parse` returns a `Result`, a success or an error; [Errors](/learn/errors/).)

## `matches!`

When you only want a `bool`, `matches!(value, pattern)` is a `match` with `true` for the pattern and `false` for the rest. It takes guards. (The `!` marks a [macro](/learn/macros-attributes-naming/#the--a-macro-call).)

## `match`, `if let` or `if`?

| You want | Use |
|---|---|
| one yes/no question | `if` ([If / else](/learn/if-else/)) |
| to act on one shape and ignore the rest | `if let`, or `let ... else` to stop otherwise (same lesson) |
| a decision for several shapes, with a check that none is forgotten | `match` |
| only a `bool` | `matches!` |

A pattern is not only for `match`: it also follows `let` (`let (a, b) = pair;`), sits in a function's parameters, and follows `for` ([Loops](/learn/loops/)).

## Your language, in Rust

<ForLang only="go" title="What you write today">

| In Go | In Rust |
|---|---|
| `switch n { case 1, 2: … default: … }` | `match n { 1 \| 2 => …, _ => … }` |
| `switch { case n < 0: … case n == 0: … }`, a tagless switch | `match n { ..0 => …, 0 => …, _ => … }` when the conditions are ranges of one number; otherwise an `if`/`else if` chain ([If / else](/learn/if-else/)) |
| `fallthrough` | no equivalent. Give two cases one arm with `\|`, or call a function from both. |
| `default:` anywhere in the `switch` | `_` last, because the first arm that fits wins |
| `switch v := x.(type) { case int: … }` | `match` on an enum, one arm per variant. The variants are a closed list, which is what lets the compiler check them ([Enums](/learn/enums/)) |

<ForLang only="java kotlin csharp" title="What you write today">

| Java | Kotlin | C# | In Rust |
|---|---|---|---|
| `case 1, 2 ->` | `1, 2 ->` | `1 or 2 =>` | `1 \| 2 =>` |

| `case Circle c ->` | `is Circle ->` | `Circle c =>` | `Shape::Circle(c) =>` ([Enums](/learn/enums/)) |
| `default ->` | `else ->` | `_ =>` | `_ =>` |

Prefer the range `101..` to the guard: the compiler counts a range towards coverage and does not count a guard (see Going deeper). Kotlin's `1..5` includes 5, like Rust's `1..=5`. In Rust `1..5` stops before 5. Your `if (x instanceof Circle c)` (Java), `if (x is Circle)` (Kotlin) or `if (x is Circle c)` (C#) is `if let Shape::Circle(c) = x` ([If / else](/learn/if-else/)).

How the check differs: Java refuses a `switch` expression over an `int` without `default` (the gotcha above). Kotlin refuses a `when` expression without `else` (below), but does not check a `when` statement over an `Int` (the gotcha). C# gives a warning (CS8509) and throws at run time (below). Rust refuses to build. Over a sealed type, Java and Kotlin already check coverage (snippets below); the `int` and `String` cases are where Rust goes further.

## How exhaustiveness is checked

The compiler reasons about the values a type can have, not about the text of your arms. Ranges are added up, so this `match` on a `u8` has no `_` and builds, because the four ranges cover 0 to 255 exactly. A constant such as `u8::MAX` can be the end of a range:

<Snippet file="exhaust-u8.rs" />

A guard is the exception, because the compiler does not run your condition. A guarded arm does not count towards coverage, even when the guards together cover every value:

<Snippet file="guards-dont-count.fail.rs" />

The error says it: "match arms with guards don't count towards exhaustivity". End with an unguarded arm.

## `_` or every case?

Both are legal; they differ when the type changes. Take a small enum (a type with a fixed list of named values; [Enums](/learn/enums/) defines them) of traffic lights. The `match` below was written when it had `Red` and `Green`, and `Yellow` was added later. Naming the cases turns the new variant into a compile error at every `match` that needs a decision:

<Snippet file="new-variant.fail.rs" />

With a `_` arm the same change builds, and yellow quietly takes the `_` arm's answer:

<Snippet file="new-variant-wild.rs" />

Use `_` when "everything else" is the real rule (a default, an unknown command). Name the cases when each variant deserves its own thought.

<ForLang only="java kotlin">

This is why you leave out `default` or `else` on a sealed type: a new subtype then turns each `switch` or `when` without one into a compile error, like the missing-case errors above. In Rust, naming the cases of an enum does the same.

</ForLang>

<ForLang only="c cpp">

This is the C habit of leaving `default:` off an `enum` `switch`, so that `-Wswitch` flags a new enumerator. In Rust that warning is an error.

</ForLang>
