<p class="lr-layer">The toolkit</p>

A **map** stores values under keys, so you can find a value by its key instead of by position. Rust's everyday map is `HashMap<K, V>`: `K` is the type of the keys and `V` the type of the values. It lives in `std::collections`, so you import it with `use std::collections::HashMap;`. A hash map turns each key into a number (its **hash**) and uses that number to decide where to store the pair, so a lookup does not have to scan every pair. Outputs on this page come from Linux on 64-bit ARM with Rust 1.99.1.

## Creating, reading, changing

<Snippet file="basics.rs" />

| You want | Write | You get back | Example on `{"a": 1}` |
|---|---|---|---|
| Add or replace | `m.insert(k, v)` | `Option<V>`: the old value, if there was one | `insert("b", 2)` is `None`, `insert("a", 5)` is `Some(1)` |
| Read | `m.get(&k)` | `Option<&V>` | `get("a")` is `Some(&1)`, `get("z")` is `None` |
| Change in place | `m.get_mut(&k)` | `Option<&mut V>` | `get_mut("z")` is `None` |
| Is it there? | `m.contains_key(&k)` | `bool` | `true` for `"a"`, `false` for `"z"` |
| Take out | `m.remove(&k)` | `Option<V>`: the removed value | `Some(1)`, then `None` |
| Read, or panic | `m[&k]` | the value | `m["a"]` is `1` |
| Size | `m.len()`, `m.is_empty()` | `usize`, `bool` | |

`HashMap::from([(k, v), …])` builds a map from an array of pairs, and `collect()` can build one from any iterator of pairs ([Iterators](/learn/iterators/)).

The methods take the key by reference because they only need to look at it. A map with `String` keys can be searched with a `&str`: `stock.get("apple")` needs no `String` to be built first. `get` gives you a reference into the map. `.copied()` turns it into a plain number (for a `String` value, use `.cloned()` or keep the reference). The [Option lesson](/learn/option/) covers the rest of what you can do with the result.

`m[&k]` is the short form of "get, and stop the program if it is missing":

Use it where a missing key would be a bug, the way you would use `unwrap`. For anything else use `get`.

There is no `m[k] = v`. The `[]` read goes through a trait called `Index`; writing would need `IndexMut`, and `HashMap` does not have it, as the error says. Writing is `insert` or `entry`.

## Looping

`for (key, value) in &map` visits every pair, giving a reference to each. `&mut map` makes the values changeable. The keys stay read-only, because changing a key would change its hash and the map could no longer find it (the docs call that a logic error). `keys()`, `values()` and `values_mut()` give just one side. They return **iterators**, a way of handing out items one at a time ([Iterators](/learn/iterators/)). `collect()` gathers an iterator's items into whatever collection you ask for; here it is a `Vec`, which `iterate.rs` then sorts.

<Snippet file="iterate.rs" />

You cannot add or remove pairs while a loop is walking the map, because the loop holds a reference into it:

<Snippet file="insert-while-looping.fail.rs" />

To remove pairs while walking, use `retain` (below). To add them, collect what you want to add first and insert after the loop.

### The order is not yours to rely on

The docs say a `HashMap` visits its pairs in "arbitrary order". This program builds four maps with exactly the same pairs, one after another in one run:

<Snippet file="order.rs" />

Each map loops in one order, here the same one every time you ask, but a second map with the same pairs can differ, and so can the next run. The docs do not promise either. They say the default hashing is chosen to resist HashDoS attacks (someone who picks your keys so that they all collide and slow the map down) and that it is **randomly seeded**; the seed is why. If the order matters, sort the keys, as `iterate.rs` did, or use a `BTreeMap` (below).

## The `entry` API: look up once, then decide

A very common job for a map is counting: "if the key is there, add one, otherwise start at one". With `get` and `insert` that is two lookups and an `if`. `map.entry(key)` looks the key up once and gives back an `Entry`: that key's slot, either occupied or vacant. A method on the `Entry` says what to do. The first three hand back a `&mut V`, a mutable reference to the value in the slot, which you change with `*` (`*count += 1` changes the number, not the reference). `and_modify` hands the entry back, so you can chain another method after it:

| Method | Key missing | Key present |
|---|---|---|
| `or_insert(v)` | stores `v` | leaves the value alone |
| `or_insert_with(f)` | calls `f`, stores the result | does not call `f` |
| `or_default()` | stores the type's default (`0`, an empty `Vec`) | leaves the value alone |
| `and_modify(f)` | does nothing | calls `f` on the value |

The `|| { … }` and `|n| …` are **closures**: small functions written inline, without a name. Here they only mean "run this code, but only when needed". The [Closures lesson](/learn/closures/) covers them.

<Snippet file="entry.rs" />

The second `or_insert_with` printed nothing, because `"pear"` was already there. `or_insert(v)` is different: `v` is worked out before the call even when the key exists (the [Option lesson](/learn/option/) shows the same thing for `unwrap_or`), so use `or_insert_with` when building the value is costly.

`entry` takes the key **by value**. With `String` keys you build the `String` before the lookup, even when the key turns out to be there. If that matters in a hot loop, try `get_mut` first and `entry` only when it returns `None`.

### Why not `get`, then `insert`?

Because a reference into the map blocks every change to the map:

<Snippet file="hold-and-insert.fail.rs" />

That is E0502, the rule from [mutable borrows](/learn/mutable-borrows/): `apples` is a reference into the map's storage, and `insert` may have to grow that storage and move every pair to a new place. Copy the number out first (`.copied()`) and the borrow ends. The program below prints each time the capacity changes while pairs are inserted, and shows `with_capacity`, which reserves room up front:

<Snippet file="capacity.rs" />

The docs say a map can hold "at least" its capacity, so the exact numbers above are not something to rely on. `entry` avoids the problem because the lookup and the change happen in one step.

## Keys need `Hash` and `Eq`

To be a key, a type must be hashable (`Hash`) and comparable for equality (`Eq`), and two equal keys must give the same hash. These are **traits**: named sets of abilities a type can have. The [Traits lesson](/learn/traits/) explains them. Strings, integers, `char` and `bool` have them already. For your own struct or enum, add `#[derive(Hash, PartialEq, Eq)]`, which the [Structs lesson](/learn/structs/) introduced (`PartialEq` gives `==`, and `Eq` adds the promise that it is a full equality).

Floats do not have them:

<Snippet file="float-key.fail.rs" />

Notice the error is on `insert`, not on `HashMap::new()`: you can name the type, but you cannot call `insert` on it. `Eq` signals that every value is equal to itself, and `NaN` breaks that:

<Snippet file="nan.rs" />

`NaN` ("not a number") is a float that is not equal to anything, itself included, so a map that used `==` could never find it again. If you need decimals as keys, store an integer (cents instead of dollars) or a string.

Tuples, `Vec`s and `Option`s are keys when their parts are, and keys are compared by value:

<Snippet file="key-types.rs" />

A `Vec` can be a key because the map owns it and only lends it out as `&K`, so ordinary code cannot change it while it is inside.

A map uses the key type's own `Hash` and `Eq`; there is no separate equality or comparator argument. For another idea of "equal" (say, ignoring case), wrap the key in your own struct and implement `Hash` and `Eq` for that. The map's third type parameter is the hasher, the algorithm that mixes the key's fields into a number (see "Going deeper").

## `BTreeMap`: a map that stays sorted

`BTreeMap<K, V>` has the same methods, but keeps its keys in order. Its keys need `Ord`, the ability to be put in order, in place of `Hash`. Like `HashMap`, it uses the key type's own ordering; to reverse it, wrap the key in [`std::cmp::Reverse`](https://doc.rust-lang.org/std/cmp/struct.Reverse.html) or your own struct.

<Snippet file="btree.rs" />

| | `HashMap` | `BTreeMap` |
|---|---|---|
| Key needs | `Hash` and `Eq` | `Ord` |
| Loop order | arbitrary | sorted by key |
| First, last, ranges | no | yes |
| Cost of a lookup (std docs) | O(1), expected | O(log n) |
| The docs suggest it for | "a map, with no extra functionality", a cache | a map sorted by key, ranges, the smallest or largest key |

"Expected" is the docs' word: hashing is probabilistic, so a `HashMap` can in theory be much slower than O(1), though the docs call that very unlikely. The docs give no timings, and this page does not either. If speed matters, measure on your own data.

**Which to pick?** If you need sorted output once, at the end, collect and sort (as `iterate.rs` does). Use a `BTreeMap` when you read in order again and again, when you need the smallest, largest or a range, or when you want the same output on every run (tests, logs). A `BTreeMap` loops in key order every time.

A **set** keeps keys without values, for "have I seen this?" and for removing duplicates. `HashSet<T>` is, in the docs' words, "implemented as a `HashMap` where the value is `()`", and `BTreeSet<T>` is the sorted one. `insert` returns whether the value was new:

| `std::map<K, V>` | `BTreeMap<K, V>` |
| `std::map<K, V, Compare>`, `KeyEqual` | none: the key type's `Ord` and `Eq` (wrap the key for another order) |
| `std::hash<K>` | the key's `Hash` (what to feed in) plus the map's hasher (how to mix it) |
| `unordered_map<string_view, V>` | `HashMap<&str, V>` |

`operator[]` reads and inserts in one call; in Rust those are two separate calls, `get` and `entry`. This program reads a missing key with `[]`, then with `at`, and prints both containers in iteration order (libstdc++'s order for the unordered one):

Moving a key matches `m.emplace(std::move(name), 30)`, except that Rust turns any later use of `name` into the error shown above. `entry(k)` takes the key by value, where `try_emplace` copies or moves it only if it inserts.

In C++, an insert that rehashes invalidates all iterators ([cppreference](https://en.cppreference.com/w/cpp/container/unordered_map/insert)), and Rust's `insert-while-looping.fail.rs` above is that bug found at compile time. References behave differently:

## Where the randomness comes from

`HashMap` has a third type parameter, the **hasher**: the code that turns a key into a number. Rust splits what C++ keeps in one `std::hash`: the key's `Hash` says which fields to feed in, and the map's hasher says how to mix them. The default hasher is `RandomState`. Its docs say a particular `RandomState` "will create the same instances of `Hasher`", but two different ones "are unlikely to produce the same result for the same values". This program hashes with two of them:

<Snippet file="hasher.rs" />

Different seeds give different hashes, so the pairs land in different places and loop in a different order. The docs say the default algorithm is currently SipHash 1-3 "though this is subject to change", and that other hashers beat it for small keys such as integers but "will typically not protect against attacks such as HashDoS". You can swap the hasher in when you have measured a need, with [`HashMap::with_hasher`](https://doc.rust-lang.org/std/collections/struct.HashMap.html#method.with_hasher) and the [`BuildHasher`](https://doc.rust-lang.org/std/hash/trait.BuildHasher.html) trait. Most programs never do.
