A closure is a function written inline as `|parameters| body`, with no name, that can use the variables around it ([the syntax](/learn/declarations-types/) is covered earlier). It is a value: store it, pass it, return it, put it in a struct. Types are usually inferred from the first use.

## What a closure captures

Using a variable from outside is called **capturing** it. Rust picks the least it can get away with, from what the body does:

<Snippet file="capture-modes.rs" />

| The body... | The closure holds | Implements | Meanwhile the code outside can... |
|---|---|---|---|
| only reads `factor` | a shared reference, `&factor` | `Fn`, `FnMut`, `FnOnce` | read it, not change it |
| changes `count` | a mutable reference, `&mut count` | `FnMut`, `FnOnce` | not touch it at all |
| moves `name` out (`drop(name)` takes a value and ends it) | the value itself | `FnOnce` | not use it: it was moved in |

These are the ordinary rules of [borrowing](/learn/borrowing/), [mutable borrows](/learn/mutable-borrows/) and [ownership](/learn/ownership/). The closure is a value that holds the references, so the borrow lasts as long as the closure is *used*. Calling `inc` changes what it holds, so the variable that holds it must be `mut`. (`Implements` is [explained below](#fn-fnmut-and-fnonce).) Each row has its error:

## Fn, FnMut and FnOnce

The compiler gives every closure some of three **traits** (a trait is a named ability; [traits](/learn/traits/) comes later), as the table's third column shows. `Fn` can be called many times, even through a shared reference; `FnMut` many times from a `mut` variable; `FnOnce` once. Which a closure gets depends on what its body does with what it captured, not on `move`.

You write the traits on the function that receives the closure, as the kind it accepts (`impl Fn()` means "any closure of that kind"; [below](#passing-a-closure-to-a-function) has the details):

## Passing a closure to a function

<Snippet file="passing.rs" />

- `impl Fn(i32) -> i32` in a parameter means "any type that implements this". `F: Fn(i32) -> i32` with `where` says the same by naming a type parameter `F` limited to such closures, ([reading signatures](/learn/reading-signatures/), [generics](/learn/generics/#bounds-what-t-may-do)).
- `&dyn Fn(i32) -> i32` is one compiled function that takes any closure of that shape through a pointer ([trait objects](/learn/trait-objects/)).
- `fn(i32) -> i32` is a plain function pointer. It accepts named functions and closures that capture nothing, and refuses the rest:

<Snippet file="ptr-capture.fail.rs" />

Ask for the most permissive trait that does the job: `FnOnce` accepts every closure in the table above, `FnMut` all but those that give captures away, `Fn` only those that just read. Ask for `FnOnce` if you call it once, `FnMut` if you call it several times (and declare the parameter `mut f`), and `Fn` if you must call it through a shared reference, such as `&self`.

A closure passed by value moves into the function; one that owns a `String` is not `Copy`:

## Returning closures

A closure's type has no name you can write, so a function returns it as `impl Fn(...)`, "some one type that implements this".

<Snippet file="returning.rs" />

The closure must own what it uses, because the function's locals are gone when it returns. Without `move`:

Each call to `make_counter` makes a closure with its own `count`. `impl Fn` names one type and every closure expression has its own, so two closures written separately cannot come out of one `if` (unless neither captures anything, below):

<Snippet file="two-closures.fail.rs" />

The fix is `Box<dyn Fn(...)>`, as `pick` does. `Box<T>` is an owned pointer to a value on the heap ([Smart pointers](/learn/smart-pointers/)). `dyn Fn(i32, i32) -> i32` means "some closure with this signature, found at run time" ([trait objects](/learn/trait-objects/)). A stored boxed closure must own what it uses, written `'static` ([lifetimes](/learn/lifetimes/)); the `registry` exercise meets it.

## Closures in the standard library

Closures are how you hand a rule to a method: `sort_by_key` takes one that works out a key, `sort_by` one that compares two items, `retain` one that says whether to keep an item. [Iterator](/learn/iterators/) adapters such as `map` and `filter` take closures the same way.

<Snippet file="sort-and-filter.rs" />

`sort_by_key` has a trap: the key may not borrow from the item.

<Snippet file="sort-key-borrow.fail.rs" />

Use `sort_by(|a, b| a.name.cmp(&b.name))`, as above, or return a copy such as `p.name.clone()`.

A closure also delays work. `unwrap_or(x)` computes `x` before the call, whether or not it is used. `unwrap_or_else(f)` runs `f` only for `None` (`ok_or_else` and `or_insert_with` follow the same pattern):

<Snippet file="lazy-default.rs" />

## Which form to write

| You are... | Write |
|---|---|
| handing a rule to a method you call right now (`sort_by_key`, `retain`, `map`) | a plain closure; no `move` |
| a `thread::spawn` thread, a returned closure, or one kept after the function ends | `move \|args\| ...` |
| a function that takes a callback | the trait that matches how you call it (above) |
| one closure in a struct; several different ones | a type parameter limited to `Fn(..)`; `Box<dyn Fn(..)>` in a `Vec` |

When the compiler complains about a closure, the message points at the capture (`x` is borrowed here, value moved into closure here) and usually offers `move` or `FnMut`. Read which variable it names first: `move` on a closure that should share a counter gives it a private copy.

## Captures are exact

A closure captures the part of a variable it names. `p.name` borrows the field `name`, and the other fields stay free. This applies from the 2021 edition on (the runner builds edition 2024); in the 2018 edition `p.score += 5` below is an error (E0506). The [Edition Guide](https://doc.rust-lang.org/edition-guide/rust-2021/disjoint-capture-in-closures.html) describes the change.

## Generic, dyn, or fn pointer

An `impl Fn` or `F: Fn` parameter is filled in with the closure's own type, so the compiler knows which code each call runs ([generics](/learn/generics/)). A `dyn Fn` value is a pointer to the closure plus a pointer to a table of its methods, and a call goes through the table, so the compiler cannot always see which code runs (an optimised build sometimes can). The sizes show the two pointers; a `fn` pointer is one:

<Snippet file="dyn-sizes.rs" />

Reach for `dyn` when you store closures of different types together or choose one at run time; otherwise prefer `impl Fn`. No timings are claimed here: measure your own case.
