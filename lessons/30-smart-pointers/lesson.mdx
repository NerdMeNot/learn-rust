## What makes a pointer smart

A reference (`&T`) borrows a value that someone else owns. A **smart pointer** is a struct that owns the data it points to, usually on the heap; implements `Deref`, so `*p` and `p.method()` reach the data; and implements `Drop`, so the data is cleaned up when the pointer goes out of scope. [Common traits](/learn/common-traits/#deref-one-reference-becomes-another) teaches `Deref` and `Drop`; this page uses them.

<Snippet file="three-things.rs" />

`r` owns nothing, so nothing happens when it goes. `b`'s `Noisy` is dropped at the closing brace of its block. By that definition this page has two smart pointers and three types that go with them:

- `Box<T>`: one owner, the value on the heap.
- `Rc<T>`: several owners, counted. Read-only.
- `Cell<T>` and `RefCell<T>` change a value through a shared reference. They are not pointers: only the guards `RefCell::borrow` returns deref.
- `Weak<T>` is a link that does not count as an owner. It does not deref: you `upgrade()` it to an `Rc` first (`check-no-deref.fail.rs`).

Because `Box` and `Rc` implement `Deref`, you rarely write the `*`. A method of the value works on the pointer, and a `&Box<String>` or `&Rc<String>` is accepted where a `&str` is wanted:

<Snippet file="deref-through.rs" />

## `Rc<T>`: several owners

[Ownership](/learn/ownership/#shared-ownership-rc-and-arc) showed the count with a `Drop`. Here is what the count means for the data:

<Snippet file="rc-share.rs" />

- `Rc::clone` copied an 8-byte pointer and added one to the count. `a` and `b` have the same buffer.
- `(*a).clone()` is the other thing, a new `Vec` with its own buffer.
- `Rc::get_mut` gives a `&mut` only while there is no other `Rc` or `Weak` (`check-get-mut-weak.rs`).

An `Rc` hands out only shared references, so the gotcha near the top is an error: `a.hits += 1` needs a `&mut`. A lone `Rc` is read-only too (`check-rc-single.fail.rs`): the compiler cannot see the count, which changes at run time. Moving the value out is refused as well, which `Box` allowed (`check-table.rs`):

<Snippet file="rc-move-out.fail.rs" />

You can also stop sharing before a change. `Rc::make_mut` gives a `&mut`, and if other owners exist it first copies the value for this one:

<Snippet file="make-mut.rs" />

`theirs` kept the old `Vec` and `mine` got its own. Once alone, `mine` changed in place (`same allocation: true`). It needs `T: Clone` and copies the whole value the first time, so it suits data read by many and rarely changed. If owners must see each other's changes, `RefCell` is next.

## `Cell` and `RefCell`: change it through a shared reference

[Mutable borrows](/learn/mutable-borrows/#the-rule-one-writer-or-any-number-of-readers) gave the rule: any number of readers, or one writer. **Interior mutability** keeps the rule and checks it at run time, in types that change their contents through `&self`.

`Cell<T>` never lends a reference into its value. `get` copies out, `set` and `replace` put a new one in. That needs no bookkeeping, and `Cell<u32>` is 4 bytes:

<Snippet file="cell.rs" />

`get` needs `T: Copy`: on a `Cell<String>` it is a compile error, and you `replace` or `take` instead.

`RefCell<T>` lends references, and counts the loans. `borrow()` and `borrow_mut()` return guards, and the loan lasts until the guard is dropped:

<Snippet file="refcell-basics.rs" />

The counter costs space: `RefCell<()>` is 8 bytes, a `RefCell<Vec<i32>>` is 32, the 24-byte `Vec` plus that counter. `try_borrow_mut` gives `Err(BorrowMutError)` rather than a panic. The unchecked version compiles, and fails when it runs:

<Snippet file="refcell-panic.panic.rs" />

That is the trade: a violation is a panic at run time, where `&mut` makes it a compile error. Use them where the program is correct but the compiler cannot see why, such as a cache behind `&self` (the memo exercise).

**When will you write this?** Less often than tutorials suggest, so ask first who the one owner is. A function that needs the data for a while takes `&` or `&mut`; an ID or an index often replaces a second owner (Ownership's [advice](/learn/ownership/#when-ownership-feels-like-a-fight)); parts that report results can send them on a [channel](/learn/channels/). `Rc<RefCell<T>>` is right when the sharing is part of the program's shape:

- closures or callbacks that each change the same state, as above ([Closures](/learn/closures/));
- a tree or graph whose nodes point back (the next sections);
- a test double that records the calls made to it while the code under test owns it.

## Across threads: `Arc<T>`

An `Rc` updates its count without protection, so two threads could corrupt it. The compiler refuses to send one to a thread:

<Snippet file="rc-thread.fail.rs" />

`Send` marks the types that may move to another thread ([Reading signatures](/learn/reading-signatures/#threadspawn-three-bounds-at-once); the trait is in [Send and Sync](/learn/send-sync/)). `Arc<T>` is the same API with an atomic count. `thread::spawn` runs a closure on a new thread and `join` waits for it ([Threads](/learn/threads/)):

<Snippet file="arc-thread.rs" />

A `RefCell<i32>` can move to another thread, but two threads cannot share one: `Sync` marks types that may be shared, and `RefCell` lacks it. The thread-safe `Rc<RefCell<T>>` is `Arc<Mutex<T>>` ([Shared state](/learn/shared-state/)). A `Mutex<T>` is a lock that owns the data it guards, with one writer at a time. A second thread that asks while it is held waits its turn (`check-mutex-wait.rs`). The same thread asking twice does not get a `RefCell`-style panic you can rely on: the [`lock` docs](https://doc.rust-lang.org/std/sync/struct.Mutex.html#method.lock) say it might deadlock.

## Which one?

| You want | Use |
|---|---|
| one owner, on the heap (recursive type, large value) | `Box<T>` |
| several owners, one thread, read-only | `Rc<T>` |
| several owners, several threads, read-only | `Arc<T>` |
| change a `Copy` value through `&` | `Cell<T>` |
| change any value through `&`, checked when it runs | `RefCell<T>` |
| change a value from several threads | `Mutex<T>` (a lock around the data), usually inside an `Arc` |
| several owners, one thread, changeable | `Rc<RefCell<T>>` |
| several owners, several threads, changeable | `Arc<Mutex<T>>` |
| a link that must not keep the value alive | `Weak<T>` |

`check-table.rs` asserts a fact for each row (a `RefCell` refuses a writer while a reader is alive, four threads add up to 4 under a `Mutex`, and so on). "One thread, read-only" is shown by `rc-thread.fail.rs` and `rc-write.fail.rs`.

## Translating from what you know

<ForLang only="go java kotlin csharp python typescript">
In your language an object (in Go, a pointer) is already shared by assignment, and a mutable one can be changed through any name. Three things differ:

- **Most sharing is a call.** Passing an object to a function that uses it for the call is a plain `&` or `&mut`. `Rc` is for what remains: several owners, none outliving the others in a way the compiler can see.
- **Changing is a second choice.** `Rc` is read-only; `RefCell` adds change, and a second writer panics.
- **Cycles are yours to avoid.** The programs below show a collector reclaiming one.
</ForLang>

<ForLang only="go">
Go has no owning pointer types: `*T` is a plain pointer, and the collector frees what is unreachable. `defer` runs at the end of a function; `Drop` when the value's scope ends, which can be earlier. Go 1.24 added a `weak` package ([release notes](https://go.dev/doc/go1.24)). The collector reclaims a cycle:

<Snippet file="cycle.go" />

<ForLang only="java kotlin csharp">

`WeakReference` has the shape of `Weak`, not the timing: `get()` returns null only after a collection has run, while `upgrade()` returns `None` the instant the last `Rc` drops. `Weak` is for back-pointers; `WeakReference` is usually for caches. `WeakHashMap` and `SoftReference` have no std counterpart; the nearest is a `HashMap<K, Weak<V>>` whose dead entries you remove yourself.

Each exercise has checks in `main`. Replace the `todo!()` calls and run until it prints `all checks passed`. The starters compile and stop at the first `todo!()`.

<Exercise name="linked-stack" title="A stack of boxed nodes">

<Exercise name="family-tree" title="Parents own children">

<Exercise name="memo" title="A memo behind &self">
