## Three forms of the loop

A `for` loop takes anything that can hand out items one at a time (an **iterator**). For a `Vec` you pick one of three forms. The choice decides what `x` is and who owns the list afterwards:

<Snippet file="forms.rs" />

| You write | `x` is | The list afterwards | Same as |
|---|---|---|---|
| `for x in &v` | `&T`, a read-only [reference](/learn/borrowing/) | unchanged | `v.iter()` |
| `for x in &mut v` | `&mut T`, a reference you can write through ([`&mut`](/learn/mutable-borrows/)) | still yours; items may have changed | `v.iter_mut()` |
| `for x in v` | `T`, the item itself | **moved into the loop**: unusable after it (unless `v` is an array of `Copy` items) | `v.into_iter()` |

`iter()`, `iter_mut()` and `into_iter()` are the methods that hand out the items; `for` calls them when you write `&v`, `&mut v` or `v` ([the end of the page](#what-the-three-forms-call) shows it).

Use the borrowing forms unless you are done with the list. The third form is the [gotcha at the top of the page](#gotcha): for a `Vec<String>` it moves each `String` out, and the compiler refuses a later use of `v`. An array has the same three forms. An array of numbers is copied into the by-value loop and stays usable, while an array of `String`s is moved like a `Vec`. A slice (`&[T]`) is already a reference, so `for x in s` borrows and `x` is `&T`. A range written directly (`for i in 0..3`) gives the numbers themselves. How other languages share or copy items in a loop is compared in [Copy or reference](/learn/copy-or-reference/).

## Getting the value out of `&T`

With `&v` and `&mut v`, `x` is a reference. `*x` follows it to the value, the pattern `&x` after `for` does that once per item ([Patterns](/learn/patterns/#references-in-patterns) explains it), and arithmetic like `x + 1` works on a `&i32` directly:

<Snippet file="values.rs" />

The `&x` pattern copies the item out, so it needs an item that can be copied. A `String` cannot, which is the E0507 error that Patterns shows. Use the reference as it is (`n.len()`, `println!("{n}")`), or ask for a copy with `n.clone()`.

## Position and backwards

<Snippet file="position.rs" />

| To loop… | Write | `x` is |
|---|---|---|
| with the position | `for (i, x) in v.iter().enumerate()` | `(usize, &T)` |
| backwards | `for x in v.iter().rev()` | `&T` |
| over part of the list | `for x in &v[1..3]` | `&T` |
| with the original position, backwards | `for (i, x) in v.iter().enumerate().rev()` | `(usize, &T)` |
| with the position, changing the item | `for (i, x) in v.iter_mut().enumerate()` | `(usize, &mut T)` |

`enumerate` and `rev` are **adaptors**: methods that turn one iterator into another. Their order changes the numbers:

<Snippet file="enumerate-rev.rs" />

`enumerate().rev()` attaches each position first, so walking backwards still prints the original indices, 2 down to 0. `rev().enumerate()` reverses first and counts what it is handed, so `cy` is numbered 0. The first order works because a slice iterator knows its length and can run from the back, and `enumerate` passes that on.

`zip`, `step_by`, `skip` and the rest are in [Iterators](/learn/iterators/), and so are the slice methods `windows` and `chunks`.

## Loops over positions

`for i in 0..v.len()` is the loop you know from C, Go and Java, and it works. It reads `v[i]`, a bounds-checked index, and nothing ties `i` to the list, so a slip such as `..=` for `..` is a panic:

<Snippet file="off-by-one.panic.rs" />

`for x in &v` has no index to get wrong. An empty list is the other trap: `v.len() - 1` underflows, because `usize` cannot go below zero ([Loops](/learn/loops/#counting-down-with-usize) runs it).

An index is the right tool when the body needs a neighbour as well as the item:

<Snippet file="index-loops.rs" />

On an empty list `1..empty.len()` is the empty range `1..0`, so the body never runs.

## Changing a list while looping over it

`for x in &v` borrows `v` until the loop ends, and `remove` needs `&mut v`. The compiler refuses:

<Snippet file="modify.fail.rs" />

The compiler's own help line names two of the fixes: "consider using an index-based loop instead, or collecting modifications into a separate collection". [Mutable borrows](/learn/mutable-borrows/#changing-a-list-while-looping-over-it) explains the rule and runs the same mistake in other languages. Here are the ways out:

<Snippet file="modify-fixed.rs" />

| You want to | Use |
|---|---|
| remove items | `v.retain(\|x\| keep(x))`: `\|x\| …` is a closure, a small function written in place ([Closures](/learn/closures/)) that says which items stay |
| change every item | `for x in &mut v`: one writer, no other borrow |
| add or remove depending on what you saw | collect the positions or new items in one loop, change `v` in a second |
| remove while walking | loop over `(0..v.len()).rev()`: the range is made once, and removing item `i` only moves later items |
| move items into a new list | `for x in v` and push each one where it belongs ([next section](#taking-the-items-out); the last exercise) |

## Taking the items out

Sometimes you want the items themselves, as owned values: to push them into another list, send them somewhere or finish with them. `for x in v` does that for the whole list. Two tools take less than all of it, or work on a list you only have a `&mut` to:

<Snippet file="take-items.rs" />

- `v.drain(range)` removes those items and hands them to the loop. The rest stay in `v`, which is still yours. `drain(..)` takes everything, and works on a `&mut Vec` parameter too.
- `std::mem::take(&mut v)` moves the whole list out and leaves an empty one in its place ([Mutable borrows](/learn/mutable-borrows/#swapping-and-taking) covers `take`). It is one way to take the items of a `&mut Vec` parameter, where `for x in v` would give you `&mut` items, not owned ones.

## Maps and text

<Snippet file="maps-and-text.rs" />

A `HashMap` loops in pairs: `for (k, v) in &map` gives `(&K, &V)`, and `&mut map` gives `(&K, &mut V)`. You may change values, not keys. The keys here are `&str`, so a reference to one prints as `&&str`. The order is not yours to rely on ([Maps](/learn/maps/#the-order-is-not-yours-to-rely-on)). A `String` or `&str` is not looped directly: pick `chars()`, `bytes()` or `char_indices()`, as the last line does ([Strings](/learn/strings/#characters-bytes-and-what-a-person-sees)).

## Your loops in Rust

<ForLang only="go">

| In Go | In Rust |
|---|---|
| `for _, n := range v` | `for n in &v` |
| `for i, n := range v` | `for (i, n) in v.iter().enumerate()` |
| `for i := range v { v[i] *= 10 }` | `for n in &mut v { *n *= 10 }` |
| `for i := len(v) - 1; i >= 0; i-- { … v[i] … }` | `for n in v.iter().rev()` |
| `slices.DeleteFunc(v, f)`, or `out := v[:0]` and an `append` loop | `v.retain(\|x\| !f(x))` |
| `for k, c := range m` | `for (k, c) in &m`; neither language promises an order |
| `delete(m, k)` inside `for k := range m` | `m.retain(\|k, _\| …)` |
| `for i, r := range s` (byte offset, rune) | `for (i, c) in s.char_indices()` |

In Go the value in `for _, n := range v` is a copy, so `n *= 10` changes nothing and you go through the index. The same `range` over a string steps by rune:

<Snippet file="range-copy.go" />

Rust's `&mut` form gives you a `&mut` reference to the item (`*n *= 10` writes through it), and `é` at offset 1 takes two bytes in `char_indices` as well. `range` takes the slice's length once, so an `append` inside is not seen ([Mutable borrows](/learn/mutable-borrows/#changing-a-list-while-looping-over-it)), and Go allows `delete` on the map it is ranging over. Rust refuses to compile both, because `&v` and `&m` stay borrowed for the whole loop.

</ForLang>

<ForLang only="java kotlin csharp">

| Your language | In Rust |
|---|---|
| Java `for (var x : list)`, Kotlin `for (x in list)`, C# `foreach (var x in list)` that only reads | `for x in &list` (read-only) |
| the same loops calling a setter or `p.age++` on each object | `for p in &mut list` |
| Kotlin `withIndex()`, C# `Select((x, i) => …)`, Java an index loop | `for (i, x) in list.iter().enumerate()` |
| Kotlin `zip`, `reversed()`, `windowed(2)`, `chunked(2)`; C# `Zip`, `Enumerable.Reverse`, `Chunk(2)` | `zip`, `rev`, `windows(2)`, `chunks(2)` ([Iterators](/learn/iterators/)) |
| Java `removeIf`, Kotlin `removeAll { }`, C# `RemoveAll` | `v.retain(\|x\| !p(x))` |

Items that are objects can be changed through the loop variable (`t.append("!")` above), because the variable refers to the object. Rust splits the for-each in two: `for x in &list` reads, and `for x in &mut list` is the one that lets you change what the item holds. The read-only form refuses `p.age += 1`:

## What the three forms call

`for` calls `IntoIterator::into_iter` on what follows `in`, then `next()` until it gets `None` ([Loops](/learn/loops/) and [Iterators](/learn/iterators/#intoiterator-why-for-x-in-v-works) explain it). `Vec<T>`, `&Vec<T>` and `&mut Vec<T>` each have their own `into_iter`, which is why one `for` has three forms:

<Snippet file="same-as.rs" />

`&v` becomes the same iterator as `v.iter()`, and `&mut v` the same as `v.iter_mut()`. The consuming form is a third type that owns the list's buffer. The names are the compiler's; you will mostly meet them in error messages.

## A consuming loop that stops early

What happens to the items a consuming loop never reached? A type can run code when a value is dropped, which means it goes away (that is the `Drop` trait; [Ownership](/learn/ownership/#scopes-drop-order-and-let-_) shows the order). Here it only prints:

<Snippet file="consume-break.rs" />

Each `item` is dropped at the end of its pass. After the `break`, `c` and `d` were never visited. `items` has been moved, so they sit in the buffer the loop's hidden iterator owns, and it drops them when the loop ends.

A borrowing loop owns nothing, so a `break` drops nothing:
