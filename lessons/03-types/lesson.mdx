<p class="lr-layer">The toolkit</p>

Rust's number types have fixed sizes (`usize` follows the target), and a number changes type only when you write the conversion. This page covers the types, what happens at their edges (overflow, `NaN`, negative remainders), and how to convert on purpose. [Declarations and types](/learn/declarations-types/) shows how literals, `as` and the turbofish are spelled; this page covers what they do. Outputs come from Linux on 64-bit ARM with Rust 1.99.1; the text says where a fact depends on the platform.

## The integer types

`i` is signed (it can be negative), `u` is unsigned (zero and up), and the number is the bit count. This program prints the size (`size_of`) and range (`MIN` and `MAX`) of each:

| Bits | Signed | Unsigned | Note |
|---|---|---|---|
| 8 | `i8` | `u8` | `u8` is the byte |
| 16 | `i16` | `u16` | |
| 32 | `i32` | `u32` | `i32` is the default integer |
| 64 | `i64` | `u64` | |
| 128 | `i128` | `u128` | see [big numbers](#big-numbers-are-not-built-in) |
| pointer width | `isize` | `usize` | lengths and positions |

`usize` and `isize` are as wide as a memory address: the [std docs](https://doc.rust-lang.org/std/primitive.usize.html) say 4 bytes on a 32-bit target and 8 on a 64-bit one, and the output above shows 8 here.

## Indexes are `usize`

A length can never be negative, and it must be able to name any position in memory, so lengths and positions are `usize`. Indexing with another integer type does not compile:

## Overflow: a panic in debug, a wrap in release

Adding past the top of a type is **overflow**. Rust does not leave it undefined. In a **debug build** (the default for `cargo run`, `cargo build` and `cargo test`, and what this page's runner makes) the program stops with a **panic** (an error that ends the program; [Errors](/learn/errors/)):

<Snippet file="overflow.panic.rs" />

A **release build** (`cargo build --release`, the optimised one, [profiles](/learn/hello-world/#debug-and-release-builds)) is different. The [Rust Book](https://doc.rust-lang.org/book/ch03-02-data-types.html#integer-overflow) says that in release mode Rust "does not include checks for integer overflow that cause panics" and instead "performs two's complement wrapping", so `256` in a `u8` becomes `0`. Try it with `cargo run --release`: this page's runner builds only in debug. What decides is the `overflow-checks` setting, not the build's name: `overflow-checks = true` under `[profile.release]` in `Cargo.toml` ([Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html#overflow-checks)), or `-C overflow-checks=on` for plain `rustc`, brings the panic back. Division is the exception: `i32::MIN / -1` panics in every build (the [Reference](https://doc.rust-lang.org/reference/expressions/operator-expr.html#overflow) says these checks stay on even when `overflow-checks` is off). The Book calls relying on the wrap "an error": decide what you want, and write it.

When the compiler can see the overflow without running the program, it refuses to build:

<Snippet file="overflow-const.fail.rs" />

Four families of methods say what you want, on every integer type:

| Method | On overflow | `250u8` plus `10` |
|---|---|---|
| `checked_add` | returns `None` | `None` |
| `wrapping_add` | wraps around | `4` |
| `saturating_add` | stops at the limit | `255` |
| `overflowing_add` | returns the wrapped value and a flag | `(4, true)` |

([Option](/learn/option/) and [Tuples](/learn/tuples/) cover the return types.) The same names exist for subtraction, multiplication and more (`checked_sub`, `saturating_mul`, `checked_pow`, `wrapping_neg`), and the last lines show why `abs` has them: `i32::MIN` has no positive counterpart.

<Snippet file="overflow-methods.rs" />

Use `checked_*` when overflow is a bug you want to report, `saturating_*` for health points or a progress bar, and `wrapping_*` for hashes, counters meant to wrap, and fixed-width register models.

## `as`: casts that never fail

`as` ([spelling](/learn/declarations-types/#as-and-the-turbofish)) never fails, so it can lose information without saying so. These are its rules for integers (the "sign bit" is explained under [two's complement](#twos-complement-in-one-example)), and `check-casts.rs` asserts every row:

| Kind | You write | Result | Rule |
|---|---|---|---|
| Narrowing | `300_i32 as u8` | `44` | keeps the low bits |
| Narrowing | `70_000_i32 as i16` | `4464` | keeps the low bits |
| Same size, other sign | `-1_i32 as u32` | `4294967295` | same bits, read the other way |
| Same size, other sign | `200_u8 as i8` | `-56` | same bits, read the other way |
| Widening unsigned | `255_u8 as i32` | `255` | the new high bits are 0 |
| Widening signed | `-1_i8 as i32` | `-1` | the new high bits copy the sign bit |
| Widening signed to unsigned | `-1_i8 as u32` | `4294967295` | sign bit copied, then read as unsigned |
| `char` to integer | `'€' as u32` | `8364` | the Unicode code point |
| `char` to `u8` | `'€' as u8` | `172` | keeps the low 8 bits (`0xAC`) |
| `bool` to integer | `true as i32` | `1` | `false` is `0` |
| `u8` to `char` | `97_u8 as char` | `'a'` | only `u8` can become a `char` |

A float cut to an integer rounds toward zero, saturates at the integer type's limits, and turns `NaN` into 0. An integer turned into a float rounds to the nearest value the float can hold:

## `From` and `TryFrom`: conversions that say what they do

`as` accepts everything. The two conversion traits (a **trait** is a set of methods a type can offer; [Traits](/learn/traits/), later) are stricter. `From` between number types exists only where no value can be lost, so it cannot fail. `TryFrom` returns a `Result` (`Ok(value)` or `Err(reason)`; [Errors](/learn/errors/)), so a value that does not fit is an `Err` you handle:

<Snippet file="convert.rs" />

`try_into` is the same call from the value's side; the target type (here `usize`, from the annotation) picks the conversion. `unwrap` takes the value out of an `Ok` and panics on an `Err`. `.ok()` turns `Ok(v)` into `Some(v)` and any `Err` into `None`, an `Option` (a value that may be missing; [Option](/learn/option/)). Asking `From` for a conversion that can lose data is an error:

<Snippet file="from-lossy.fail.rs" />

Use `i64::from(x)` (or `x.into()`) when the value always fits, `u8::try_from(x)` (or `x.try_into()`) when it might not and you must know, and `x as u8` when you want the bits cut. For a position or length from a signed value, use `usize::try_from(x)`.

## Floats: `NaN`, infinity and comparing

`f64` is the default 64-bit IEEE-754 float; `f32` is the 32-bit one. Float division by zero is not an error, and `NaN` ("not a number") is not equal to anything, itself included:

`partial_cmp` returns an `Option` because floats do not always have an order: `None` for `NaN`. `total_cmp` gives every float a place (negative zero before positive zero, a positive `NaN` after everything else), so it can sort. Plain `sort()` is refused on floats:

## Division and remainder

Integer `/` cuts toward zero, and `%` takes the sign of the left side. For an index that has to stay in range, `rem_euclid` always gives a result of zero or more:

<Snippet file="division.rs" />

`7 / 2` is `3`: two integers divide to an integer, so convert one side first for `3.5`. Dividing an integer by zero panics, as does `i32::MIN / -1` (see [overflow](#overflow-a-panic-in-debug-a-wrap-in-release)); `checked_div` returns `None` for both (`check-division.rs` asserts it). The zero case:

<Snippet file="div-zero.panic.rs" />

Method calls bind tighter than unary minus, so `-7_i32.rem_euclid(2)` is `-1`: put the negative number in parentheses, as `division.rs` does (`check-division.rs` asserts it).

## Two's complement in one example

Rust stores signed integers in two's complement: the top bit counts as a negative weight. Negating is "flip every bit, add one", and everything in the casts table follows. (`{:08b}` and `{:#x}` are in [format strings](/learn/macros-attributes-naming/#format-strings).)

<Snippet file="twos-complement.rs" />

Read it top to bottom. `!` flips every bit of an integer (Rust has no `~`; on a `bool` it is logical not), so `-x` and `!x + 1` print the same bits. `-x as u8` keeps those bits and reads them as `251`; `200_u8 as i8` keeps `11001000` and reads it as `-56`. Adding one to `127` carries into the top bit and gives `-128`; adding one to `255` in a `u8` carries out of the byte and leaves `0`. Narrowing drops the high bits: `0xA1B2C` as a `u8` is `0x2c`, and `300` is `0b100101100`, which loses its top bit and leaves `0b00101100`, which is `44`.

## No implicit widening

Going from `i32` to `i64` loses nothing, so why does Rust ask for `i64::from`? Because the rule is by type, not by value. A language that converts silently decides pair by pair which conversions are safe, and the decision is invisible at the call site. Java and C# convert `int` to `float` on their own. C and C++ go furthest (their programs are under "Coming from"): `u8 + u8` is promoted to `int`, so `200 + 100` is `300`, and storing that back into a `u8` gives `44`; and `-1 < 1u` is false, because the signed side becomes unsigned. Rust has neither: `u8 + u8` is `u8` ([What Rust lacks](/learn/what-rust-lacks/) shows `i32 + i64`), and a mixed comparison does not compile:

<Snippet file="compare-sign.fail.rs" />

E0308. The help suggests converting `limit` with `try_into().unwrap()`, which panics only if `limit` does not fit in an `i32`. Which side to convert, and what happens on failure, is your decision. Every place a number changes type is searchable, and each is `From` (cannot lose), `TryFrom` (tells you) or `as` (you chose to cut). The cost is real: code that mixes `usize` counts with `i32` values has more conversions than in a language that converts for you.

## Try it

Open each exercise in the Playground, replace the `todo!()`, and run it until it prints `all checks passed`. Two return an `Option`: `Some(x)` is "here is the answer" and `None` is "no answer" ([Option](/learn/option/), later).

<Exercise name="percent" title="A safe percentage">
`percent(part, total)` returns `part * 100 / total`, rounded down, as a `u32`. It is `None` when `total` is 0 or when the answer does not fit in a `u32`. Doing the arithmetic in `u32` overflows for large inputs, so widen first with `u64::from`, and use `u32::try_from` for the result, with `.ok()` to get the `Option`. The check with 50 million of 100 million is the one people get wrong.
</Exercise>

<Exercise name="digit-sum" title="Digit sum of any integer">
`digit_sum(n)` adds the decimal digits of an `i64`, ignoring the sign: `-1234` gives `10`. Loop with `%` and `/`. `i64::MIN` has no positive twin, so `n.abs()` would overflow: use `unsigned_abs()`, which returns a `u64`. A digit is below 10, so turning it into a `u32` with `as` cannot cut anything.
</Exercise>

<Exercise name="checked-index" title="A checked index">
`checked_index(i, len)` turns an `i32` into a slot number (a `u8`) in a table of `len` slots, or `None` when `i` is negative or past the end. Use `u8::try_from(i)`, and `.ok()` to get an `Option`. `i as u8` is the shortcut to avoid: it turns 256 into 0 and 300 into 44, and the checks include both.
</Exercise>
