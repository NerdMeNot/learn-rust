<p class="lr-layer" id="layer-toolkit">The toolkit</p>

[Macros, attributes and naming](/learn/macros-attributes-naming/) taught you to call macros such as `println!` and `vec!`. This page is for reading the others: a `macro_rules!` block in a dependency, the `#[derive(...)]` above a struct, the `#[tokio::main]` above `main`. The aim is to open one, say what it accepts and what it becomes, and know when a function would do. Outputs: Linux on 64-bit ARM, Rust 1.99.1, a debug build.

A macro runs inside the compiler. It reads the *tokens* of your call (the words, numbers and symbols of source, such as `x`, `+` or `(`) and writes new tokens in place of the call. The Book says "macros are expanded before the compiler interprets the meaning of the code" ([chapter 20.5](https://doc.rust-lang.org/book/ch20-05-macros.html)), so a macro can produce what a function cannot, such as a trait implementation.

## Four shapes of macro

| What you see | What it is | Examples |
|---|---|---|
| `name!(...)`, `name![...]`, `name!{...}` | Declarative: `macro_rules!`, written in ordinary Rust | `vec!`, `println!` |
| the same | Procedural, function-like: a Rust function over tokens, in a crate of its own | `make_answer!` in the procedural section |
| `#[derive(Name)]` | Derive: a procedural macro; the built-in ones ship with the compiler | `Debug`, serde's `Serialize` ([serde](/build/serde/)) |
| `#[name]`, `#[path::name(...)]` | Attribute: a procedural macro, or built into the compiler | `#[tokio::main]` ([tokio](/build/tokio/)), `#[test]` |

To tell which you are looking at:

- **A `!` after a name** is a function-like macro, and the brackets are not an array or an index: `vec![1, 2]` is a call. What it accepts is written in its docs or its `macro_rules!` block ([`vec!`](https://doc.rust-lang.org/std/macro.vec.html) shows its declaration).
- **`#[derive(A, B)]`** calls one derive macro per name.
- **Another `#[...]`** is built into the compiler (`#[inline]`, `#[cfg(...)]`, `#[test]`) or an attribute macro from a crate, which a path such as `tokio::main` gives away.
- **An attribute inside a derived type**, such as `#[serde(rename = "x")]` or `#[default]`, is a *helper attribute*: the derive reads it.

## Reading a `macro_rules!` block

A `macro_rules!` block is a list of rules, like the arms of a `match`, except the patterns match source code. Each rule is `(pattern) => { code }`. This one follows std's `vec!` without its `[x; n]` form:

<Snippet file="my-vec.rs" />

To read a call, find the first rule whose pattern fits. `my_vec![]` fits the first, `Vec::new()`. For `my_vec![1, 2 + 3, 4,]` the second fits:

- `$x:expr` captures one whole expression, so `2 + 3` is one capture, not three tokens.
- `$( ... ),+` means "one or more, separated by commas"; `*` is zero or more and `?` zero or one, so `$(,)?` allows a trailing comma.
- `$(v.push($x);)+` is written once per capture.
- The doubled braces: the outer pair delimits the code, the inner pair makes a block, so the expansion is one expression.

The `$name:kind` part is a *fragment specifier*, the kind of code to capture ([all of them](https://doc.rust-lang.org/reference/macros-by-example.html)).

| Specifier | Captures | Example |
|---|---|---|
| `expr` | an expression | `1 + 2 * x.len()` |
| `ident` | a name | `total` |
| `ty` | a type | `Vec<&str>` |
| `pat` | a pattern | `Some(1 \| 2)` |
| `literal` | a literal, with an optional `-` | `-3.5` |
| `tt` | one token, or one bracketed group | `+` or `(b, c)` |
| `block` `stmt` `item` `path` `lifetime` `meta` `vis` | rarer: look them up | - |

<Snippet file="fragments.rs" />

`$($t:tt)*` takes any tokens and hands them on untouched, which is how `println!` passes its arguments on. Its second rule is in the std source ([macros.rs](https://doc.rust-lang.org/src/std/macros.rs.html)): `($($arg:tt)*) => {{ $crate::io::_print($crate::format_args_nl!($($arg)*)); }}`. `$crate` stands for the crate the macro was written in, so the expansion works wherever it is called.

### Other things you will see

| You see | It means |
|---|---|
| `#[macro_export]` | The macro is available from the crate's root path, so other crates can `use` it. |
| A leading `::`, as in `::std::collections::HashMap` | An absolute path: not something of the same name in the caller's scope. |
| A pattern starting with `@inner` | An internal rule, by convention: the macro calls itself with that marker. Read the public rules first ([Little Book of Rust Macros](https://lukaswirth.dev/tlborm/decl-macros/patterns/internal-rules.html)). |

## Why `hashmap!` uses `=>`

The gotcha gave `hashmap!` a `:`. A rule with `$key:expr` cannot accept it: after an `expr` fragment only `=>`, `,` and `;` may follow ([Reference](https://doc.rust-lang.org/reference/macros-by-example.html), "follow-set ambiguity restrictions").

<Snippet file="follow-set.fail.rs" />

A `literal` key has no such limit, so another macro could take `"Ada": 36`. This one takes any expression as a key, so it uses `=>`.

## Derive macros: what the one line writes

`#[derive(Debug, Clone, PartialEq)]` is a macro call. It reads the struct and writes `impl` blocks. This is the code after the derives ran, for a struct and for an enum with a helper attribute:

<Snippet file="derive-expanded.rs" />

Each `impl` is plain code: `Clone` clones each field, `PartialEq` compares each field, `Debug` calls a helper with the name and fields. `#[automatically_derived]` marks the block as generated; the Reference says it "has no direct effect". `#[default]` survives expansion: it only marks the variant for `Default`.

The built-in derives add a bound for every type parameter, whether the fields need it or not ([Reference](https://doc.rust-lang.org/reference/attributes/derive.html): `impl<T: Clone> Clone for Foo<T>`). `PhantomData<T>`, a field that stores no data, is `Clone` for any `T` ([docs](https://doc.rust-lang.org/std/marker/struct.PhantomData.html)), yet the derive demands `T: Clone`:

The note says "consider manually implementing the trait to avoid undesired bounds"; [Common traits](/learn/common-traits/#to-do-this-implement-that) covers when.

An attribute macro receives the item it sits on and returns what replaces it. `#[test]` is built into the compiler but works like one: it keeps your function, adds a constant that describes it, and adds a `main` that runs the list. This is what `cargo test` builds (it passes `--test` to the compiler):

| Attribute | Written by | What it does |
|---|---|---|
| `#[tokio::main]` | the tokio crate | "helps set up a Runtime" for `async fn main` ([docs](https://docs.rs/tokio/latest/tokio/attr.main.html); [Async with Tokio](/build/tokio/) uses it) |
| `#[serde(rename = "x")]` | serde's derive | a helper attribute that configures the generated code ([serde](https://serde.rs/attributes.html)) |

## Procedural macro crates

A procedural macro is a Rust function that takes tokens in and returns tokens. The Reference says it "must be defined in the root of a crate with the crate type of proc-macro" and "may not be used from the crate where" it is defined; with Cargo the crate sets `proc-macro = true` under `[lib]` ([Reference](https://doc.rust-lang.org/reference/procedural-macros.html)). So it lives in a different crate from its users.

The lesson runner compiles one file, so this harness writes a two-crate workspace to a temporary folder and builds it with Cargo; the macros are in the string `SHOUT_LIB`. It needs no dependencies, because `proc_macro` ships with the compiler. One macro of each procedural kind; the attribute prints what it receives during compilation:

<Snippet file="proc-macro.rs" />

The two `attr`/`item` lines came from compile time: the attribute received `loud, times = 2` and the whole function as tokens, and returned it unchanged. The function-like macro ignored its input and wrote `answer`. The derive read the name after `struct` and wrote an `impl`. [Project structure](/further/project-structure/) covers workspaces. The Book's examples use `syn` to parse the tokens and `quote` to write them.

Two Reference facts matter when you read someone else's code. Procedural macros "are unhygienic": they act as if their output was written inline. And they have "the same security concerns that Cargo's build scripts have": a dependency with one runs code on your machine when you build. A panic in one becomes a compiler error.

## When to write one

Writing one is rare. In order of preference:

1. **A function**, the easiest to read, test and debug.
2. **Generics and traits** ([Generics](/learn/generics/), [Traits](/learn/traits/)) for code that must work for many types.
3. **A `macro_rules!` macro**, for one of the five powers above, such as one implementation repeated for a list of types.
4. **A procedural macro**, when it must read a struct's fields or parse its own syntax. It costs a separate crate.
