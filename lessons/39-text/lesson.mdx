<p class="lr-layer" id="layer-toolkit">The toolkit</p>

Outputs come from Linux on 64-bit ARM with Rust 1.99.1, debug build. Other languages ran in the same image: Go 1.27, Java 25, Kotlin 2.4, .NET 10, Python 3.13, Node 24, GCC 14.

[Strings](/learn/strings/) explains the types: `String`, `&str`, UTF-8, bytes and chars. This page is the everyday toolkit on top of them: cut text apart, find things, turn text into numbers, and compare it. Most methods return a **view**: a `&str` that points into the original text instead of copying it.

<Snippet file="edges.java" />

`split` takes a regex. `"a.b".split(".")` matched every character, so every piece was empty and Java dropped them all; `"a|b".split("|")` split between every char. Java drops trailing empty pieces unless the limit is non-zero; a positive limit caps the pieces like `splitn`.

Two names change meaning. Java's `Pattern` is the regex class; Rust's pattern is a `char`, `&str`, set of chars or closure. Java's `matches` tests a whole string against a regex; Rust's `matches` returns an iterator of hits (`contains` is the yes/no). `replace` is literal in both and changes every match; `replaceAll` is a regex.

The edges are run. `strip` and `trim` both leave U+00A0; `strip` leaves U+0001 and removes U+3000, `trim` the reverse. Rust's `trim` removes U+00A0 and U+3000 but not U+0001. `equalsIgnoreCase` equated `É` and `é`; `eq_ignore_ascii_case` does not. `parseInt` agrees with `parse` on the four ASCII inputs but reads `٣` as 3. `lines()` ends a line at a lone `\r`; Rust's does not. `" a  b".split("\\s+")` starts with an empty piece, hence `trim()` first. `toLowerCase()` follows the default locale (Turkish in the run); Rust's `to_lowercase` reads none.

## Patterns: one idea behind every method

Most methods that look inside a string take a **pattern**. According to the [`str` docs](https://doc.rust-lang.org/std/primitive.str.html#method.split), it can be a `&str`, a `char`, a slice of `char`s (an array works too), or a function or closure that decides for one `char` (a [closure](/learn/closures/) is a small function written in place, like `|c: char| c.is_ascii_digit()`). ## Cutting text apart

Most `split` methods return **iterators** ([Iterators](/learn/iterators/)), so nothing is cut until you ask for a piece. (`split_once` returns an `Option` of a pair.) Every row of the table is asserted in the lesson's source:

| Call | Pieces |
|---|---|
| `"a,b,c".split(',')` | `a` `b` `c` |
| `"a,b,".split(',')` | `a` `b` `""` |
| `"a,b,".split_terminator(',')` | `a` `b` |
| `"a,b,c".splitn(2, ',')` | `a` `b,c` |
| `"a,b,c".rsplitn(2, ',')` | `c` `a,b` |
| `"a,b,c".rsplit(',')` | `c` `b` `a` |
| `"a\nb\n".split_inclusive('\n')` | `a\n` `b\n` |
| `" a  b\t".split_whitespace()` | `a` `b` |
| `"a\r\nb\n".lines()` | `a` `b` |
| `"k=v=w".split_once('=')` | `Some(("k", "v=w"))` |
| `"k=v=w".rsplit_once('=')` | `Some(("k=v", "w"))` |
| `"kvw".split_once('=')` | `None` |

Three edge cases cause most surprises:

<Snippet file="split-family.rs" />

- A separator at the end gives an empty last piece. `split_terminator` drops it.
- `"".split(',')` gives one empty piece, but `"".split_whitespace()` gives none.
- `lines` is not `split('\n')`. It strips a `\r` before a `\n`, and gives no empty last line for a final newline. A lone `\r` stays in the line.

`split_whitespace` splits on Unicode white space (U+0085 yes, U+001C and U+FEFF no); `split_ascii_whitespace` only on ASCII ones.

Every piece borrows the original, so it cannot outlive it; copy one with `to_string()` to keep it ([Borrowing](/learn/borrowing/) and [Lifetimes](/learn/lifetimes/) explain why).

## Trimming and stripping

`trim` removes Unicode white space from both ends, including characters your terminal may not show; `trim_ascii` only ASCII ones. ## Text to numbers

`parse` turns text into any type that implements [`FromStr`](/learn/common-traits/#converting-between-types). The error type belongs to the target type, and its `Display` text is the message you can show a user:

<Snippet file="parse.rs" />

- The whole text must be the number. Spaces, `_`, a `.` for an integer and `0x` all fail. A leading `+` is accepted.
- A number outside the target type is an error (`PosOverflow`, `NegOverflow`), not a wrap-around: `3000000000` fits an `i64`, not an `i32`. `-1` for a `u8` is an invalid digit.
- Floats accept `1e3`, `.5`, `NaN` and `inf`, and refuse a comma as the decimal mark: std has no locale.
- `"٣".parse::<i32>()` fails: only ASCII digits count.
- `bool` accepts exactly `true` and `false`, and `char` exactly one char.

The target type decides the range and the sign: `"200"` parses as an `i16` or a `u8` but not an `i8`. For text a user typed, avoid `unwrap_or(0)`: it makes `"abc"` and `"0"` look the same.

`?` passes a parse error up to the caller ([Errors](/learn/errors/)). With `split_once`, a small parser is a few lines:

## One char at a time

A `char` is one Unicode scalar value. Its classification methods come in two families: `is_alphabetic`, `is_numeric` and `is_alphanumeric` follow Unicode, while the `is_ascii_*` ones accept only ASCII.

<Snippet file="chars.rs" />

Use `to_digit(radix)`, where the radix is the base (10, 16, up to 36), to read a digit, rather than subtracting `'0'`: it returns `None` for a non-digit. `char::from_u32` returns `None` for numbers that are not valid chars, such as `0xD800`, a surrogate (a code reserved for UTF-16 pairs). [Strings](/learn/strings/#characters-bytes-and-what-a-person-sees) says when to walk chars and when bytes.

## Case is more than A to Z

`to_uppercase` and `to_lowercase` follow Unicode, which is why `str` returns a `String` and `char` returns an iterator: one char can become several.

<Snippet file="case.rs" />

- A Greek sigma is `σ` or `ς` by its place in the word. The docs say `str::to_lowercase` handles this and `char::to_lowercase` does not; the run shows both.
- Neither method reads a locale. The docs say the Turkish and Azeri rules for `I` are not handled: `"I"` becomes `i` everywhere, and `İ` becomes `i` plus a combining dot.
- `eq_ignore_ascii_case` compares ASCII only: `É` and `é` differ. Lowercasing both sides equates them, yet `STRASSE` and `straße` still differ: lowercase `ß` stays `ß`.

Unicode's tool for this is case folding. `str` has `to_casefold_unnormalized`, and `eq_ignore_case_unnormalized` to compare without allocating. On 1.99.1 both are nightly-only: the nightly compiler (the experimental channel for unfinished features) accepts them, and the stable one refuses:

<Snippet file="casefold.fail.rs" />

So for a full caseless comparison you lowercase both sides (good for most text) or use a crate.

## Equal-looking text that is not equal

Unicode can write `é` as one char (`U+00E9`) or as an `e` plus a **combining accent** (`U+0301`), a char that attaches to the one before it. Both display as `é`. Converting both to one form is **normalization**.

<Snippet file="unicode-equal.rs" />

`==` compares bytes, so these differ, and `str` has no normalization method. The same trouble reaches `chars()`: a char is not what a reader sees as one letter, a grapheme ([Strings](/learn/strings/#characters-bytes-and-what-a-person-sees)). Reversing by chars moves the accent to the wrong letter:

<Snippet file="reverse.rs" />

The accent now sits on the `l`. The `chars` docs say grapheme clusters are "not provided by Rust's standard library, check crates.io instead".

## Sorting text

[Strings](/learn/strings/) showed that capitals sort first. Comparing bytes has two more surprises: `é` sorts after `z`, and `file10` before `file2`. The docs promise that `sort_by_cached_key` calls the key function at most once per element, which matters when the key allocates:

<Snippet file="sorting.rs" />

`é` starts with byte 195 and `z` is 122. Std has no locale-aware or natural-order comparison; for names in a user's language you need a crate.

## Cutting at a byte limit

A database column or a network packet limits **bytes**, and `&text[..max]` panics when `max` falls inside a char. `floor_char_boundary`, stable since Rust 1.91 ([docs](https://doc.rust-lang.org/std/primitive.str.html#method.floor_char_boundary)), gives the nearest boundary at or below `max`. A char boundary is not always a letter boundary: the last lines cut a flag, which is two chars, in half.

## What std leaves out

The 1.99.1 `str` and `char` docs list no stable method for the jobs on the left (the casefold pair is nightly-only). The right column is where people go; each crate is on crates.io.

| You need | Look at |
|---|---|
| Regular expressions | `regex` |
| Grapheme clusters, word boundaries | `unicode-segmentation` |
| Normalization (NFC joins `e` and an accent into `é`; NFD splits them) | `unicode-normalization` |
| Locale-aware sorting | `icu_collator` (the ICU4X project) |
| Case folding, locale-specific case | `icu_casemap` (the ICU4X project) |

[Finding and using crates](/start/using-crates/) shows how to add one. `regex` is maintained by the Rust project's regex team ([team page](https://github.com/rust-lang/team/blob/main/teams/regex.toml)) but is a separate crate. Its [docs](https://docs.rs/regex/latest/regex/) say the syntax lacks look-around and backreferences, in exchange for a worst-case search time proportional to pattern size times text size. [`Regex::new`](https://docs.rs/regex/latest/regex/struct.Regex.html#method.new) returns a `Result`, since the pattern can be invalid, and compiling is not cached, so build a regex once. Not run here: the lessons' runner has no crates.
