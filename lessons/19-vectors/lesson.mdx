## Making a Vec

A `Vec<T>` is a list of items that all have the same type `T`. Its items live on the [heap](/learn/stack-heap/), so it can grow and shrink while the program runs.

<Snippet file="create.rs" />

- `vec![…]` is the usual way; `vec![0; 4]` makes four copies of `0`.
- `Vec::new()` makes an empty list. The compiler must learn the item type, from a written type (`Vec<i32>`) or a later line such as a `push`.
- `with_capacity(n)` is empty with room for at least `n` items ([capacity and growth](#capacity-and-growth)).
- `collect()` turns many things into a `Vec` ([iterators](/learn/iterators/)).

`{:?}` prints a whole list; plain `{}` is not defined for lists.

## Adding, reading and removing

<Snippet file="basics.rs" />

- `push` adds at the end and `pop` takes the last item off. `pop` returns an [`Option`](/learn/option/), because the list may be empty.
- `v[1]` reads (and `v[1] = 25` writes) the item at position 1. The first item is position 0, and the `Vec` must be `let mut` to write.
- `get(i)`, `first()` and `last()` also return an `Option`: the way to ask for an item that might not be there.

Reading a position that does not exist is not an `Option`: `v[i]` **panics**, which stops the program with a message:

<Snippet file="out-of-bounds.panic.rs" />

Safe Rust checks every index. Use `v[i]` when a missing item would be a bug, and `get(i)` when it is a normal case (user input, a lookup that might miss). The index must be a `usize` (an unsigned number the size of an address), not an `i32`:

<Snippet file="index-i32.fail.rs" />

Keep positions as `usize` from the start. What your language does for an index past the end is run in [Your lists in Rust](#your-lists-in-rust).

## Changing the list

<Snippet file="editing.rs" />

| Call | What it does | Notes |
|---|---|---|
| `insert(i, x)` | puts `x` at position `i` | later items shift right; panics if `i > len()` |
| `remove(i)` | takes out item `i` and returns it | later items shift left. It removes by **position**, not by value |
| `swap_remove(i)` | takes out item `i` and returns it | the last item fills the gap: order changes, nothing shifts (O(1), say the docs) |
| `drain(a..b)` | removes positions `a` up to `b` and hands them to you | the rest shift down |
| `extend(w)` | adds the items of `w` | a `Vec` `w` is **moved** in (below). `extend(&w)` copies `Copy` items and keeps `w` |
| `append(&mut w)` | moves all of `w`'s items over | leaves `w` empty |
| `truncate(n)`, `clear()`, `resize(n, x)` | cut to `n` items, remove all, or cut or pad with `x` to exactly `n` | `truncate` and `clear` keep the capacity |
| `retain(f)` | keeps the items for which `f` says true | in place |
| `dedup()` | removes repeats **next to each other** | `[1, 1, 2, 1]` becomes `[1, 2, 1]`; sort first to remove all repeats |
| `reverse()` | flips the order | in place |

`|x| *x != 30` is a **closure**, a small function written inline ([closures](/learn/closures/)). `retain` calls it per item with a reference, so `*x` is the number. `remove` and `swap_remove` hand you the removed item, which matters for lists of `String` ([below](#owning-the-items)).

`extend(w)` uses `w` up, so a later use of it is an error:

## Looping

<Snippet file="looping.rs" />

- `for s in &scores` borrows the list and gives a `&i32` per item. The list is still yours afterwards.
- `for s in &mut scores` gives `&mut i32`, so `*s += 5` changes the item in place.
- `for s in scores` (no `&`) **moves** the list into the loop, so the last comment is true.
- `.iter().enumerate()` adds the position. [Iterators](/learn/iterators/) has the rest, including `sum`, `min` and `max` (iterator methods, not `Vec` methods); [looping over collections](/learn/for-collections/) covers the three loop forms.

## Sorting and searching

<Snippet file="sorting.rs" />

- `sort()` orders the items in place. It is **stable**: equal items keep their relative order (the docs say so). `sort_unstable()` may reorder equal items, which does not matter when they look the same.
- `sort_by(|a, b| …)` takes a closure that gets two references and returns an `Ordering`: `Less`, `Equal` or `Greater`. `a.cmp(b)` gives one, so `b.cmp(a)` puts the biggest first.
- `sort_by_key(|w| w.len())` sorts by a value worked out from each item.
- `contains(&x)` checks items one by one until it finds `x`. `binary_search(&x)` looks at far fewer on a long list but **needs a sorted one**; otherwise its answer means nothing. It returns a `Result` ([errors](/learn/errors/)): `Ok(position)`, or `Err(position)` where `x` could be inserted to keep the order. With equal items, any of them may be returned.

### Sorting floats

`f64` cannot use plain `sort()`:

<Snippet file="sort-floats.fail.rs" />

`Ord` is a **trait**, a named ability a type has or lacks ([traits](/learn/traits/)): "any two values can be put in order". `f64` lacks it because of `NaN` ("not a number"), which is neither smaller than, larger than nor equal to anything, itself included. `partial_cmp` returns an `Option` of an `Ordering`, `None` for that case. `total_cmp` puts every `f64` in one fixed order; use it with `sort_by`:

<Snippet file="sort-floats.rs" />

`a.partial_cmp(b).unwrap()` works until a `NaN` is compared, and then panics. Strings sort by bytes, so capitals come first ([strings](/learn/strings/#changing-text)).

## Slices: a window onto a list

A **slice**, written `&[T]`, is a borrowed view of items stored in a row: a pointer to the first one and a count. `&v[1..3]` is the items at positions 1 and 2 (the end is left out). Nothing is copied.

<Snippet file="slices.rs" />

- Leave out either end of the range for "from the start" or "to the end".
- `&v[1..9]` on a shorter list panics, like `v[9]`. `v.get(3..9)` returns `None`.
- `split_at`, `windows` and `chunks` are slice methods. `windows(2)` gives overlapping pairs, `chunks(2)` gives pieces that do not overlap, the last possibly shorter. Both panic on 0. More in [iterators](/learn/iterators/#peeking-windows-and-chunks).
- `concat` glues a list of lists into one, `join(sep)` does it with something in between (strings too), and `to_vec()` copies a slice into a new `Vec`.

A function that only reads takes `&[i32]`; one that changes items takes `&mut [i32]`. Both accept a `Vec`, an array, or part of either ([Borrowing](/learn/borrowing/) says why). Writing through `&mut v[3..]` changes `v` itself, because it is a view:

<Snippet file="slice-params.rs" />

A slice has a length but no capacity, so it cannot `push`. The `Vec` that owns the items can, so a function that must grow a list takes `&mut Vec<T>` ([Mutable borrows](/learn/mutable-borrows/)).

<ForLang only="go">

A Go slice is a pointer, a length **and a capacity**: one value is both handle and view. Rust splits the job: `Vec<T>` owns and grows, `&[T]` views and has no capacity. A Go subslice can write into spare room it does not own, and be resliced up to its capacity:

<Snippet file="subslice-append.go" />

A Rust slice can be cut only up to `len` and has no `push`. A `push` on the `Vec` while a slice is alive is refused ([below](#changing-a-list-you-are-reading)). The [Borrowing lesson](/learn/borrowing/) shows the same surprise, in its Go box "Why bother, when Go has pointers?".

</ForLang>

<ForLang only="python">

A Python slice is a **copy**, so changing it leaves the list alone. Rust's `&mut v[3..]` is a view. For Python's behaviour, copy with `v[1..3].to_vec()`.

## Arrays

An **array**, `[T; N]`, has its length `N` in its type. It cannot grow, and needs no heap: its items sit in the variable.

<Snippet file="arrays.rs" />

| | `[i32; 4]` | `Vec<i32>` | `&[i32]` |
|---|---|---|---|
| Length known | when compiling | when running | when running |
| Can grow | no | yes | no |
| Items stored | in the variable itself | on the heap | not owned: a view |
| Is `Copy` | yes, when the items are | no | yes (a reference) |

## Lists of lists

A grid is a `Vec<Vec<T>>`. `vec![vec![0; 3]; 2]` makes two rows of three zeros. The inner `vec![0; 3]` is **cloned** for each row, so the rows are independent.

<Snippet file="grid.rs" />

Each non-empty row is its own heap block, so rows can differ in length, at the cost of one more pointer to follow.

## Owning the items

`let x = v[0]` copies a number out, but a `String` is never copied by accident, so `let first = names[0]` is the [gotcha at the top of the page](#gotcha) (E0507, "cannot move out of index"). So is any item that is not `Copy`, a row of a `Vec<Vec<T>>` included. This is the rule from [Ownership and Moves](/learn/ownership/#moving-out-of-things): a list owns its items, so taking one out must leave something valid behind. The ways to say what you mean:

<Snippet file="owning.rs" />

| You want | Use | What the list is left with |
|---|---|---|
| to look at it | `&names[0]` | unchanged |
| a second copy | `names[0].clone()` | unchanged |
| the item, and the gap closed | `names.remove(0)` | one shorter, the rest shift down |
| the item, and the order may change | `names.swap_remove(0)` | one shorter, the last item fills the gap |
| the item, and the position kept | `std::mem::take(&mut names[0])` | an empty `String` in that position |

`mem::take` and `mem::swap` are in [Mutable borrows](/learn/mutable-borrows/#swapping-and-taking), which also covers `split_at_mut` for two `&mut` items at once.

<ForLang only="cpp">

Row for row: `mem::take(&mut names[0])` is `std::exchange(names[0], {})`, and `remove` is moving out and then `erase`. Rust has no moved-from state to leave in the slot: a slot that was moved out of would still be dropped with the list.

</ForLang>

## Where the bytes live

On this 64-bit machine a slice is 16 bytes (address and length), a `Vec` header 24 (adding the capacity), and an array is just its items.

## Capacity and growth

<ForLang only="python typescript java">

Skip to the last paragraph here if you like. Python lists, JavaScript arrays and `ArrayList` also reallocate when full, but hide the capacity.

</ForLang>

A `Vec` has a **length** (items held) and a **capacity** (items that fit in its block before it needs a bigger one). Watch both while pushing:

<Snippet file="growth.rs" />

- An empty `Vec` has capacity 0 and no buffer. The first push creates it.
- Here the capacity went 4, 8, 16, 32, 64. **Rust does not promise that**: the docs say `Vec` "does not guarantee any particular growth strategy when reallocating when full", only that `push` is amortised O(1). The first size depends on the item size:

<Snippet file="first-push.rs" />

- Whether the items **move** depends on the allocator, the part of the system that hands out heap blocks. It can sometimes make a block longer where it stands. On the runner (Linux) no push moved an existing buffer (`same address`); on another system you may see `buffer moved` on every line. When a block cannot be extended, the items are copied into a new one and the old one is freed:

<Memory
  title="v.push(5);   // v: Vec<u32> is full, len 4, cap 4"
  stack={[
    { name: 'v', type: 'Vec<u32>', cells: ['ptr', 'len 5', 'cap 8'], to: 'new' },
  ]}
  heap={[
    { id: 'new', label: "v's new buffer, room for 8", cells: ['1', '2', '3', '4', '5', '', '', ''] },
    { id: 'old', label: 'old buffer, room for 4', freed: true, cells: ['1', '2', '3', '4'] },
  ]}
  caption="The four items were copied across, the fifth was written, and three cells of spare room remain. If the allocator could extend the block in place, `old` and `new` would be the same address and nothing would be freed."
/>

`with_capacity(40)` never moves, because the room was reserved first (the docs recommend it when you know the size). `truncate` and `clear` keep the memory; `shrink_to_fit` asks for capacity to match the length, and the docs say the result depends on the allocator. `reserve(extra)` makes room for `extra` items beyond the length: `vec![1, 2, 3]` with `reserve(5)` has capacity 8, not 5.

The compiler cannot know whether a push will move the items, so it treats every push as one that might. That is why a reference into a `Vec` cannot survive a `push`: [Mutable borrows](/learn/mutable-borrows/#a-reference-into-a-list-that-moves) draws the dangling reference this would leave.

</ForLang>

## Changing a list you are reading

Any call that needs `&mut self` is a writer: `push`, `clear`, `remove`, `sort`. A slice, a reference to one item and a loop over `&v` are readers, and readers and a writer cannot overlap ([Mutable borrows](/learn/mutable-borrows/)):

<Snippet file="slice-then-clear.fail.rs" />

Take the slice after the change, or copy the part you need with `to_vec()` first. [Mutable borrows](/learn/mutable-borrows/#changing-a-list-while-looping-over-it) shows the loop version and other languages. This is the biggest idea Rust adds to lists: the view and the list cannot both be live when the list changes.

<ForLang only="c cpp">

C++ calls the hazard **iterator invalidation**: `push_back` (everything, if it reallocates; the end iterator even if it does not, which is why a range-for that pushes is undefined behaviour), `erase` (from the erase point on) and `clear` (everything) invalidate iterators, references and `span`s into a vector. Using one afterwards is undefined behaviour, and nothing stops you. [Mutable borrows](/learn/mutable-borrows/#changing-a-list-while-looping-over-it) runs a `push_back` in a loop under AddressSanitizer. Rust makes it a compile error.

</ForLang>

<Exercise name="unique" title="Remove repeats, keep the order">

</Exercise>

</Exercise>

<Exercise name="reverse-in-place" title="Reverse a &mut slice">

<Exercise name="take-longest" title="Take a name out of the list">
