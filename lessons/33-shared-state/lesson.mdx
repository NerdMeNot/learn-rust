## What Rust refuses

A **data race** is two accesses to the same memory with nothing ordering them, at least one a write and at least one not atomic (the wording of the [`atomic` docs](https://doc.rust-lang.org/std/sync/atomic/index.html#memory-model-for-atomic-accesses)). In the gotcha near the top, `move` hands the list to the first thread (E0382). An `Arc` shares a value but, through `Deref`, hands out only `&`:

<Snippet file="arc-read-only.fail.rs" />

A `Mutex` holds the value, so there is no way to reach it without asking:

<Snippet file="no-access.fail.rs" />

The `help:` is the recipe: `lock().unwrap()`. `Arc<Mutex<T>>` means many owners (`Arc`), one user at a time (`Mutex`). In safe Rust a data race does not compile; [deadlocks and logic races](#what-rust-does-not-prevent) do.

## `Arc<T>`: owners across threads

An `Rc` updates its count with no protection, so the compiler refuses to send one to a thread ([Smart pointers](/learn/smart-pointers/#across-threads-arct) shows the error). `Arc` is the same idea with an atomic count.

<Snippet file="arc-count.rs" />

`Arc::clone` copies a pointer and adds one to the count; the `Vec` is not copied (`ptr_eq` asks whether two `Arc`s share one allocation). `Arc<RefCell<_>>` is refused: `Send` means a value may move to another thread, `Sync` means a `&T` may be shared between threads, and `RefCell` is not `Sync` ([Send and Sync](/learn/send-sync/#arcrefcellt-fails-arcmutext-works) shows the error). The fix is `Mutex`, the thread-safe cousin of `RefCell`.

## `Mutex<T>`: the data lives inside the lock

`lock()` waits until no one else holds the lock, then returns a **guard**. The guard derefs to the data, and when it is dropped the lock opens ([Common traits](/learn/common-traits/) covers `Drop`). `lock` returns a `Result` because of poisoning, next section. It takes `&self`, so a shared `&Mutex` can still reach the data mutably: a `Mutex` is the thread-safe `RefCell` ([Smart pointers](/learn/smart-pointers/#cell-and-refcell-change-it-through-a-shared-reference)). Each `+= 1` below is a read, an add and a write, and the lock makes those three steps one:

<Snippet file="counter.rs" />

`try_lock` returns `Err` at once instead of waiting, so the next programs use it to ask whether the lock is free:

<Snippet file="guard.rs" />

A temporary guard dies at the end of its statement; a named guard lives to the end of its block, or until `drop`. The surprise is a temporary in the head of a `match`, `if let` or `while let`, which lives through the whole body. An `if` condition releases it, and edition 2024 (this page's) drops an `if let` guard before the `else`:

<Snippet file="temporaries.rs" />

Locking again in such a body, from the same thread, is a bug: the [`lock` docs](https://doc.rust-lang.org/std/sync/struct.Mutex.html#method.lock) call the behaviour unspecified and say it might panic or deadlock. Bind the value first, as `let n = ...;` does. A `Mutex` is not reentrant because its guard gives `&mut`, and a second guard on one thread would be a second `&mut` to the same data; the unstable `ReentrantLock` (`check-unstable-sync.fail.rs`) hands out only `&` for [that reason](https://doc.rust-lang.org/std/sync/struct.ReentrantLockGuard.html).

## When a thread panics: poisoning

If a thread panics while it holds a guard, the data may be half updated. The `Mutex` records that, and the next `lock()` returns `Err`. The error still contains the guard:

<Snippet file="poison.rs" />

The docs call the data "likely tainted". `into_inner` on the error is the way back in, and `clear_poison` (Rust 1.77) marks the repair done. Most code simply unwraps, as the docs note, which turns one panic into a panic in every thread that touches the lock:

<Snippet file="poison-unwrap.rs" />

That is a design choice. [The translating section](#translating-from-what-you-know) runs the same failure in Go, Java, Kotlin, C#, Python, C++ and C, where the lock simply opens and the next thread sees the half-done state. A non-poisoning `Mutex` is also unstable in Rust 1.99.1; the `parking_lot` crate's `Mutex` does not poison.

## `RwLock<T>`: many readers or one writer

`read()` gives a shared guard, any number at once. `write()` gives an exclusive one, and only a panicking writer poisons the lock. Two reader threads below meet at a barrier, so each must hold its guard while the other arrives; if readers excluded each other this would never finish:

<Snippet file="rwlock.rs" />

If a writer is waiting, may new readers go ahead? The docs leave the policy to the operating system and promise none. An `RwLock<T>` is shared across threads only when `T` is `Sync` too, where a `Mutex<T>` needs just `Send` (`check-rwlock-sync.fail.rs`). Start with a `Mutex`, and switch when many threads really do read at once.

## Atomics: one value, no lock

An atomic type changes a single integer, flag or pointer in one indivisible step; it exists for `bool`, the integers and raw pointers, not for a struct. `fetch_add` returns the old value. `compare_exchange(current, new, ..)` writes only if the value is still `current`, and says what it found otherwise. `compare_exchange_weak` may fail even when the values match, so it goes in a retry loop; `try_update` is that loop written for you (`fetch_update` is its older, now deprecated name). A `static` needs no `Arc`.

<Snippet file="atomic.rs" />

The extra arguments are orderings ([Going deeper](#orderings-and-what-they-promise)); use `SeqCst` when unsure. Atomics make each operation indivisible, not a sequence of them: this load-then-store loses an update every run, because the barrier makes both threads read first:

<Snippet file="atomic-lost.rs" />

## `Condvar`: wait until something is true

A condition variable puts a thread to sleep until another thread says something changed. It pairs with a `Mutex` holding the state. `wait_while` releases the lock while asleep, takes it back on waking, and re-checks the condition, because a wake-up can be spurious (with no `notify` behind it; the [docs](https://doc.rust-lang.org/std/sync/struct.Condvar.html) say so). The closure says when to keep sleeping: the call "blocks the current thread until the provided condition becomes false". The second half notifies before anyone waits, and the flag makes that safe.

<Snippet file="condvar.rs" />

## What Rust does not prevent

The type system rules out data races, and says nothing about these two problems.

**Deadlock.** Each thread below holds one lock and wants the other's. `try_lock` shows what `lock` would have done, which is wait forever, so the program can run and report it:

<Snippet file="deadlock.rs" />

Nothing in a type records lock order. The cures are one agreed order (the second exercise), one lock at a time, or one lock for both.

**Logic races.** [Send and Sync](/learn/send-sync/#what-they-do-not-prevent) runs one: every access is locked, and the balance still goes negative, because the check and the change lock separately. The cure is one guard across both. Two threads each try to take 60 from 100, and exactly one succeeds in either order:

<Snippet file="one-guard.rs" />

## Holding a guard too long

While a guard lives, every other thread that wants the lock waits. Do the slow work first and lock only to store the result:

<Snippet file="slow-part.rs" />

In `async` code a function can pause at an `.await` with its guard alive. A future holding a `MutexGuard` across an `.await` is not `Send`, so a runtime's `spawn` refuses it ([Async basics](/learn/async-basics/) shows the error). A lock taken in a temporary, or in a block that ends before the `.await`, is accepted (`check-guard-dropped.rs`); a named guard that is used and then passed to `drop` is still refused on 1.99.1 (`check-guard-drop.fail.rs`). To hold a lock across an `.await` on purpose, [Tokio](/build/tokio/) has `tokio::sync::Mutex`.

## Which tool, and how big a lock

| You need | Reach for | Shown above |
|---|---|---|
| read-only data in many threads | `Arc<T>` | `arc-count.rs` |
| one value that many threads change | `Arc<Mutex<T>>` | `counter.rs` |
| many readers, occasional writer | `Arc<RwLock<T>>` | `rwlock.rs` |
| a counter, flag or id | `AtomicUsize`, `AtomicBool` | `atomic.rs`, `release-acquire.rs` |
| sleep until a condition holds | `Mutex` plus `Condvar` | `condvar.rs` |
| a value built once, first use wins | `OnceLock`, `LazyLock` | `check-once.rs` |

If threads produce values that one place consumes, use a [channel](/learn/channels/): a queue that moves each value from a sender to a receiver, so one thread owns it at any moment and no lock is needed. If many threads read and update one table, share it. Neither is the better one in general; the question is whether the data should move or stay put. The `entry` call does a map's compound update inside the one lock, as Java's `merge` does:

<Snippet file="tally.rs" />

`std` has no concurrent map: the options are a `Mutex<HashMap>`, a map split into shards, or a crate (`dashmap` for a map, see [Maps](/learn/maps/); `crossbeam-queue` for queues). How much one lock covers is a separate choice. One lock around everything is the simplest and has no lock-order problem, but shuts out every other thread. A lock per item lets threads on different items run at once, though a view of several items needs several locks, in an agreed order. Shards sit in between: threads on different shards run together, and your code picks the shard (`check-granularity.rs` asserts these three).

## Orderings, and what they promise

An ordering says what else becomes visible, not whether the operation is atomic: `fetch_add` is indivisible with any of them. By the [docs](https://doc.rust-lang.org/std/sync/atomic/enum.Ordering.html), `Relaxed` means "no ordering constraints, only atomic operations", and a pair of `SeqCst` operations also synchronizes other memory, in one total order. A flag announcing "the other data is ready" needs `Release` on the store and `Acquire` on the load:

<Snippet file="release-acquire.rs" />

Rust follows the C++20 model [without `consume`](https://doc.rust-lang.org/std/sync/atomic/index.html#memory-model-for-atomic-accesses). There is no default ordering: `hits.fetch_add(1)` is E0061 (`check-atomic-default.fail.rs`). `compare_exchange` takes one ordering for success and one for failure, and a `Release` failure ordering is a deny-by-default lint, because a failed exchange writes nothing (`check-atomic-failure.fail.rs`). When unsure, use `SeqCst`.

A `Mutex` is used the same way: what one thread wrote before unlocking is visible to the next thread that locks, as after leaving `synchronized` (Java's [rule](https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html#jls-17.4.4)). The `Mutex` docs do not use the words "happens-before"; the [Nomicon](https://doc.rust-lang.org/nomicon/atomics.html) calls `Acquire` and `Release` "perfectly suited for acquiring and releasing locks".

## Try it

Each exercise has checks in `main`: replace the `todo!()` calls and run until it prints `all checks passed`. The starters compile and stop at the first `todo!()`. Where a wrong answer could hang, the check fails with a message instead.

<Exercise name="cache" title="Compute outside the lock">
`get_or_compute` caches slow results in a `Mutex<HashMap>`. The slow call runs with the lock released, and if another thread stored the key meanwhile, that value wins. It is not single-flight: two threads that miss together may both compute. Then write `warm`: an `Arc` around the table, a clone moved into each thread, a join for all. The checks fail a held guard, an overwrite, no caching, and copying the map.
</Exercise>

<Exercise name="bank" title="Lock in order, move money atomically">
`transfer` needs two account locks, and opposite transfers deadlock if each takes `from` first. Lock the lower index first, handle `from == to` and an empty account, and call the provided `lock` so the checks can read your order. Hold both locks until both balances change: a reader sums every account while four threads transfer, and the total must be 3000 every time.
</Exercise>

<Exercise name="update" title="A retry loop without a lock">
Write `update`, your own `try_update`, on a `Slot` with only `load`, `store` and `compare_exchange`. A check plays a rival thread that changes the slot while your closure runs, which fails a load-then-store and a single `compare_exchange`. Then write `claim_all`: one slot shared with `Arc`, and per-thread counts that add up to the limit exactly.
</Exercise>
