## What `unsafe` unlocks

The Rust Book says it plainly: ["`unsafe` doesn't turn off the borrow checker or disable any of Rust's other safety checks"](https://doc.rust-lang.org/book/ch20-01-unsafe-rust.html#performing-unsafe-superpowers). It lets you do five more things. The compiler cannot check any of them, so each comes with a promise, and breaking one is *undefined behavior* (UB). That is not an exception, a crash you can reproduce or a wrong answer. A program with UB has no defined meaning: the compiler may assume it never happens, so the program can do anything, including look fine until the optimizer changes. The [Nomicon](https://doc.rust-lang.org/nomicon/what-unsafe-does.html) says UB "gives the compiler full rights to do arbitrarily bad things to your program". The Reference's [list](https://doc.rust-lang.org/reference/behavior-considered-undefined.html) of what counts, which is not exhaustive, includes data races, accessing a dangling or misaligned place, and producing an invalid value such as a `bool` that is not 0 or 1. To *dereference* a pointer is to read or write the value at its address.

| `unsafe` lets you | You promise |
|---|---|
| dereference a raw pointer (see [Raw pointers](#raw-pointers)) | it is not null, is [aligned](/learn/stack-heap/#padding-and-alignment-optional) for its type, points at a live value of that type, and no other access conflicts with it |
| call an `unsafe fn` | the conditions in its `# Safety` documentation hold |
| read or write a `static mut` | no other access happens at the same time |
| implement an `unsafe trait` | you meet the contract the trait states ([`Send` and `Sync`](/learn/send-sync/) are the ones you meet) |
| read a field of a `union` (all its fields share the same bytes) | the bytes are a valid value of that field's type |

The [Reference](https://doc.rust-lang.org/reference/unsafety.html) lists a few more, such as declaring an `extern` block and applying an `unsafe` attribute; these five are the ones you will meet first. Each appears in this program, and the `ZeroIsValid` trait shows the pattern for a trait: its author writes the contract, and each `unsafe impl` signs it.

Without the `unsafe` blocks, the dereference, the call, the `static mut` and the union read are each an E0133 error, as in the gotcha above. And the block does not switch the borrow checker off: two `&mut` into one vector are still refused inside it.

## Should you write it?

Usually not. It is needed to call C or an operating system, to build a primitive such as `Vec` that safe Rust cannot express, and for a structure the borrow checker rejects (the [borrow checker lesson](/learn/borrow-checker/) lists the safe alternatives first). It is not a speed switch. If you know `sun.misc.Unsafe` as the Java way to go faster, do not carry that over: `get_unchecked` skips one check and hands you a proof to write, and this page has no timing. Try safe code, then std (`split_at_mut`, `swap`, `mem::take`), then a well-used crate, and only then your own block, small and commented, behind a safe function.

## Raw pointers

A raw pointer, `*const T` or `*mut T`, is an address with a type and nothing else: no lifetime, no promise that it is valid, and it can be null or dangling (pointing at memory that is gone). You can make one from a reference (`&raw const x`, `&raw mut x`, or `as_ptr()`), and arithmetic that only produces a pointer (`wrapping_add`) is safe too. Reading or writing through one is the unsafe part.

<Snippet file="raw-pointers.rs" />

Safe code cannot get a dangling reference, but it can make a dangling pointer. Reading this one would be undefined behavior, so it only checks for null:

<Snippet file="dangling.rs" />

The compiler does not follow raw pointers, so it cannot tell you two of them overlap. That is the second half of "you promise": here `a` and `b` point at the same `n` and nothing complains (with two `&mut n` it would be E0499).

<Snippet file="raw-alias.rs" />

Raw pointers may alias, as in C. References may not: a `&mut` is a promise that nothing else reaches that place, like a C `restrict` pointer, and merely creating two `&mut` to one place is UB even if neither is used. Turning raw pointers back into references is a common way to get UB inside `unsafe`.

## `unsafe fn`, blocks and `// SAFETY:` comments

The `unsafe` keyword has two jobs, and the [Reference](https://doc.rust-lang.org/reference/unsafe-keyword.html) names them: it is "used to create or discharge the obligation to prove something safe". An `unsafe fn` creates an obligation: its caller must meet the conditions it lists. An `unsafe` block discharges one: the author says "I checked". The habit that makes this readable is two comments. On the function, a `# Safety` section in the docs lists the conditions, as [`get_unchecked`](https://doc.rust-lang.org/std/primitive.slice.html#method.get_unchecked) does ("Calling this method with an out-of-bounds index is undefined behavior"). On each block, a `// SAFETY:` comment says why the conditions hold *here*. The Book calls the `SAFETY` comment idiomatic. Clippy can ask for both: `missing_safety_doc` is on by default for a `pub unsafe fn`, `undocumented_unsafe_blocks` is opt-in (the page build does not run Clippy).

Since the 2024 edition, the body of an `unsafe fn` is no longer an unsafe block. The [edition guide](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-op-in-unsafe-fn.html) says the `unsafe_op_in_unsafe_fn` lint "now warns by default" (warning-level output is not shown on this page, so the snippet denies it to show the message):

<Snippet file="unsafe-fn-body.fail.rs" />

Keep blocks small, as the Book advises.

## A safe function over unsafe code

The aim is not to scatter `unsafe` through a program. It is to hide it behind a function that is safe to call, whose checks make the promise true for every input. The classic case is `split_at_mut`: two non-overlapping `&mut` halves of one slice. Safe Rust cannot write it, because the borrow checker sees two borrows of `v`, even though they cover different elements:

<Snippet file="split-naive.fail.rs" />

The standard library has `split_at_mut` already. Writing it again with raw parts shows the shape:

<Snippet file="split.rs" />

Who is responsible for what?

| Piece | Who makes the promise | Written as |
|---|---|---|
| `from_raw_parts_mut` (an `unsafe fn`) | the code that calls it | its `# Safety` docs, your `// SAFETY:` |
| `split_at_mut` (a safe `fn`) | its author, for **every** caller and input | the `assert!`, and the comment above the block |
| a private field that must stay true (an *invariant*) | the module that owns it ([Modules](/learn/modules/)) | no code outside can break it |

If the `assert!` were missing, a safe call with a big `mid` could create slices past the end. Such a function is called *unsound*: safe code can cause undefined behavior through it. With the check, a bad input is a panic, which is defined:

<Snippet file="split-panic.panic.rs" />

`Vec` is built the same way. By the [documentation](https://doc.rust-lang.org/std/vec/struct.Vec.html#guarantees) it is "a (pointer, capacity, length) triplet", with `len` initialized elements followed by `capacity - len` uninitialized ones. Safe methods are the only code that can change `len`, so they can keep it true, and safe code never sees the uninitialized slots.

This is also why Rust's standard library needs `unsafe` when Java's `ArrayList` and Python's `list` do not. They sit on a layer that is already unchecked: `ArrayList` on an array the JVM allocates and bounds-checks (HotSpot is C++), a `list` on C code inside CPython. Rust has no such runtime underneath, so that layer is Rust: a small amount of `unsafe` inside `Vec` and friends, behind safe methods.

<Snippet file="vec-parts.rs" />

## Globals and `static mut`

## Reviewing a block: five questions

When you read someone's `unsafe` block, or write your own, ask the questions that the Reference's list of undefined behavior turns into. They are the choices in the first exercise.

| Ask | What goes wrong if the answer is no |
|---|---|
| Is the index or offset **in bounds**? | an access past the end of the allocation (`get_unchecked`, `ptr.add`) |
| Is the pointer [**aligned**](/learn/stack-heap/#padding-and-alignment-optional) for the type it is read as? | a misaligned access, which the Reference lists as undefined behavior |
| Is what it points at **alive**? | a dangling access, as with the pointer to `x` above |
| Is the memory **initialized**, and a valid value of the type? | an invalid value, such as the `bool` that held 3 |
| Is anything else using the same memory (is it **aliased**)? | two `&mut` to one place, or a data race ([Send and Sync](/learn/send-sync/)) |

A good `// SAFETY:` comment answers the ones that apply, with the reason: "`mid` is at most `len`, asserted above" answers the first and the last in `split_at_mut`. A comment that says "this is fine" answers none.

## How much `unsafe` is out there

A 2020 study ([Evans, Campbell and Soffa](https://arxiv.org/abs/2007.00752)) found `unsafe` "in less than 30% of Rust libraries", while more than half of the libraries "cannot be entirely statically checked by the Rust compiler because of Unsafe Rust hidden somewhere in a library's call chain". Both facts matter: your own code may have none, and your program still runs on code that does.

Each exercise has checks in `main`: replace the `todo!()` calls and run until it prints `all checks passed`. The starters compile and fail when run.

<Exercise name="audit" title="Audit six unsafe blocks">

</Exercise>

<Exercise name="wrap" title="Wrap an unsafe function">
`swap_unchecked` is an `unsafe fn`. Write `swap_checked`, a safe function that returns an error for a bad index and calls it otherwise. The unsafe function only counts a bad call, so a mistake cannot corrupt memory here. The checks count calls to it: using the safe `slice::swap` instead (real code would), or calling it without checking, fails.
</Exercise>

<Exercise name="registry" title="Share state without `unsafe`">
This is the lesson's "do not reach for `unsafe`" exercise. A registry of names has to be shared by four threads.
