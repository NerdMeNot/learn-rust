<p class="lr-layer">The toolkit</p>

[Macros, attributes and naming](/learn/macros-attributes-naming/#format-strings) owns the format-string syntax: `{}`, `{:?}`, `{0}`, `{name}`, width, precision and `{{`. This page covers what is behind it: which trait each letter calls, how to write those traits for your own types, and where the text goes. Outputs come from Linux on 64-bit ARM with Rust 1.99.1, a debug build.

## One trait for each letter

Every `{...}` calls a method of a trait on the value, and the letter after the colon picks the trait. A type prints that way only if it implements the trait.

| You write | Trait | Meant for |
|---|---|---|
| `{}` | `Display` | people |
| `{:?}` `{:#?}` | `Debug` | programmers; `#` spreads it over lines |
| `{:x}` `{:X}` | `LowerHex` `UpperHex` | hexadecimal |
| `{:o}` `{:b}` | `Octal` `Binary` | base 8, base 2 |
| `{:e}` `{:E}` | `LowerExp` `UpperExp` | scientific notation |
| `{:p}` | `Pointer` | an address |

<Snippet file="traits.rs" />

The program prints only whether the `{:p}` text starts with `0x`, because the address is different on every run. `{:x?}` is `Debug` with integers in hex. An integer has every trait in the table except `Pointer`, which is for references and pointers. The letters are a closed set: `{:K}` is an unknown format trait, and `{:p}` on an integer is E0277:

## Writing `Display`

`impl Display` is one method, `fmt`, which gets a `&mut Formatter` (named `f`): the destination for the text, plus the **spec**, everything after the colon (`>8`, `.2`, `#x`). It also gives you `to_string()`, through a blanket impl ([Common traits](/learn/common-traits/#the-rules-between-traits)); the [`ToString` docs](https://doc.rust-lang.org/std/string/trait.ToString.html) say to implement `Display`, not `ToString`. What you can do with the `Formatter`:

| Call | What it does |
|---|---|
| `f.write_str("text")` | writes the text exactly as given |
| `write!(f, "{}-{}", a, b)` | formats, then writes; returns `fmt::Result`, so end with it or add `?` |
| `f.pad("text")` | writes text after applying width, fill, alignment and precision |
| `Display::fmt(&self.0, f)` | lets another value print itself, with the caller's spec |
| `f.width()` `f.precision()` `f.fill()` `f.align()` `f.alternate()` `f.sign_plus()` `f.sign_aware_zero_pad()` | read the spec |
| `f.debug_struct("Name")`, `debug_tuple`, `debug_list`, `debug_map`, `debug_set` | builders for `Debug` |

Each trait in the first table has its own `fmt`. This `LowerHex` reads the `#` flag:

<Snippet file="custom-hex.rs" />

To see the spec your code receives, print it:

<Snippet file="spec-dump.rs" />

`{:*^+#012.3}` is fill `*`, centered, a sign, `#`, a `0` flag, width 12, precision 3. Nothing applies any of it: it is data, and each `fmt` decides what it means.

## Width is your job

[Common traits](/learn/common-traits/#printing-debug-and-display) showed the surprise; this is the cause. Padding is not applied to the text your `fmt` writes. `write!(f, "#{}", self.0)` starts a new format with an empty spec, so the caller's `{:>8}` is in `f` and nothing reads it. Three types, three behaviours:

<Snippet file="width-ignored.rs" />

`Plain` ignores the width. `Padded` uses `f.pad`, which applies width, fill and alignment, and also **precision**: `{:.2}` cuts the text to two characters, which is why `#12345` became `#1`. `Forward` hands the spec to its `f64`, so `8.2` and `+.1` work for free. Use `pad` for text-like output and forwarding for a wrapper around a number. To pad several pieces as a whole, build the `String` first and then call `pad`.

`Debug` has the same rule. The [std::fmt docs](https://doc.rust-lang.org/std/fmt/index.html) say "alignment might not be implemented by some types. In particular, it is not generally implemented for the Debug trait", and suggest formatting first, then padding the result:

<Snippet file="debug-pad.rs" />

The derived `Debug` for `Some(1)` passes the spec to the `1` inside, so `{:5?}` pads the number and not the whole value.

## `Debug`: derive it, or build it

`#[derive(Debug)]` is the default choice, and the std docs say "generally speaking, you should just derive a `Debug` implementation". Write it by hand when a field should not appear. The builders print the right shape and make `{:#?}` work for free:

<Snippet file="debug-manual.rs" />

`finish_non_exhaustive()` ends with `..` so a reader knows a field was left out. `{:?}` on text shows its escapes, which makes invisible differences visible:

<Snippet file="debug-escapes.rs" />

Tab, newline, control characters, the zero-width space `U+200B` and the combining accent after the `e` are escaped, and so is `"` in a string (a `'` only in a `char`), while `é`, `日本` and the emoji print as themselves. A float with no fraction prints as `1.0` in `Debug` and `1` in `Display`; `1e21` is `1e21` in `Debug` and all its digits in `Display`. [A later section](#debug-is-not-a-file-format) says why not to depend on the exact form.

## Numbers

The spec letters (`{:08.3}`, `{:+}`, `{:#x}`) are in [the earlier lesson](/learn/macros-attributes-naming/#format-strings). A precision cuts text and an integer ignores it (`{:.3}` of `"Hello"` is `Hel`, of `7` it is `7`). Zeros go after the sign (`{:08.3}` of `-3.14159` is `-003.142`), and a `bool` pads like text. `{:x}` of a negative integer shows the bits of its type (`-1i8` is `ff`, `-255i32` is `ffffff01`), and `{:e}` of `1234.5` is `1.2345e3`. `check-table.rs` asserts each of these. Floats have the odd cases:

<Snippet file="floats.rs" />

`0.30000000000000004` is what `0.1 + 0.2` produces in `f64`, not a formatting fault: `{}` prints enough digits to parse back to the same value (the third line checks it). `NaN` and the infinities print as words, and `-0.0` and `{:.0}` of `-0.5` keep their sign. For rounding, the std docs say "Rust uses round half-to-even": `0.5` and `2.5` give `0` and `2`, `1.5` and `3.5` give `2` and `4`, and the exact ties `0.125` and `0.375` give `0.12` and `0.38`. `2.675` gives `2.67` because it is not a tie: the nearest `f64` is a little below it (the last line prints 20 digits). Languages differ here: Java, Kotlin and JavaScript's `toFixed` round `0.5, 1.5, 2.5` to `1 2 3`, while Go, Python, C, C++ and C# print `0 2 2` like Rust (each language's tab below has its run).

## Width and precision from variables

[The earlier lesson](/learn/macros-attributes-naming/#format-strings) showed `{:>w$}` and `{:.p$}`. There are three more forms: `1$` takes the width from argument 1, `.*` takes the precision from the next argument before the value, and a named argument (`width = 4`) works too. The common use is a column as wide as its widest entry:

## Where the text goes

| Macro | Destination |
|---|---|
| `print!` `println!` | standard output. Panics if the write fails (the [docs](https://doc.rust-lang.org/std/macro.print.html)) |
| `eprint!` `eprintln!` | standard error |
| `format!` | a new `String` |
| `write!` `writeln!` | anything with a `write_fmt` method: a `String`, a `Vec<u8>`, a file, a locked stdout. Returns a `Result` |
| `dbg!` | standard error, with file, line and expression; returns the value |
| `panic!` `assert!` `todo!` | the message is a format string too |

## `format_args!`, and what `format!` costs

`format!` builds a `String`, which keeps its text on the heap, so a non-empty `format!` allocates. `write!` into a buffer with room does not, and `format_args!` builds only a description of the text (a `fmt::Arguments`), which `println!` and `write!` are made from. This counts calls to the allocator, which are not time:

<Snippet file="allocations.rs" />

`format!` allocated once for a short text and six times for `{n:>200}`, where the padding made the `String` grow again (this run's count, not a promise). `write!` allocated once into `String::new()` and never into a `String` with room. The last line passes a `format_args!` to a function that writes it to `io::sink()`: 0, so a function can take `fmt::Arguments` and pass it on with no `String` built. (Creating one alone could not fail the count, so the program measures the passing.) A logging wrapper forwards its arguments the same way ([the earlier lesson](/learn/macros-attributes-naming/#format-strings) left that for here):

## What the macro hands to your code

The format string is checked at compile time, but the text is made at run time. The macro builds a `fmt::Arguments`, which the [docs](https://doc.rust-lang.org/std/fmt/struct.Arguments.html) call a "precompiled version of a format string and its arguments", and at run time each value's trait method is called with its spec in a `Formatter`. So a trait that a type lacks is a compile error, and a spec that a trait ignores is not.

For a one-off view of a value you do not need a new type: `fmt::from_fn` (stable since Rust 1.93) turns a closure into a value that implements `Display` and `Debug`:

## When `fmt` returns an error

`fmt::Result` lets a destination whose write fails cancel the formatting. The [`fmt::Error` docs](https://doc.rust-lang.org/std/fmt/struct.Error.html) say an impl "should not return this Error unless they received it from their Formatter". Return one anyway and `write!` into a `String` hands it back, while `to_string()` panics, because for a `String` the only possible failure is a bug in your `Display`:

<Snippet file="fmt-error.panic.rs" />

## Debug is not a file format

The std docs for [`Debug`](https://doc.rust-lang.org/std/fmt/trait.Debug.html) say: "Derived Debug formats are not stable, and so may change with future Rust versions. Additionally, Debug implementations of types provided by the standard library (std, core, alloc, etc.) are not stable". So parsing `{:?}` output, or saving it for comparison, can break on a compiler upgrade. When the text is a format that another program reads, use a library such as serde ([Serde](/build/serde/)), and use `Display` for text that you promise to keep.

## No locale

Some languages change formatting by the machine's language settings: C's `printf` follows `setlocale` ([man page](https://man7.org/linux/man-pages/man3/setlocale.3.html)), C# follows [`CultureInfo.CurrentCulture`](https://learn.microsoft.com/en-us/dotnet/api/system.globalization.cultureinfo.currentculture), and Java's `String.format` uses a `Locale`. The C and C# behaviour is from their docs, not run (this image has no German locale or culture data), so there a `1.5` may print as `1,5`. Rust's formatting does not. The [docs](https://doc.rust-lang.org/std/fmt/index.html#localization) say the format functions "do not have any concept of locale and will produce the same results on all systems regardless of user configuration". There is no thousands separator and no way to choose a decimal comma. People use crates for that, [`num-format`](https://crates.io/crates/num-format) for grouping and [ICU4X](https://crates.io/crates/icu) for full locale data; this page has not run either.
