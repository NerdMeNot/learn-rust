<p class="lr-layer">The toolkit</p>

A **trait** names a set of methods. A type that has those methods, and says so, can be used wherever the trait is asked for. It is what Rust uses where other languages use interfaces, abstract base classes or protocols. Outputs come from Linux on 64-bit ARM, Rust 1.99.1.

## Defining a trait and implementing it

<Snippet file="first-trait.rs" />

- `trait Speaker { ... }` lists methods. `speak` has no body: every type that implements the trait must write one. `shout` has a body: a **default method**, used unless a type replaces it.
- `impl Speaker for Dog { ... }` is a block of its own, apart from the struct. The trait is not part of the type's definition, so it can be added later, and in another place.
- `Parrot` replaces `shout`, and `Dog` and `Robot` keep the default. The default calls `self.speak()`, so it works for any type.
- The first parameter means what it does in [Methods](/learn/methods/).
- Once the trait is in scope, `Dog.speak()` is an ordinary method call ([scope](#a-traits-methods-and-scope), below).

A replacement cannot call the default it replaces. There is no `super`. Writing `Speaker::shout(self)` inside `Parrot`'s `shout` names `Parrot`'s own `shout`, so it calls itself until the stack is gone:

<Snippet file="super-call.panic.rs" />

Move the shared part into another method or a plain function.

A trait can hold more than methods:

| A trait can list | Example | Shown in |
|---|---|---|
| Methods, with or without a default body | `fn speak(&self) -> String;` | `first-trait.rs` above |
| Associated functions, with no `self` | `fn make() -> String;` | [two traits](#two-traits-one-method-name) |
| Associated types and constants | `type Item;`, `const LIMIT: u32;` | [associated items](#associated-types-and-constants) |
| Fields | not allowed | below |

<Snippet file="no-fields.fail.rs" />

A trait body has no fields. When the data matters, the trait asks for a method (`fn name(&self) -> &str`) and each type decides where the data is stored.

## Asking for a trait: bounds

A function says which trait it needs from its argument. That requirement is a **bound**.

<Snippet file="bounds.rs" />

- `T: Speaker` reads "T is some type that implements `Speaker`". `T` is a **type parameter**, a placeholder the caller fills in ([Generics](/learn/generics/)).
- `&impl Speaker` is the same bound without naming `T`. `where T: Speaker` is the same bound moved after the signature, which helps when a signature gets long.
- `+` asks for several traits: `T: Speaker + Display`.
- Inside the function, the bounds decide which methods `T` has: `intro_a` can call `speak` because of its bound, and nothing the bound does not mention.

Each call to `intro_a` uses one concrete type, chosen by the caller and known when the program is compiled: the compiler produces a copy of the function for each type. That is **static dispatch**. [Going deeper](#static-and-dynamic-dispatch-in-one-program) shows the other kind.

## A trait's methods and scope

To call a trait's method on a concrete type, the trait must be in scope in the **module** where you write the call. A `mod` block in the same file is another scope (a named container of code, covered in [Modules](/learn/modules/)):

<Snippet file="not-in-scope.fail.rs" />

The impl exists, and the compiler suggests `use crate::zoo::Speaker;`. Two cases need no import: a generic function with a bound `T: zoo::Speaker`, and a `&dyn zoo::Speaker`. The bound names the trait, so its methods are reachable. And `use ... as _;` brings a trait into scope for method calls without taking its name:

<Snippet file="scope-ok.rs" />

The **prelude** (the names every module gets without writing `use`) already includes `Iterator`, `Clone`, `Default` and other common traits, which is why you do not usually import those. [Its page](https://doc.rust-lang.org/std/prelude/index.html) lists them.

## Two traits, one method name

Two traits can have a method with the same name. A type's own method wins over a trait's. To pick a trait yourself, name it:

<Snippet file="explicit-call.rs" />

- `Vehicle::start(&car)` calls the `Vehicle` version, passing the receiver by hand.
- `<Car as Appliance>::make()` is the **fully qualified** form. With no `self` there is no receiver to guide the choice, so you name the type and the trait.

A type may implement both traits, even when both have a default `start`. The error comes only from a bare call that could mean either:

## Traits for types you did not write

You can implement your trait for any type, including `i32`, `&str` and `Vec<T>`:

<Snippet file="foreign.rs" />

`impl<T: Describe> Describe for Vec<T>` says "a `Vec` of describable things is describable". A blanket impl covers every type that meets a bound:

<Snippet file="blanket.rs" />

`impl<T: Display> Shout for T` gave `Shout` to `&str`, `i32` and `Robot` at once. The standard library's [`ToString`](https://doc.rust-lang.org/std/string/trait.ToString.html) reaches every `Display` type this way.

There is a limit. You may write `impl Trait for Type` if the trait **or** the type is defined in your own crate (your package's code). This is the **orphan rule**:

| Trait | Type | Allowed? | Shown by |
|---|---|---|---|
| yours | yours | yes | `first-trait.rs` |
| yours | foreign (`i32`, `Vec<T>`) | yes | `foreign.rs` |
| foreign (`Display`) | yours | yes | `newtype.rs` below |
| foreign (`Display`) | foreign (`Vec<i32>`) | no, unless a type of yours is among the trait's own type parameters (next paragraph) | `orphan.fail.rs` below |

<Snippet file="orphan.fail.rs" />

[E0117](/errors/#E0117) is the orphan rule. Traits can take type parameters (`From<T>` does), and `impl From<Meters> for f64` is accepted when `Meters` is your type, because it appears among the trait's parameters. The [Reference](https://doc.rust-lang.org/reference/items/implementations.html) states the full rule.

The way around is a **newtype**: a one-field struct that wraps the foreign type. The wrapper is yours, so the impl is allowed:

<Snippet file="newtype.rs" />

## Supertraits

A trait can require another trait. `Pet: Speaker` reads "to be a `Pet`, a type must also be a `Speaker`", so `Pet`'s methods may call `speak`:

## Associated types and constants

A trait can leave a **type** or a **constant** for each implementing type to choose:

<Snippet file="assoc.rs" />

`C::Item` means "the `Item` of whichever `C` this is", and `C::KIND` reads the constant. `&'static str` is the type of a string literal such as `"names"` ([Lifetimes](/learn/lifetimes/) explains `'static`). `alloc::string::String` is the full path of the standard library's `String`.

`Iterator` has a `type Item` like this ([Iterators](/learn/iterators/) writes one). In Java, `Iterator<T>` lets the user of the interface pick `T`. Here each implementing type writes its `Item` once, so the trait is plain `Iterator`.

## Returning "something that implements a trait"

`impl Speaker` also works as a return type. It hides the type but does not make it vary:

<Snippet file="impl-return.fail.rs" />

`impl Speaker` means one concrete type that the compiler knows and the caller does not name. When the answer depends on run-time data, the compiler suggests a **trait object**: `Box<dyn Speaker>`, a pointer to any value that implements the trait. [`Box<T>`](/learn/ownership/#boxt-one-value-on-the-heap) is an owned pointer to a value on the heap, and `dyn` marks that the method is looked up while the program runs ([Trait objects](/learn/trait-objects/)):

<Snippet file="impl-return.rs" />

A trait is not a type, so its bare name cannot stand where a type goes. Programmers used to interfaces write this first:

<Snippet file="bare-trait.fail.rs" />

[E0782](/errors/#E0782) lists the fixes: a bound, `impl`, or `dyn`. [Trait objects](/learn/trait-objects/) explains why `dyn` is needed.

| Spelling | Where | The type is |
|---|---|---|
| `T: Speaker`, `&impl Speaker` | parameter | any one type, chosen by the caller |
| `-> impl Speaker` | result | one type, chosen by the function |
| `&dyn Speaker`, `Box<dyn Speaker>` | parameter, result, or inside a collection | any type, looked up at run time |

## Translating from what you know

<ForLang only="go">
A Go interface and a Rust trait both list methods. They differ in who has to say that a type fits.

| In Go | In Rust |
|---|---|
| `type Speaker interface { Speak() string }` | `trait Speaker { fn speak(&self) -> String; }` |
| `Robot` fits because it has `Speak` | `impl Speaker for Robot { ... }` |
| `var _ Speaker = Robot{}` (a check that it fits) | not needed: the impl is the check |
| `func introduce(s Speaker)` | `fn introduce(s: &dyn Speaker)`: a run-time lookup, as in Go |
| `func Foo[T Speaker](x T)` | `fn foo<T: Speaker>(x: &T)`: one compiled copy per type |
| `[]Speaker` | `Vec<Box<dyn Speaker>>` (a trait is not a type, so not `Vec<Speaker>`) |
| no default methods: a helper function (`shout(s Speaker)`) | a default method in the trait |
| embedding a struct to promote its methods | no equivalent: a field plus forwarding methods |
| `any`, `s.(Robot)` | see [Trait objects](/learn/trait-objects/) |

Embedding shares code, but it is not a default method: the embedded type cannot call the outer type's `Speak`.

<ForLang only="java kotlin csharp">
| In Java / Kotlin / C# | In Rust |
|---|---|
| `interface Speaker` | `trait Speaker` |
| a `default` method (Java), a method with a body (Kotlin), a default interface method (C# 8) | a default method in the trait |
| `class Dog implements Speaker` / `: Speaker` | `impl Speaker for Dog { ... }`, a separate block |

| `<T extends Speaker>`, `<T : Speaker>`, `where T : ISpeaker` | `T: Speaker`: a copy per type, no lookup |
| `List<Speaker>` | `Vec<Box<dyn Speaker>>` (not `Vec<Speaker>`: a trait is not a type) |
| `Speaker.super.shout()` (Java), `super<Speaker>.shout()` (Kotlin) | none: the `Parrot` example above overflows the stack |
| two interfaces with the same default: Java and Kotlin refuse the class until it overrides | both impls compile; the error is at a bare call |
| an `abstract class` that has fields | a struct with the fields, and a trait with getter methods |

A trait is not an abstract class. It holds no fields, so a Kotlin or C# interface property becomes a getter method, and there is no struct inheritance ([Methods](/learn/methods/#no-inheritance)). Shared state lives in a struct your type contains; shared behaviour lives in default methods or a blanket impl.

A class has to be edited to implement an interface, which you cannot do to a library class, so the answer there is a wrapper that holds the library object. Rust has the wrapper too (the newtype above), and when the trait is yours it also lets you implement it on the library type directly.
</ForLang>

## Static and dynamic dispatch in one program

<Snippet file="dispatch.rs" />

- `generic` prints a different `T` for each call. The compiler knows which `speak` to call, because each call is for one type. This is **static dispatch**, and the [generics lesson](/learn/generics/) explains how the compiler produces a version for each type. (The text `type_name` prints is not guaranteed, so use it to look, not to compare.)
- The `Vec<Box<dyn Speaker>>` holds a `Dog` and a `Robot` side by side, which a `Vec<T>` cannot. The method is looked up while the program runs. This is **dynamic dispatch**, and [Trait objects](/learn/trait-objects/) explains the lookup.

## Why the orphan rule exists

Without it, two crates could implement the same trait for the same type, and Rust would not know which to use (the property that prevents this is **coherence**). The same reasoning applies in your own crate: two impls that could both apply to one type are refused ([E0119](/errors/#E0119)):

<Snippet file="overlap.fail.rs" />

`i32` implements `Display`, so the blanket impl already covers it. The rule's price is boilerplate: a newtype forwards the methods you need by hand ([advanced traits](https://doc.rust-lang.org/book/ch20-02-advanced-traits.html) covers the pattern).

## `derive` is a trait impl

Each name in `#[derive(Debug, Clone)]` is a trait, and the compiler writes the `impl` block from the fields ([Structs](/learn/structs/)). Write one by hand when the generated one is wrong or no `derive` exists, as for `Display`; [Common traits](/learn/common-traits/) says which to derive. A trait can also have no methods at all, like `Copy`: implementing it is a statement about the type ([`std::marker`](https://doc.rust-lang.org/std/marker/index.html) lists such traits).

## A trait or an enum?

Both answer "this value is one of several kinds"; they differ in who can add a kind.

| | An [enum](/learn/enums/) | A trait |
|---|---|---|
| The kinds | listed in one place; adding one means editing the enum | any crate can add a type with an `impl` |
| `match` over the kinds | the compiler checks that every case is covered | not directly: the code sees the trait's methods, not the concrete type |

When you know every kind (the commands of a protocol), an enum lets the compiler check each place that handles them. When other code should add kinds (plugins, a library that calls your code), use a trait. Neither is better in general.
