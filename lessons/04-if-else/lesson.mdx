## `if` is an expression, and both arms agree

An `if`/`else` has a value, so it can sit wherever a value can ([Statements and expressions](/learn/statements-expressions/#statement-or-expression) has the rules). A branch may be a whole block; its last expression, with no `;`, is the value.

<Snippet file="as-value.rs" />

Every branch must give the same type, because `limit` gets exactly one. Rust will not widen an integer to a float to match:

<Snippet file="arms-differ.fail.rs" />

The fix is `1.0`: an integer and a float are different types, not one `number`. A branch that ends in `return`, `continue` or `panic!` is exempt, because it never gives a value (the [never type](/learn/statements-expressions/#when-nothing-comes-back-the-never-type)). An `if` with no `else` gives `()`, so it cannot supply a value (E0317, in [Smaller slips](/learn/statements-expressions/#smaller-slips)).

## Only a `bool` is a condition

There is no truthiness: a number, a string, a list or an `Option` is not a condition (E0308, "expected `bool`"). The number case is in [Smaller slips](/learn/statements-expressions/#smaller-slips) and the others are on [What Rust lacks](/learn/what-rust-lacks/). Write the comparison you mean: `n != 0`, `!name.is_empty()`, `found.is_some()`.

## Comparing and combining

`==` and `!=` compare contents (numbers, text, tuples, arrays and many other types); `<`, `>`, `<=` and `>=` need a type with an order. Two numbers must have the same type, with no implicit widening ([Numbers and types](/learn/types/#no-implicit-widening)). A few mixed pairs, such as `String` and `&str`, are written to be comparable.

## `else if`, and when to use `match` instead

`if`/`else if`/`else` tests in order and takes the first branch that is true. When the chain is the function's value, as here, the last `else` is required, or the chain fails with the E0317 named in the first section (message in [Smaller slips](/learn/statements-expressions/#smaller-slips)).

<Snippet file="chain.rs" />

(`&'static str` is the type of a string literal: [Reading signatures](/learn/reading-signatures/).)

When the branches compare one value with fixed cases or ranges, [`match`](/learn/match/) is more direct and the compiler checks that no case is missing. A chain of `if`s does not; use it when the tests are different questions.

## `if let` and `let ... else`

`if let` asks "does this value have this shape?" and unpacks it in one step. The pattern goes left of the `=`. Here the value is the `Result` that `parse` gives back: `Ok(number)` or `Err(reason)` ([Errors](/learn/errors/) covers it). `parse` also rejects a number that does not fit the type, as `"99999999999"` shows for `i32`. `Option` ([Option](/learn/option/)) and any enum ([Enums](/learn/enums/)) work the same way.

## Comparing floats

Floats follow IEEE 754, as in most languages: results are not exact, and NaN ("not a number") is neither smaller, equal nor larger than anything. Rust's own point is the `else`.

<Snippet file="floats.rs" />

Test closeness with a tolerance you choose, not `==`, and remember that the `else` of `x < 0.0` is not "x is zero or more" when `x` might be NaN. [Numbers and types](/learn/types/) covers the rest of float behaviour.

## Your language, in Rust

<ForLang only="go">

| In Go | In Rust |
|---|---|
| `if v, err := f(); err != nil { … } else { … }` | `if let Ok(v) = f() { … } else { … }`. The blocks swap places: Go's first block is the error, Rust's is the success, and Rust's `v` exists only there (the `else` never sees the `Err`; use `match` for that). |
| `v, err := f(); if err != nil { return err }` | `let Ok(v) = f() else { return … };` is the same guard, and `?` shortens the common case ([Errors](/learn/errors/)). |
| `if x := g(); x > 3 { … }` | A block `{ let x = g(); if x > 3 { … } }`, or compute `x` before the `if`. Rust has no init statement. |
| `switch { case n < 0: … case n == 0: … default: … }` | an `if`/`else if`/`else` chain, or [`match`](/learn/match/) |
| `var s string; if c { s = "a" } else { s = "b" }` | `let s = if c { "a" } else { "b" };` |
| `v, ok := m[k]; if ok { … }` | `if let Some(v) = m.get(&k) { … }` ([Maps](/learn/maps/); `&k` is a borrow, not a copy) |
| `if v, ok := x.(T); ok { … }`, type `switch` | `match` on an enum ([Enums](/learn/enums/)) |

Same as Go: a `bool` condition, no `int32 == int64`, NaN != NaN, `&` above `==`. New: `if` as a value, `&` and `|` that do not short-circuit, `!` on integers.

## A `bool` as an `Option`

`bool::then_some(value)` gives `Some(value)` when the `bool` is true and `None` when it is false. It is close to `if c { Some(v) } else { None }` ([Option](/learn/option/)), except that `then_some` evaluates its argument either way. Its sibling `then` takes a closure and runs it only when true ([closures](/learn/closures/)).
