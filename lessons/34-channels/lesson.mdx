## A channel is a queue with two ends

`mpsc::channel()` returns a pair: a `Sender` (`tx`) that puts values in, and a `Receiver` (`rx`) that takes them out, first in, first out. `mpsc` stands for "multiple producer, single consumer": you can clone the sender, never the receiver, so **one** thread receives. Go channels, Java queues and C# channels accept several consumers; `mpsc` does not, and the [pool](#a-pool-of-workers) shows what that costs.

<Snippet file="basics.rs" />

`send` and `recv` both return a `Result`. `recv` waits for a value, and returns `Err` only when the queue is empty and every sender is gone.

## When does `for msg in rx` end?

When the queue is empty and **every** sender has been dropped. The classic mistake is a main thread that keeps its own `tx` while it loops on `rx`: the workers finish, one sender is still alive, and the loop waits for a message that cannot come. No error is reported; the loop prints what arrived and then stops making progress. The `mpsc` docs say the program "will not complete" without the `drop`. A hang cannot be shown here, so this is the state just before it, measured with calls that give up:

<Snippet file="loop-ends.rs" />

`Empty` means "nothing now, but a sender exists", `Disconnected` "nothing, ever", and `Timeout` is `recv_timeout` giving up. All the ways to receive:

| Call | Queue has a message | Empty, a sender exists | Empty, every sender dropped |
|---|---|---|---|
| `recv()` | the message | waits | `Err(RecvError)` |
| `try_recv()` | the message | `Err(Empty)` | `Err(Disconnected)` |
| `recv_timeout(d)` | the message | waits up to `d`, then `Err(Timeout)` | `Err(Disconnected)` |
| `for m in rx`, `rx.iter()` | each message | waits | the loop ends |
| `rx.try_iter()` | each queued message | ends | ends |

"Waits" is the docs' word ("will always block the current thread"); every other cell is asserted. Whoever makes the channel holds the first `tx`: move it into the last worker or `drop(tx)` before you loop.

## Bounded channels and back-pressure

The docs call `channel()` "infinitely buffered": a producer faster than its consumer makes the queue grow without a limit. `sync_channel(n)` holds at most `n` messages: `send` waits while it is full, and `try_send` returns `Full(value)` instead of waiting. With `0` it is a rendezvous: each send completes only when a receiver takes the value.

<Snippet file="bounded.rs" />

That limit is **back-pressure**: the producer is held to the consumer's pace. This program asserts it at every receive, for three bounds, then shows `channel()` letting the producer run ahead:

<Snippet file="backpressure.rs" />

`try_send` exists only on `SyncSender`, a different type from `Sender`: a function that takes one does not accept the other.

## More than numbers

A message is any `Send` value. A channel can even carry an `Arc<Mutex<..>>`, and then both threads share memory again, with the lock visible in the type; [Shared state](/learn/shared-state/) says when a lock is the simpler tool. Channels are a design tool:

- an **enum** for several kinds of message, which also merges several sources into one receiver: one `tx` clone per source, the variant says who sent it;
- a **`Sender` inside a request**, so the other thread knows where to reply;
- a **`Result`**, so an error crosses to another thread as data;
- a **boxed closure**, `Box<dyn FnOnce() + Send>`, for "run this" ([Closures](/learn/closures/), [Trait objects](/learn/trait-objects/)).

## A pool of workers

This is fan-out, with a cost. A `Receiver` cannot be cloned, so workers share one behind `Arc<Mutex<..>>` and take the lock only to receive the next job. Idle workers wait on the lock, not on the queue; a Java `ThreadPoolExecutor` or N Go goroutines on one channel need nothing like it. (`crossbeam-channel` has cloneable receivers; not run here.) Dropping `job_tx` ends the workers:

<Snippet file="pool.rs" />

The lock must be released before the job runs. In `let job = rx.lock().unwrap().recv();` the guard is a temporary and ends at the semicolon. In `while let Ok(job) = rx.lock().unwrap().recv() { .. }` it lives through the loop body, so no other worker can take a job while this one is busy (`try_lock` returns `Ok` only if the lock is free):

<Snippet file="guard-held.rs" />

That compiles and gives correct answers, but the pool runs one job at a time ([the Rust Book](https://doc.rust-lang.org/book/ch21-02-multithreaded.html) shows the same trap). The second exercise catches it.

<ForLang only="go">
Go has one channel type and puts the size in the `make`; Rust has two constructors. Go closes from the sending side; Rust has only the last drop.

| In Go | In Rust |
|---|---|
| `make(chan T)`, unbuffered | `sync_channel(0)` |
| `make(chan T, n)` | `sync_channel(n)` |
| no unbounded channel built in | `channel()` |
| `close(ch)` by a sender | drop the last `Sender` |
| `v, ok := <-ch` | `rx.recv()`: `Ok(v)` or `Err` |
| `for v := range ch` | `for v in rx` |
| `select { case ch <- v: default: }` | `tx.try_send(v)`, on a `SyncSender` |
| `select { case v := <-ch: default: }` | `rx.try_recv()` |
| `case <-time.After(d)` | `rx.recv_timeout(d)` |
| `sync.WaitGroup` and a closer goroutine | not needed: each producer owns a clone of `tx`; the last drop closes |
| `close(done)` or `ctx.Done()`, a broadcast | no equivalent in `std`; see below |
| `select` over several channels, `nil` to switch a case off | not in `std`: one `Receiver` fed by every sender, tagged by an enum; an `Option<Receiver>` for "off" |

## What each end can do

`Receiver` is neither `Clone` nor `Sync`: `rx.clone()` is E0599 and sharing `&rx` between threads is E0277, which is why the pool needs a `Mutex` around `rx`. `Sender` is `Clone`, and has been `Sync` since Rust 1.72 (the docs say so), so a `&Sender` may be shared between threads. [Send and Sync](/learn/send-sync/) explains the traits.

## What `std` does not have

- **`select` over several receivers.** Use one receiver fed by many senders, tagged by an enum, or poll `try_recv` on each. `crossbeam-channel` provides `select`, and async runtimes such as Tokio bring their own channels ([Async basics](/learn/async-basics/)); neither is run here.
- **Several consumers on one queue.** `std::sync::mpmc` exists but is unstable on 1.99.1 (as is `oneshot`):

<Snippet file="mpmc.fail.rs" />

- **A `close` call**, a sender count or a queue length: `rx.len()`, `tx.close()` and `tx.sender_count()` do not compile. A channel closes when you drop its ends. `is_disconnected` exists but is unstable on 1.99.1 (E0658).

<Exercise name="ordered-results" title="Results in input order">
Write `parallel_map`: run `f` on every item, each on its own thread, and return the results in input order. Send `(index, result)` on a channel, so that arrival order does not matter. Clone the sender for each thread, and drop the original `Sender`: while it is alive the receiving loop never ends, for every input. Item 0 is the slowest and results fall and rise, so arrival order fails and so does sorting the values. (Joining `JoinHandle`s in order, Java's `Future`s or Python's `ThreadPoolExecutor.map` also pass; this exercise is for the channel and the loop that must end.)
</Exercise>

<Exercise name="worker-pool" title="A pool of boxed jobs">
Finish `Pool`: `new` starts workers that share one `Receiver`, `run` sends a boxed closure, and `finish` lets the queued jobs run and joins the workers. `jobs` is an `Option` so that `finish` can take the `Sender` out and drop it while the workers still run. Two jobs wait for each other at a `Barrier` (`Barrier::new(2)`: the first `wait()` sleeps until a second arrives), so they finish only if two workers are inside a job at once; a worker that keeps the lock while it runs a job is caught, as are a thread per job and a `finish` that does not join. `finish` drains the queue and cannot abort it: Go would cancel with a `ctx`; here you would add a shared `AtomicBool` that workers check (not part of this exercise).
</Exercise>

<Exercise name="hang-up" title="Stop when nobody is listening">
Write `count_up`: send 0, 2, 4, ... until `send` fails, and return how many sends succeeded and the value that bounced. A rendezvous channel makes the counts exact. A version that unwraps panics, and one that ignores the error never stops; the checks name both mistakes. This is what `ctx.Done()` does for a Go producer, done by the type.
</Exercise>
