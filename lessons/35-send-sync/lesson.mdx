## Two questions about a type

Threads share one address space, so a type that is fine on one thread can cause a **data race** on two: both use the same memory, at least one writes, nothing orders them. Safe Rust rules that out in two halves. One is the borrow rules: a `&mut` is exclusive ([Mutable borrows](/learn/mutable-borrows/)). The other is two **marker traits**, traits with no methods that state a fact about a type:

- **`Send`**: a value of this type may be moved to another thread.
- **`Sync`**: a `&T` may be used by several threads at once. The [standard library's definition](https://doc.rust-lang.org/std/marker/trait.Sync.html) is "`T` is `Sync` if and only if `&T` is `Send`".

Nearly everything has both; the exceptions change data without telling anyone, or count owners without locking. If you share data by never changing it, `Sync` is the compiler-checked version: nothing changes a `Vec<String>` through a `&`, so threads can read an `Arc<Vec<String>>` with no lock.

A function asks for the trait in a bound, as `thread::spawn` does ([Reading signatures](/learn/reading-signatures/#threadspawn-three-bounds-at-once)). To ask the compiler yourself, state a bound in a function that does nothing:

## The types you meet

Which of the two does a thread call ask for? Look at what happens to the value. Error messages use the same words: "cannot be **sent**" is `Send`, "cannot be **shared**" is `Sync`.

- It is **moved** to another thread: `thread::spawn(move || ...)`, a channel's `send`, a thread's return value. That needs `Send`.
- Several threads look at it **through a reference**: a `thread::scope` borrow, a `static`, the `T` inside an `Arc<T>`. That needs `Sync`. (The `Arc` itself is moved too, so it needs `Send`.)

| Type | `Send` | `Sync` | Because |
|---|---|---|---|
| `i32`, `String`, `Vec<String>` | yes | yes | plain owned data; a `Vec<T>` is as good as its `T` |
| `Rc<i32>` | no | no | the count is not atomic |
| `Arc<i32>` | yes | yes | the count is atomic; `Arc<T>` needs `T` to be both `Send` and `Sync` |
| `Cell<i32>`, `RefCell<i32>` | yes | no | change through `&self` with no synchronization |
| `Mutex<i32>` | yes | yes | access is one thread at a time; needs `T: Send` |
| `Mutex<Rc<i32>>` | no | no | `T: Send` fails: clones of the `Rc` escape the lock |
| `MutexGuard<'_, i32>` | no | yes | pthreads release a lock on the thread that took it ([docs](https://doc.rust-lang.org/std/sync/struct.MutexGuard.html)) |
| `*const i32`, `*mut i32` | no | no | a lint ([Going deeper](#making-the-promise-yourself)) |
| `&T` | if `T: Sync` | if `T: Sync` | sending a `&T` is sharing the `T` |
| `&mut T` | if `T: Send` | if `T: Sync` | sending a `&mut T` hands the `T` over |
| `&mut Rc<i32>` | no | no | the `T` is not `Send` |
| `Arc<RefCell<i32>>` | no | no | `RefCell` is not `Sync`, so the `Arc` is not `Send` |
| `Arc<Mutex<i32>>` | yes | yes | the pattern for shared, changeable data |
| `RwLock<Cell<i32>>` | yes | no | many readers hold `&T` at once, so `T` must be `Sync` too |
| `Receiver<i32>` | yes | no | one consumer ([Channels](/learn/channels/)) |

`check-table.rs` asks the compiler about every row, both columns, and fails if one differs. It also checks that `&T` is `Send` exactly when `T` is `Sync`, for nine types.

## They come from the fields

`Send` and `Sync` are **auto traits**: the compiler gives a struct, tuple or closure the trait when all its fields have it, with no `impl`. So one bad field spoils every struct, tuple or closure that contains it. Types with their own rules, such as `Mutex`, `Arc` and `&T`, decide differently. ## `Arc<RefCell<T>>` fails, `Arc<Mutex<T>>` works

`Rc` to `Arc` is the obvious repair, and it is not enough ([Shared state](/learn/shared-state/) shows this error first):

<Snippet file="arc-refcell.fail.rs" />

The note says "required for `Arc<RefCell<i32>>` to implement `Send`". `Arc<T>` is `Send` only when `T` is `Send` and `Sync`, and each half has a reason. `Sync`: every thread holding the `Arc` gets a `&T`, and `RefCell` changes its borrow count through `&self` unsynchronized. `Send`: [`Arc::into_inner`](https://doc.rust-lang.org/std/sync/struct.Arc.html#method.into_inner) hands the `T` itself to whichever thread holds the last `Arc`. So `Arc<MutexGuard<i32>>` is not `Send`, though a `MutexGuard` is `Sync`.

A `Mutex<T>` is `Sync` when `T` is `Send`, not when `T` is `Sync`. The lock makes access exclusive, so two threads never hold a `&T` together. But exclusive access is a `&mut T`, and a thread holding one can swap the `T` out or, for an `Rc`, clone it, and both leave the lock behind:

<Snippet file="escape.rs" />

Two threads could each keep such a clone and update one unlocked, non-atomic count. So a `Mutex` makes a `Send` type shareable, even a `Cell`, and does nothing for an `Rc`. An `RwLock` lets many readers hold a `&T` at once, so it asks for `Sync` too. The version that compiles:

## Fixing a `Send` or `Sync` error

Read the first line for the type that is the problem, then use the table.

| The message says | Usual fix |
|---|---|
| `Rc<T>` cannot be sent between threads safely | `Arc<T>` (`Mutex<Rc<T>>` does not help) |
| `Cell<T>` or `RefCell<T>` cannot be shared between threads safely (also for a `static`) | replace it with `Mutex<T>`, `RwLock<T>` or an atomic; wrapping is not enough (`RwLock<Cell<T>>` is not `Sync`) |
| `MutexGuard<..>` cannot be sent between threads safely | take the lock inside the thread |
| `dyn Trait` cannot be sent between threads safely | `Box<dyn Trait + Send>` |
| `*const T` cannot be sent between threads safely | a safe type; `unsafe impl` only if you can state why it is sound (Going deeper) |
| "required because it appears within the type `X`" | one field of `X` is the cause: follow the chain up to it |

## Translating from what you know

In your language, which types may cross threads is mostly documentation or convention (this collection is not safe, immutable objects are). Rust works it out from the types and checks it at every thread call.

<ForLang only="go">
Go compiles racy code. Its race detector (`go run -race`) is a run-time tool: it reports accesses with no synchronization between them, not only ones that overlap in time, but only on executions you ran (the [docs](https://go.dev/doc/articles/race_detector): it "only finds races that happen at runtime"). [Shared state](/learn/shared-state/#translating-from-what-you-know) runs one. The Go [memory model](https://go.dev/ref/mem) says a racy read of a word-sized value sees a value some goroutine wrote, but for an interface, slice, map or string "such races can in turn lead to arbitrary memory corruption".

| In Go | In Rust |
|---|---|
| a `sync.Mutex` field beside the data | `Mutex<T>` around the data |
| `go run -race` | the compiler, for safe code, on every path. Neither flags a check-then-act bug in which every access is locked |
</ForLang>

<ForLang only="java kotlin csharp">
Racy code compiles: the gotcha at the top hands an `ArrayList` or `List<T>` to a thread, and the docs say neither is safe to share ([Java](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/ArrayList.html), [.NET](https://learn.microsoft.com/en-us/dotnet/api/system.collections.generic.list-1)). Annotations such as `@ThreadSafe`, `@Immutable` and `@GuardedBy` record intent, and a checker can enforce it: Error Prone's [`@Immutable`](https://errorprone.info/bugpattern/Immutable) is a compile-time error for a class that is not deeply immutable. They are opt-in per class; `Send` and `Sync` are worked out for every type, the library's too.
</ForLang>

<ForLang only="java kotlin">
Java does not treat a race as undefined behavior, but "defined" is not "correct". The memory model limits what a racy read may see (JLS [17.4.5](https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html): an array cannot report a wrong length), yet [17.7](https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html#jls-17.7) lets a non-volatile `long` be written as two 32-bit halves, so a read can see a value no thread wrote. `volatile` makes each access visible, not a read followed by a write atomic. ## Making the promise yourself

Both traits are `unsafe` to implement. `unsafe impl Send for T {}` tells the compiler "I checked, this is fine", and if you are wrong the result is undefined behavior ([Nomicon](https://doc.rust-lang.org/nomicon/send-and-sync.html)). A raw pointer is neither `Send` nor `Sync`, which the Nomicon calls "more of a lint": a type holding one has untracked ownership, and refusing by default stops it becoming thread-safe by accident. It is the `void *` of Rust, with a guard. So this type is refused even though it is harmless:

<Snippet file="raw-no-send.fail.rs" />

This version's claim covers every `Table` that can exist: the field is private and `new` takes a `&'static i32`, which is shared, read-only, never freed, and already `Send` and `Sync`. (Contrived: a `&'static i32` field needs no `unsafe`. It shows the form.)

<Snippet file="unsafe-send.rs" />

[`unsafe`](/learn/unsafe/) has its own lesson; the point is the size of the promise: nothing checks it, and it must hold for every value the type can have.

To go the other way, `impl !Send for T {}` would be the direct form, but the compiler refuses it on stable:

<Snippet file="negative.fail.rs" />

What works today is a field that is not `Send`. `PhantomData<T>` stores no data; the compiler treats the struct as if it held a `T`, and its `Send` and `Sync` follow `T`'s ([docs](https://doc.rust-lang.org/std/marker/struct.PhantomData.html)). So `PhantomData<*const ()>` removes both traits (`Pinned` in `check-table.rs`).

## What they do not prevent

The Nomicon [is exact](https://doc.rust-lang.org/nomicon/races.html): safe Rust has no data races, and does not prevent "general race conditions". It also calls deadlock "safe" ([Shared state](/learn/shared-state/#what-rust-does-not-prevent) runs both). That page's check-then-act example uses an `Arc<Mutex<i32>>`, which the table shows is `Send` and `Sync`. Every access is locked, the types raise no objection, and two threads still lose an update, because the check and the change are separate steps. The cure is a design: one guard around both. The marker traits answer "may these threads touch this value", never "is the sequence of touches right".
