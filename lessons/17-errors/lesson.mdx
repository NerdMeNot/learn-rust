## Two kinds of failure

Rust splits failures into two kinds and gives each its own tool.

| | Expected failure | Bug |
|---|---|---|
| Examples | The user typed `abc` where a number goes. A file is missing. | An index past the end. A "can't happen" that happened. A broken promise by the caller. |
| What happens | The caller decides: retry, use a default, report it | Nobody can fix it at run time, so the thread stops (on the main thread, the program) |
| Tool | Return a `Result` | `panic!` |
| In the signature | Yes. The caller handles it or passes it up with `?`; ignoring it draws a warning | No |

A value that is merely missing, such as a search that found nothing, is not a failure: that is `Option`, in the [previous lesson](/learn/option/). The rest of this lesson is mostly `Result`.

## `Result` is an enum

`Result<T, E>` is an enum with two variants: `Ok(T)` holds the value when things worked, `Err(E)` holds the error when they did not. [Enums](/learn/enums/) showed how to take one apart with `match`. A `Result` is the same:

`parse` can fail, so it returns a `Result`. You cannot use the number without opening it first, and `match` will not compile unless you handle both arms. The `{e}` and `{:?}` texts above come from the same `ParseIntError`.

## `?`: pass the error up

Most functions can do nothing useful about an error except hand it to their caller. A `match` for that on every line is noisy, so Rust has `?`:

<Snippet file="question-mark.rs" />

After an expression that returns a `Result`, `?` means: if it is `Ok`, take the value out and carry on. If it is `Err`, return that error from the whole function, right now. The happy path stays a straight line, and each `?` marks a place where the function may return early.

Here is the same function with the `?` written out as a `match`:

<Snippet file="question-expanded.rs" />

Both print the same. The `Err` arm calls `From::from(e)` before returning. `From` is the standard way to say "make this type out of that one". Here the error is already a `ParseIntError`, so it changes nothing.

### When the error types differ

The error `?` finds has to become the error type in your signature. If Rust has no conversion between the two, you get E0277:

<Snippet file="mismatch.fail.rs" />

The message says it: `?` converts through the `From` trait, and `String` has no `From<ParseIntError>`. Three ways out:

- **`map_err`**: change the error by hand at that spot (below).
- **A `From` impl** for your own error type, so `?` converts by itself (see [Your own error type](#your-own-error-type)).
- **`Box<dyn Error>`** as the error type, which accepts any error type (see [the catch-all](#boxdyn-error-the-catch-all)).

### `?` needs a function that returns a `Result`

`?` returns the error, so the function's return type must be able to hold one. `main` returns `()` by default:

<Snippet file="question-in-main.fail.rs" />

The `help:` shows the fix: give `main` a return type ([below](#main-can-return-a-result)). `?` also works on an `Option` inside a function that returns `Option`, as the [Option lesson](/learn/option/) shows.

### Cleanup still happens

An early return from `?` does not skip cleanup. A value with a `Drop` impl (code that runs when the value goes out of scope, from [Ownership](/learn/ownership/)) is cleaned up on both paths:

<Snippet file="cleanup.rs" />

This does the job of `finally`, a destructor or `defer`. One limit: `drop` cannot return an error, so if closing or flushing a file can fail, call the type's `flush` yourself and use `?`.

## Do not ignore a `Result`

If you call a function that returns a `Result` and do nothing with it, Rust warns you: `Result` is marked `#[must_use]`. By default that is only a warning and the program still builds. To show the message on this page, the program below turns that one warning into an error:

`let _ = save("");` says "I know, and I do not care". It is allowed and visible in the code, and only the first call is flagged.

## Panics: when the thread stops

A panic stops the code at the spot where something impossible happened. The most common source is `unwrap`, which takes the `Ok` value out of a `Result` and panics on `Err`:

<Snippet file="unwrap-err.panic.rs" />

Read it from the top. `thread 'main' (1) panicked at src/main.rs:3:36:` gives the thread (`main`, then its id number, which differs between runs) and the place: line 3, column 36. The next line is the message; for `unwrap` it shows the error's `Debug` form (the `{:?}` text). The `note:` says that setting `RUST_BACKTRACE=1` makes a panic also print a backtrace, the calls that led here ([the Book, chapter 9.1](https://doc.rust-lang.org/book/ch09-01-unrecoverable-errors-with-panic.html)). A panic on the main thread ends the program with exit code 101 (with the default unwinding, [below](#exit-codes)).

By default a panic **unwinds**: Rust walks back up the call stack and cleans up each function's values. The Book describes a `panic = "abort"` setting in `Cargo.toml` that skips the cleanup and ends the program at once.

A panic ends only the thread it happens on. A spawned thread that panics leaves the rest of the program running, and the thread waiting for it gets an `Err` from `join` ([threads](/learn/threads/) come later):

<Snippet file="thread-panic.rs" />

`std::panic::catch_unwind` can catch a panic, but its docs say not to use it as a general try/catch.

Panics also come from indexing past the end, a failed `assert!` (checked in every build, release too), `unreachable!()`, `todo!()`, and your own `panic!("message")`. Here is a panic that is the right call: the function has a rule (the slice must not be empty), and a caller who breaks it has a bug:

<Snippet file="panic-bug.panic.rs" />

The Book's rule of thumb: return a `Result` when failure can happen in a correct program, such as bad input. Panic when an assumption or promise is broken, because that is a bug, and a caller should not have to handle a bug ([chapter 9.3](https://doc.rust-lang.org/book/ch09-03-to-panic-or-not-to-panic.html)). If an empty list can come from user data, return an `Option` or `Result` instead.

## `unwrap` and `expect`

`unwrap` says "I am sure this worked, and if I am wrong, stop." It is what an uncaught exception does elsewhere, minus the traceback. `expect("why")` adds your message in front of the error, so the panic explains your assumption:

<Snippet file="expect-err.panic.rs" />

Both are fine in some places:

<Snippet file="unwrap-fine.rs" />

- **A value you can check by reading the code**, like the hard-coded address. Use `expect` and say why it cannot fail.
- **Tests, examples and quick prototypes**, where a panic is the failure you want. The Book says this too.
- **A chosen fallback** with `unwrap_or(80)` is not a crash at all.

On real input, `unwrap` waits for the wrong input. Use `?` or `match` there.

## Changing and combining results

Small methods on `Result` cover most of what you would otherwise `match` for. `|e| …` is a closure, a small unnamed function ([Closures](/learn/closures/) come later). Read it as "given `e`, do this".

<Snippet file="combinators.rs" />

- `ok_or(error)` turns an `Option` into a `Result`: `None` becomes `Err(error)`. `ok_or_else(|| …)` builds the error only when needed, which matters when that costs something, such as making a `String`.
- `map_err(f)` rewrites the error and leaves an `Ok` alone. Use it to add context or switch to your own error type.
- `and_then(f)` runs the next step only if the last one worked. The step returns a `Result` itself, so failures chain without nesting.

More methods. The inputs are `Ok(4)` and `Err("bad")`, with `String` as the error type:

| Method | Does | On `Ok(4)` | On `Err("bad")` |
|---|---|---|---|
| `map(\|n\| n * 10)` | change the `Ok` value | `Ok(40)` | `Err("bad")` |
| `map_err(\|e\| e.len())` | change the `Err` value | `Ok(4)` | `Err(3)` |
| `unwrap_or(0)` | value, or a fallback | `4` | `0` |
| `unwrap_or_else(\|e\| e.len() as i32)` | value, or compute a fallback from the error | `4` | `3` |
| `ok()` | drop the error: becomes an `Option` | `Some(4)` | `None` |
| `is_ok()` / `is_err()` | ask which one | `true` / `false` | `false` / `true` |

## Your own error type

A `String` error works for a first draft, but a caller cannot tell failures apart without comparing text. The usual answer is an `enum` with one variant per way to fail. Variants can carry data, as [Enums](/learn/enums/) showed:

<Snippet file="custom-error.rs" />

Four parts:
- `#[derive(Debug)]` gives the `Debug:` lines, the shape of the value for programmers.
- `impl fmt::Display for ConfigError` writes the message a person reads, the `Display:` lines (what `{}` prints). An `impl` block holds the functions of a type, as in [Methods](/learn/methods/). This one reads `impl Trait for Type`: a **trait** is a named set of functions a type promises to provide, much like an interface, and `Display` is the one `{}` asks for ([Traits](/learn/traits/) covers them). For now read it as "here is how to print a `ConfigError`". `write!` is `println!` that writes into `f`. `fmt::Result` is a short name for `Result<(), fmt::Error>`.
- `impl Error for ConfigError` marks the type as an error, which `Box<dyn Error>` and other tools need. It requires `Debug` and `Display`. Its `source` method is optional: it returns the error that caused this one, or `None`. Copy that signature as written. A message describes its own level and leaves the cause to `source`, so the cause is not printed twice.
- `impl From<ParseIntError> for ConfigError` is the function `?` calls. Because it exists, `text.parse()?` compiles in a function that returns `Result<_, ConfigError>`, and `NotANumber` is built for you. When two failures of one type need different context, use `map_err` instead.

The `match` in `fmt` has no `_` arm, so a new variant makes the compiler list every `match` that needs one.

## `Box<dyn Error>`: the catch-all

When you do not care which errors there are, only that they are errors (a small tool, a script, `main`), the error type can be `Box<dyn Error>` ([in a library's API](/learn/idioms/#boxdyn-error-in-a-librarys-api)):

<Snippet file="boxed.rs" />

Read `Box<dyn Error>` as "some error, of a type decided when the program runs". `dyn` marks a type not fixed at compile time. A `Box` is a pointer to a value on the heap, and the value is any type that implements `Error`. ([Trait objects](/learn/trait-objects/) get their own lesson later; the [picture below](#what-a-result-looks-like-in-memory) shows what is inside.) `?` turns any type that implements `Error` into one. So does `.into()`, which is `From` seen from the other side, and it also turns a `&str` or `String` into one.

The price is that the type is hidden. `downcast_ref` asks "was it this one?", but a `match` on an enum is nicer. Many projects use their own enum in libraries and `Box<dyn Error>` in applications.

<Aside type="tip" title="Real projects use two crates for this">
A **crate** is a library you add to a project. `thiserror` writes the `Display`, `Error` and `From` code above from a few attributes. `anyhow` gives you one error type that, like `Box<dyn Error>`, holds any error, and it adds context ("while reading config.toml") as an error travels up. [Errors in real apps](/build/app-errors/) shows both. Learn the by-hand version first: `thiserror` generates this code.
</Aside>

## What `?` really does

The `match` earlier is a simplified `?`. The Reference defines `?` through a trait named `Try`, which is unstable, so you cannot implement it for your own types yet. For a `Result` its rules are the ones used here: `Ok(val)` evaluates to `val`, and `Err(e)` returns `Err(From::from(e))`. The same operator also covers `Option` and a few other types ([Reference](https://doc.rust-lang.org/reference/expressions/operator-expr.html)).

The conversion is why `Box<dyn Error>` accepts any type that implements `Error`: it has a `From` impl for those types (and for `&str` and `String`), which the `?` in `boxed.rs` uses.

## Error chains and `source`

An error often has a cause: "could not load limits.txt", because "bad value for threads", because "invalid digit found in string". Each error returns the one below it from `source()`, and `custom-error.rs` already did this for `NotANumber`. This program walks a two-level chain, then does what Go's `errors.As` does: look for a `ParseIntError` at any depth.

<Snippet file="chain.rs" />

Testing only the top-level error finds nothing, because `downcast_ref` and `matches!` look at one layer. The loop over `source()` finds the `ParseIntError`. It is the same shape as Go's `errors.Unwrap`, Java's `getCause`, C#'s `InnerException` and Python's `__cause__`. The std docs say a cause should be reached through `source()` or shown in `Display`, but not both.

## Try it

Each exercise has checks in `main`. Open it in the Playground, replace the `todo!()`, and run it until it prints `all checks passed`. A plain `for` loop is fine.

<Exercise name="parse-range" title="Parse a range">
Write `parse_range`, which turns `"3-7"` into `Ok((3, 7))`, with an `Err` message for each failure: no `-` (`"missing '-'"`), a side that is not a whole number (starting `"bad start"` or `"bad end"`), and a start after the end (`"start is after end"`). Use `split_once`, `ok_or`, `map_err` and `?`. Spaces are fine, and an empty side such as `"-7"` is an error.
</Exercise>

<Exercise name="username" title="Check a username">
Finish the `Display` impl for `UsernameError`, then write `check_username`. A name is 1 to 12 characters, each alphanumeric (letters and numbers of any script count) or `_`. Count characters, not bytes: twelve `é` are 24 bytes and still a valid name.
</Exercise>

<Exercise name="sum-numbers" title="Sum a list of numbers">
Write `sum_numbers`, which adds up `"1, 2, 3"`. Return a `Box<dyn Error>` for a bad piece and for a sum that overflows an `i32` (see `checked_add`). An empty string has no numbers, so its sum is 0, but `"1,,2"` has an empty piece and is an error.
</Exercise>
