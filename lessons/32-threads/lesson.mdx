## Start a thread, wait for it

`thread::spawn` takes a closure, runs it on a new thread and returns a `JoinHandle<T>`, where `T` is what the closure returns. `join()` waits for the thread and gives that value back inside a `Result`:

Dropping a `JoinHandle` does not stop the thread: the [docs](https://doc.rust-lang.org/std/thread/struct.JoinHandle.html) say it *detaches* it, and nothing can wait for it afterwards. [Reading signatures](/learn/reading-signatures/#threadspawn-three-bounds-at-once) explains `spawn`'s bounds.

## `move`: the thread owns what it uses

## Hand data in, get it back

A `move` closure takes ownership, and its return value hands it back. A `Vec` can go to a thread, be changed there, and return, with no copy of the elements:

## A thread that panics

By default a panic ends the thread, not the program (a build with `panic = "abort"` ends the process, as Go does: [Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html#panic)). `join()` returns `Err` holding the panic's payload, boxed as `Any`, so a handler asks for the type it expects. It is a `&str` for fixed text (the compiler folds even `panic!("boom {}", 1)`) and a `String` for a message built from a run-time value, so a handler tries both:

<Snippet file="panic-join.rs" />

The messages go to the error stream when the panics happen. `.unwrap()` on the `Err` starts a new panic in the joining thread, with a message about the `Err`; `let _ = handle.join();` discards the value and the news that the thread panicked:

<Snippet file="join-unwrap.panic.rs" />

If the work itself can fail ([Errors](/learn/errors/)), `join()` adds a layer: the outer `Result` says whether the thread panicked, the inner one is the job's own. `?` flattens them, once the outer error has a message:

<Snippet file="nested-result.rs" />

## Borrowing without `move`: `thread::scope`

`thread::scope` runs a closure with a handle `s` that spawns threads which may borrow local variables. The scope joins them all before it returns, so no borrow outlives the variable. No `move`, no `Arc`:

<Snippet file="scope.rs" />

`spawn` insists that a closure owns what it uses, or borrows only data that lives for the whole program (`'static`, [Lifetimes](/learn/lifetimes/#static)). A scope lifts that, because it joins. The closure must still be `Send`, which marks the types that may move to another thread ([Send and Sync](/learn/send-sync/)).

The borrowing rules still hold inside a scope. Two threads that both add to one counter are the classic data race, which C, Go and Java compile. Rust refuses it:

<Snippet file="scope-mut.fail.rs" />

Safe Rust has no data races ([Nomicon](https://doc.rust-lang.org/nomicon/races.html)); races in a program's logic are still yours ([Shared state](/learn/shared-state/#what-rust-refuses)). A scoped thread that panics and was not joined by hand makes the scope panic, while the other scoped threads still run to their end; join it inside the scope to see the `Err` ([`scope` docs](https://doc.rust-lang.org/std/thread/fn.scope.html); `check-scope-panic.rs` runs both).

## Can I start 100,000 threads?

The Book says the standard library uses a 1:1 model: one operating-system thread per Rust thread ([chapter 16.1](https://doc.rust-lang.org/book/ch16-01-threads.html)). This program starts 10,000, each adding 1 to the total. A `Barrier` stops every thread that calls `wait()` until the agreed number have arrived, here the 10,000 workers and `main`, so when it opens all of them were alive at the same moment:

<Snippet file="many-threads.rs" />

That is a count, not a cost: nothing here measures time or memory, and it says nothing about 100,000. Each thread has a stack of its own, and the operating system can refuse another thread. `std` has no thread pool; crates provide them. Programs that wait on huge numbers of connections usually use async tasks ([Async Basics](/learn/async-basics/)).

## Thread, scope, channel, lock or async?

Five tools, with no claim about speed:

| The job | Reach for |
|---|---|
| run something, then use its result | `spawn` and `join()` |
| several threads read or change local data, all finished before the function returns | `thread::scope` |
| a thread produces values that others consume | a channel ([Channels](/learn/channels/)) |
| several threads read or change one value that outlives the function | `Arc<Mutex<T>>` or an atomic ([Shared state](/learn/shared-state/)) |
| many tasks that mostly wait for I/O | async tasks ([Async Basics](/learn/async-basics/)) |

</Exercise>
