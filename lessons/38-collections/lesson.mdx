<p class="lr-layer" id="layer-toolkit">The toolkit</p>

`std::collections` holds the containers beyond `Vec`: `HashMap` and `HashSet`, `BTreeMap` and `BTreeSet`, `VecDeque`, `BinaryHeap` and `LinkedList`. The module docs open with advice worth hearing first: "you should probably just use Vec or HashMap", because the others "have specific use cases where they are the optimal choice". This page is about those use cases. [Vectors](/learn/vectors/) and [Maps](/learn/maps/) already cover the two basics, `entry`, `retain`, `with_capacity` and a first look at `BTreeMap` and sets. Outputs come from Linux on 64-bit ARM with Rust 1.99.1.

## Which collection?

`check-table.rs`, `check-set-index.fail.rs` and `check-linked-index.fail.rs` assert every cell below except the hashed loop order, which the docs call "arbitrary" and no test can prove:

| | Use it for | Loop order | A repeated item | `x[i]` or `x[&key]` |
|---|---|---|---|---|
| `Vec` | a list, or a stack (`push` and `pop` at the end) | by position | kept | yes |
| `VecDeque` | a queue: add at one end, take from the other | front to back | kept | yes |
| `HashMap`, `HashSet` | a value found by key; "have I seen this?" | arbitrary | replaces or is refused | map: yes, set: no |
| `BTreeMap`, `BTreeSet` | keys in order, a range of keys, the smallest or largest | sorted by key | replaces or is refused | map: yes, set: no |
| `BinaryHeap` | the biggest item next | `iter`: arbitrary; `pop`, `into_sorted_vec`: ordered | kept | no |
| `LinkedList` | joining two long lists in O(1) | front to back | kept | no |

The standard docs also give costs, with `n` items and `i` a position. `~` means expected and `*` amortized (averaged over the occasional resize):

| | `get(i)` | `insert(i)` | `remove(i)` | `range` |
|---|---|---|---|---|
| `Vec` | O(1) | O(n-i)* | O(n-i) | none |
| `VecDeque` | O(1) | O(min(i, n-i))* | O(min(i, n-i)) | none |
| `HashMap` | O(1)~ | O(1)~* | O(1)~ | none |
| `BTreeMap` | O(log n) | O(log n) | O(log n) | O(log n) |

These are [the docs' tables](https://doc.rust-lang.org/std/collections/index.html#performance), not measurements. Big-O ignores constant factors, so it cannot rank collections on a small input; for equal costs the docs say "Vec is generally going to be faster than VecDeque, and VecDeque is generally going to be faster than LinkedList". Rule a collection out with the tables, then measure.

## Sets: union and friends

The set methods return iterators, and the operators `&`, `|`, `-` and `^` build a new set (cloning the items, so `T: Clone`). Both sets must be the same kind, hashed or sorted (`check-set-needs.fail.rs`: E0308 for a mixed pair, E0369 without `Clone`). A `HashSet` has no promised order, so sort before printing:

## `VecDeque`: a queue you can index

`VecDeque` adds and removes at both ends. Iteration goes front to back whatever the layout, and `q[i]` works.

<Snippet file="deque.rs" />

Its items may sit in two pieces of memory (Going deeper shows how). A `VecDeque` is not a slice: for `sort` or a slice-only function, call `make_contiguous`, which moves the items into one piece and hands back a `&mut [T]`.

## `BinaryHeap`: the biggest next

A `BinaryHeap` is a priority queue, and it is a **max**-heap: `pop` gives the greatest item by `Ord`. `peek` looks without removing, `into_sorted_vec` ends the heap and gives a `Vec` sorted ascending (smallest first), and `peek_mut` changes the top in place and restores the heap's order when the reference goes away. Wrap items in `std::cmp::Reverse` to flip the order:

<Snippet file="heap.rs" />

Tuples and `derive(Ord)` compare field by field, so put the priority first. Ties fall to the next field:

<Snippet file="job-heap.rs" />

Both `deploy` and `alert` have priority 9, and `deploy` came out first although `alert` was pushed first, because `"deploy" > "alert"`. The docs promise no first-in, first-out order among equal items. For one, give each item an arrival number, compared last and in `Reverse` so the earlier arrival counts as greater (the second half).

A `BinaryHeap` has no comparator argument and no update in place: the order comes from the item's `Ord`, so a different order means a wrapper type or a tuple. There is no `remove` by value, no `contains` and no decrease-key (`check-heap-missing.fail.rs` gets E0599 for `new_by`, `remove` and `contains`). To change a priority, push a new entry and skip the old one when it pops.

The classic use is shortest paths. Dijkstra's algorithm, for costs that are never negative, repeatedly fixes the cost of the cheapest node not yet fixed, and a min-heap (`Reverse`) of `(cost, node)` pairs finds it:

<Snippet file="dijkstra.rs" />

Node 4 has no way in, so its answer is `None`. A cost cannot be lowered in the heap, so an entry is pushed for each route found, a node can pop more than once, and the loop skips the later, dearer entries.

## `LinkedList`: one row

The docs say "It is almost always better to use Vec or VecDeque because array-based containers are generally faster, more memory efficient, and make better use of CPU cache". The index lists reasons to use one anyway, among them that you can't tolerate amortization or want to "efficiently split and append lists". `append` joins two lists in O(1), but `split_off` still walks to the split point (O(n) in the docs); `check-table.rs` runs both. There is no `x[i]` (E0608, `check-linked-index.fail.rs`). And an insert or remove at a position you already hold is not on stable Rust: `remove` and the cursor methods are unstable, E0658 on 1.99.1 (`check-linked-unstable.fail.rs`).

## What the items must provide

`Vec`, `VecDeque` and `LinkedList` need nothing from their items. `HashMap` keys and `HashSet` items need `Hash` and `Eq` ([Maps](/learn/maps/)); `BTreeMap` keys, `BTreeSet` items and `BinaryHeap` items need `Ord` ([Common traits](/learn/common-traits/)).

`derive` gives your own types these traits; an order other than the derived one is a hand-written `Ord`, as the last exercise has you write. Leave one out and the error names it:

Both heaps pop the largest first. `std::set_intersection` works on sorted ranges, so `std::unordered_set` has no set algebra in the standard library; Rust's `HashSet` and `BTreeSet` both have it. `std::map` `[]` inserts a default for a missing key; Rust's `[]` never inserts (the gotcha above).

`std::map` keeps iterators to its entries valid across inserts and across erases of other entries, so entries never move; the program held one through 189 inserts. `BTreeMap` is a B-Tree, which keeps several entries in a node and shifts them as nodes fill and empty, so it makes no such promise, and the borrow checker enforces the other side: a reference into the map blocks an insert ([Maps](/learn/maps/)). `std::deque` likewise keeps references valid across `push_back` and `push_front` (the program held one through 2,000), where `VecDeque` is one ring buffer that may reallocate. `std::list` inserts and erases through an iterator you hold; stable `LinkedList` cannot.

## How `VecDeque` keeps both ends cheap

A `Vec` keeps its items at the start of its buffer, so `remove(0)` moves every other item down. A `VecDeque` is, in the docs' words, "a growable ring buffer": the buffer is a circle and a head position says where the first item is. Removing from the front moves the head; adding at the back may wrap round to free space at the buffer's start. This program fills a capacity-4 deque, pops two items, pushes two more and asks for the pieces:

<Snippet file="ring.rs" />

After the pushes, the items `3, 4` and `5, 6` are two slices, though the deque still iterates `3, 4, 5, 6`. `make_contiguous` moves them into one. A deque is a `Vec`-sized header plus one word, 32 bytes here against 24.

## `==` and `cmp` must agree

A `BTreeMap` or `BTreeSet` decides that two keys are the same with `cmp` alone: `insert`, `contains`, `range` and the set operations never call `==`. `collect` and `From` differ: they also use `==` to drop repeats. The `Ord` docs say `PartialEq`, `PartialOrd` and `Ord` must agree. This `Word` compares by `cmp` ignoring case but by `==` on exact spelling, which shows what a disagreement costs:

<Snippet file="case-key.rs" />

`insert` refused `ana` without calling `==` once, and `collect` kept both spellings, because `==` said they differ. A `HashMap` has the same rule: equal keys must hash equally, which `derive` guarantees and a hand-written pair can break. A key whose ordering changes while it is in the map is, say the docs, "a logic error" with unspecified results, "encapsulated to the BTreeMap" and not undefined behaviour. The map owns its keys, so ordinary code has no second handle to change one; the docs name the ways in: interior mutability (`Cell`, `RefCell`: [Smart pointers](/learn/smart-pointers/)), global state, I/O or `unsafe`.
