## A future is a value that has not run

Calling an `async fn` runs none of its body. It returns a **future**, a value that stands for the work. The [`Future` docs](https://doc.rust-lang.org/std/future/trait.Future.html) say: "Futures alone are inert; they must be actively polled for the underlying computation to make progress." **Polling** is calling the future's `poll` method, which runs the body until it finishes or has to wait. Whatever does the polling is the **executor**, the core of a runtime; a future it owns and polls is a **task**. Read `block_on`, the smallest executor, as "call `poll` until it answers `Ready`"; the other lines are explained below.

<Snippet file="lazy.rs" />

- `fetch_name()` built the future. `fetch_name is running` printed only after `block_on` polled it.
- `pin!` fixes the future in place, because `poll` demands it ([Pin](#what-the-compiler-builds-and-why-pin-exists)). A `Context` carries a **waker**, how a future asks to be polled again (next section). `Waker::noop()` does nothing; stable since Rust 1.85 ([docs](https://doc.rust-lang.org/std/task/struct.Waker.html)).
- This future finished on its first poll. The loop busy-waits.

If you call an `async fn` and ignore the result, the compiler warns (`unused_must_use`). `deny` turns the warning into an error the page can show:

<Snippet file="unused-future.fail.rs" />

The lint fires only on a discarded statement: `let _ = save();` and `drop(save());` stay silent (`check-unused-let.rs`), though the work never runs.

## Pending, Ready and the waker

`poll` answers `Ready(value)` when the future is finished and `Pending` when it is not. Here is a future written by hand that is not ready the first time, and an `async fn` that waits on it:

<Snippet file="poll-once.rs" />

- `YieldNow` returned `Pending` once and `Ready(())` on the second poll.
- `.await` is that conversation. In the [Reference's words](https://doc.rust-lang.org/reference/expressions/await-expr.html), if the inner `poll` returns `Pending`, the outer future returns `Pending` too, and when polled again it resumes at the same `.await`. `before the await` printed once, though the body was polled twice.
- An `.await` on a future that is already `Ready` does not stop: the last line shows one poll.
- `wake_by_ref` is the future saying "poll me again soon".

A real executor sleeps instead of looping, and the waker wakes it. This one records whether it was woken and gives up rather than sleep forever. `Wake` turns an `Arc` of your own type into a `Waker`:

<Snippet file="wake.rs" />

The first future woke the executor before each `Pending`, so it was polled again and finished. The second never asked: a real executor would wait for a wake-up that never comes. A runtime stores the waker and calls it when a timer fires or a socket has data ([Tokio guide](/build/tokio/)).

## The standard library has no runtime

Nothing in [`std::future`](https://doc.rust-lang.org/std/future/index.html) runs a future, so `main` cannot be async: nothing would poll it.

<Snippet file="async-main.fail.rs" />

That is why `#[tokio::main]` exists. A runtime is an event loop, which learns when timers fire and sockets are readable, plus a scheduler, which decides which task to poll next. Node and `asyncio.run` hide this loop; `block_on` is the smallest. The language gives you `async`, `.await` and `Future`, and the scheduler is a library you choose.

## Two futures on one thread: join

To make progress on two futures, poll both. `std::future::join!` is experimental on 1.99.1 (E0658; `check-join-unstable.fail.rs`), so here it is by hand; `poll_fn` turns a closure into a future. A finished future is left alone: the `Future` docs warn that polling after `Ready` may panic or block forever.

<Snippet file="join.rs" />

One after the other, the steps run `a1 a2 a3 b1 b2`. Joined, they take turns: `a1 b1 a2 b2 a3`, with no second thread.

## A future that must cross threads is `Send`

Tokio's default runtime is multi-threaded: the [`#[tokio::main]` docs](https://docs.rs/tokio/latest/tokio/attr.main.html) say `multi_thread` "is the default flavor". A task can then resume on another worker thread after any `.await`, so [`spawn`](https://docs.rs/tokio/latest/tokio/task/fn.spawn.html) asks for `Send` ([Send and Sync](/learn/send-sync/)) and `'static`, as `thread::spawn` does ([Reading signatures](/learn/reading-signatures/#threadspawn-three-bounds-at-once); [`'static`](/learn/lifetimes/#static)). The `spawn` below calls `thread::spawn`, so the bound is real. A future holds everything alive across an `.await`, so an `Rc` there makes it not `Send`:

<Snippet file="send-rc.fail.rs" />

The first note says "future is not `Send` as this value is used across an await". End the `Rc`'s life before the wait:

<Snippet file="send-scope.rs" />

An `Arc` there compiles too (`check-send-arc.rs`). Dropping early is less reliable than ending a block. On 1.99.1 a `drop(words)` before the wait does not help once the value was used:

<Snippet file="send-drop.fail.rs" />

A value that was only created and then dropped is accepted (`check-send-drop-unused.rs`), but I found no documented rule, so end the block. A lock is the same: [`Mutex::lock`](/learn/shared-state/) returns a guard, and one held across an `.await` makes the future not `Send`:

A guard used and then dropped still fails (`check-send-guard-drop.fail.rs`); one only locked and dropped compiles (`check-send-guard-unused.rs`). Lock in a block, or in a temporary that ends at the semicolon, and lock again after the wait (exercise 3).

## What the keyword costs: function colour

A plain function cannot `.await`. It needs a runtime or a `block_on`:

<Snippet file="async-color.fail.rs" />

This is **function colour**: async and plain functions are two kinds, and a plain one cannot wait on an async one, so callers turn async or carry a runtime. Libraries split too: `std::fs` and `std::net` block the calling thread, so async code uses a runtime's own I/O types, and a crate usually serves one world. Some runtimes avoid the split by parking a blocked call themselves. Rust has no runtime in `std` to do that, so it marks each wait in the types. You pay with the split, and get a future you can store, drop or poll by hand.

## What the compiler builds, and why `Pin` exists

An `async fn` becomes a value, and its size is the data it must keep while it waits. The program prints the sizes of three futures whose only wait is one `YieldNow`:

<Snippet file="state.rs" />

With nothing to keep, the future is 2 bytes. A `[u8; 1000]` used after the wait makes it 1,002. Used up before the wait, the array is not kept and the future is 16 bytes, because the `usize` `n` is still needed. The layout is the compiler's business and may change.

The Rust Book calls this a state machine ([Futures and the Async Syntax](https://doc.rust-lang.org/book/ch17-01-futures-and-syntax.html)). The future is that state, stored wherever its owner puts it, and not a pointer to a frame allocated elsewhere, which is how a C++20 coroutine works (see the C++ note). That is why Rust needs `Pin`. A future may hold a reference into its own fields across an `.await`, so moving it after the first poll could leave the reference pointing at the old place. `poll` therefore takes `Pin<&mut Self>`, a promise that the value will not move ([`std::pin`](https://doc.rust-lang.org/std/pin/index.html)), unless its type is `Unpin`, the marker for types that do not mind being moved. The future of an `async fn` is not `Unpin`. `pin!` pins on the stack and `Box::pin` on the heap; `Pin::new` needs `Unpin`, and the compiler points to the first two:

## Dropping a future cancels it

Dropping a future between polls ends the work: everything it held is dropped and the rest of the body never runs. This `forward` takes an item off a queue, waits, then delivers it:

<Snippet file="cancel.rs" />

In the second run `delivered` never printed and `dropped item 1` did: cleanup runs through `Drop` ([Common traits](/learn/common-traits/#drop-the-trait-behind-scope-exit)), which is a plain function and cannot `.await` (`check-drop-await.fail.rs`). The item was also lost: it left the queue and was never delivered. A future is **cancellation safe** if being dropped at an `.await` loses nothing; `forward` is not. The place this bites is `select!`. Tokio's [`select!`](https://docs.rs/tokio/latest/tokio/macro.select.html) returns "when the first branch completes, cancelling the remaining branches", and its docs list which methods are cancellation safe. `timeout` cancels its future the same way ([Tokio guide](/build/tokio/)).

## Async or threads?

`std` has native OS threads ([Threads](/learn/threads/)) and futures without a runtime. The [Async Book](https://rust-lang.github.io/async-book/) says async programming is "a good fit for systems which need to handle very many concurrent tasks and where those tasks spend a lot of time waiting". Two other reasons: cancellation, since a [`JoinHandle`](https://doc.rust-lang.org/std/thread/struct.JoinHandle.html) can `join` a thread or check `is_finished`, not stop it, while a future can be dropped; and crates, since axum, reqwest, tonic and sqlx are built on Tokio ([guide](/build/tokio/)).

Async does not split one task's computation across threads, and long CPU work stalls the thread it runs on. [Rayon and Tokio together](/build/rayon-tokio/) sends parallel CPU work to rayon and a blocking call to `spawn_blocking`. A reasonable default is threads, until your program mostly waits on many things or needs timeouts.
