## From error to fix

This page is for the moment after the borrow checker said no: what do I change? It does not re-teach the rules ([Ownership](/learn/ownership/), [Borrowing](/learn/borrowing/), [Mutable borrows](/learn/mutable-borrows/)).

A borrow error points at up to three places: the first move or borrow, the use that clashes, and a *later use* of the first that keeps it alive ([Mutable borrows](/learn/mutable-borrows/#the-rule-one-writer-or-any-number-of-readers) shows all three). A fix moves one: end the first borrow earlier, avoid the clash, or stop needing the first. [Reading compiler errors](/errors/) explains the layout.

The `help:` lines are hints, not a diagnosis: a suggested `clone` can compile and do the wrong thing ([moving out](#moving-out-of-a-borrow-e0507)), and a suggested type can only move the error (the Java, Kotlin and C# box [below](#the-habit-you-bring-the-error-you-meet)).

**A small fix, or a design problem?** Most errors take one local change, listed below. These signs mean the design is the cause; read [the redesign section](#when-the-error-does-not-go-away-redesign):

- the third `clone` or `Rc` in one struct, added to quiet an error;
- `&mut self` methods that call each other while a field is borrowed;
- a struct that stores a reference into something it also owns, such as a parser holding a `String` and slices of it ([self-referential](#parent-pointers-and-graphs-indices-not-references));
- lifetime annotations spreading through three signatures;
- two parts that both want to change one value.

| Error | The compiler says | Try first |
|---|---|---|
| [E0382](#use-after-move-e0382) | borrow of moved value: `x` | borrow instead of moving |
| [E0499](#two-borrows-at-once-e0499-e0502) | cannot borrow `x` as mutable more than once | copy a value out, or split the data |
| [E0502](#two-borrows-at-once-e0499-e0502) | cannot borrow `x` as mutable because it is also borrowed as immutable | end the first borrow earlier |
| [E0500](#two-borrows-at-once-e0499-e0502) | closure requires unique access to `*self` | name the field inside the closure |
| [E0505](#moved-or-assigned-while-borrowed-e0505-e0506) | cannot move out of `x` because it is borrowed | finish with the borrow first |
| [E0506](#moved-or-assigned-while-borrowed-e0505-e0506) | cannot assign to `x` because it is borrowed | finish with the borrow first, or `mem::replace` |
| [E0507](#moving-out-of-a-borrow-e0507) | cannot move out of `x` which is behind a mutable reference | `take`, `as_ref` |
| [E0596](#the-habit-you-bring-the-error-you-meet) | cannot borrow `*x` as mutable, as it is behind a `&` reference | take `&mut`, or add `mut` |
| [E0106](#parent-pointers-and-graphs-indices-not-references) | missing lifetime specifier | an id instead of a reference |
| [E0597](#a-reference-that-outlives-its-owner-e0515-e0597-e0716) | `x` does not live long enough | keep the owner longer, or own the data |
| [E0515](#a-reference-that-outlives-its-owner-e0515-e0597-e0716) | cannot return reference to local variable `x` | return an owned value |
| [E0716](#a-reference-that-outlives-its-owner-e0515-e0597-e0716) | temporary value dropped while borrowed | bind the temporary with `let` |

## Use after move (E0382)

<Snippet file="move.fail.rs" />

`total` takes the `Vec` by value, so `scores` belongs to it after the call. The fix depends on what the function does with it:

<Snippet file="move-fixes.rs" />

- **It only reads: change the signature** to borrow (`&[u32]`). Nothing is copied.
- **It keeps the value, and you need yours too: clone.** The output shows a different buffer: an allocation and a copy of every element. Fine for a small value built once; a smell in a loop, when the function only reads, or when the copies must stay in sync ([clone or share](#clone-or-share-when-rcrefcellt-is-the-honest-answer)).
- **It keeps the value, and you are done with it: move it.** Same buffer.

## Two borrows at once (E0499, E0502)

A reference still used after a `push` is E0502. A borrow ends at its last use ([Mutable borrows](/learn/mutable-borrows/#a-borrow-ends-at-its-last-use)), so copy the small value out first (`let n = v.len();`) or move the use above the `push`. A `Drop` impl counts as a use at the closing `}` (E0499 here):

<Snippet file="drop-ends-borrow.fail.rs" />

The note says so: "first borrow might be used here, when `guard` is dropped". `drop(guard)` after its last use ends the borrow there.

**Two elements.** The compiler does not look at index values, so `&mut v[0]` and `&mut v[3]` both borrow the whole `Vec` ([Mutable borrows](/learn/mutable-borrows/#changing-two-parts-at-once)). `swap` swaps, `split_at_mut` gives two halves that cannot overlap, and `get_disjoint_mut` (Rust 1.86) checks the indices when it runs:

<Snippet file="disjoint.rs" />

**Two fields and a method.** The gotcha failed because `self.note(..)` takes `&mut self`, which borrows *all* of `self`, including the `items` being read. A field access names one field, so `items` and `log` are different places:

<Snippet file="self-fixes.rs" />

| Fix | What it costs |
|---|---|
| Name the field: `self.log.push(..)` | you give up the helper; its logic is repeated |
| A function that takes only the field it needs | callers pass the field |
| Work out what to do first, then call the method (the gotcha's fix) | an extra `Vec` and a second pass |
| Take the field out with `mem::take`, call the method, put it back | `items` is empty in between, and an early `return` or `?` forgets to put it back |
| Make the field its own type (`Log`) | one more type, which often matches the data anyway |

A closure that calls the method captures all of `self` the same way:

<Snippet file="closure-self.fail.rs" />

Naming the field in the closure (`self.log.push(..)`) captures only `log`. [Closures](/learn/closures/) explains capture.

## Handing out a `&mut`

Ask for a `&mut` to just the part you change: `opt.as_mut()` or `as_deref_mut()` on an `Option`, `iter_mut()`, `last_mut()` or `iter_mut().find(..)` on a `Vec`, `get_mut(key)` on a map. Use it inside `if let Some(x) = ..`, and do other work after it, where the `&mut` is over. One shape still fails: returning the `&mut` when the key is found and inserting otherwise.

<Snippet file="get-mut-return.fail.rs" />

Both errors are E0499 on 1.99.1. `entry` looks up once and gives back the slot:

<Snippet file="get-mut-return.rs" />

The cost: `entry` takes the key by value, so the `String` is built even when the key is there. [Maps](/learn/maps/#why-not-get-then-insert) has the simpler `get`-then-`insert` shape.

## Moving out of a borrow (E0507)

Behind a `&self` or `&mut self` you cannot take a value out of a field and leave a hole ([Ownership](/learn/ownership/#moving-out-of-things) and [Mutable borrows](/learn/mutable-borrows/#swapping-and-taking) show the error). Its `help:` suggests `clone`, which compiles and is wrong here:

<Snippet file="clone-is-wrong.rs" />

`logout` must leave the session without a token, and a clone leaves the old one in place. Choose between looking, taking and copying:

| You want | Use | What is left behind |
|---|---|---|
| to look at the text in an `Option<String>` | `opt.as_deref()`, or `opt.as_ref()` for a `&String` | `opt`, unchanged |
| the value, and `None` in its place | `opt.take()` | `None` |
| a whole `String` or `Vec`, and an empty one in its place | `mem::take(&mut x)` | the empty value (the type needs a default) |
| the old value, and one you choose in its place | `mem::replace(&mut x, new)` | `new` |
| a second, independent value | `x.clone()` | `x`, unchanged; you paid for a copy |

<Snippet file="arena.rs" />

This is the handle pattern of C++ game engines and ECS libraries: a `Vec` of components and an `Entity(u32)` id.

## Clone or share: when `Rc<RefCell<T>>` is the honest answer

Cloning to get past an error gives you a second value. If two parts of the program must see each other's changes, that is a bug:

<Snippet file="shared.rs" />

When the design really is "many owners of one changing value", `Rc<RefCell<T>>` says so ([Box, Rc and RefCell](/learn/smart-pointers/)). The price: the borrow rules are checked while the program runs, so a mistake is a panic, and `Rc` cannot cross threads.

| The situation | Usual answer |
|---|---|
| a small value, copied once at a boundary | `clone` |
| a counter or cache that a `&self` method updates | `Cell<T>` for a `Copy` value |
| two parts must see the same changes | `Rc<RefCell<T>>` (`Arc` and a lock across threads: [Shared state](/learn/shared-state/)) |
| it keeps coming back as one big `&mut self` | restructure ([below](#when-the-error-does-not-go-away-redesign)) |

## When the error does not go away: redesign

The signs are at the top. [Ownership](/learn/ownership/#when-ownership-feels-like-a-fight) lists the broad changes (one owner per piece of state, ids for references), [Returning references](/learn/returning-references/) returns results up, and [Lifetimes](/learn/lifetimes/#when-to-own-instead-of-borrow) weighs owning against borrowing. Two belong here:

- **Split a struct when its fields change at different times.** A method that wants `items` read-only and `log` writable is describing two types (the `Log` fix above).
- **Decide with `&self`, then apply with `&mut self`.** Read everything, return a plan of positions, then change. The cost is the plan, and the list must not change in between.

<Snippet file="plan-apply.rs" />

`apply` removes from the back so earlier positions stay valid.

[`unsafe`](/learn/unsafe/) does not switch the checker off: it lets you do what the compiler cannot check, and a mistake there is yours. The checker also rejects some programs that would run fine, such as the conditional return in [Lifetimes](/learn/lifetimes/#where-a-borrow-really-ends); the fix is a shape it accepts, not a trick.

## Try it

Each starter compiles and stops at `todo!`. The first draft you would write anywhere fails with the error named below: write it, read the error, then fix it. The checks count clones, compare buffer addresses and forbid `unsafe`, so copying the data does not pass.

<Exercise name="low-stock" title="Flag low stock">
Write `flag_low`: for each item with a count below 5, in order, call `self.note` with `low: NAME (COUNT)`. Your first draft fails with E0502. Call `note` itself (it numbers each line), and do not copy the items.
</Exercise>

<Exercise name="ledger" title="Settle a ledger">
Write `settle`: apply each entry in order with `self.apply` (it needs `&mut self`), and return the first `Err`. Your first draft fails with E0502. Every entry must stay in the ledger, in the same buffer, even when `apply` fails.
</Exercise>

<Exercise name="org" title="Teams by id">
Write `relabel`: set a team's `path` to its parent's path, a slash and its own name, then do the same below it. Your first draft fails with E0502: it holds `&mut self.teams[i]` while reading the parent, or loops over the teams while calling `self.relabel`. The checks count clones of a `Team`.
</Exercise>
