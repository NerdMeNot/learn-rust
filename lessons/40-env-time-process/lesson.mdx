<p class="lr-layer">The toolkit</p>

Outputs come from Linux on 64-bit ARM with Rust 1.99.1, in debug mode. A program here starts with no arguments and an environment of its own, so several start a copy of themselves with `Command` (it starts another program, and `.output()` runs it and captures what it printed; [Running other programs](#running-other-programs) teaches it). `env::current_exe()` is the path of the running program, and an argument tells the copy what to do. The tools they run (`echo`, `sort`, `sleep`, `sh`, `pwd`) are common on Linux and macOS; Windows has different ones. A `Duration` is an amount of time (see Time).

## Arguments

`env::args()` is an iterator of `String`s. Item 0 is the program, then one item per argument. Here `args[1]` is the `--child` marker, so the parent's arguments start at `args[2]`:

<Snippet file="args.rs" />

The docs call the first item "traditionally the path of the executable" and say not to rely on it for security ([docs](https://doc.rust-lang.org/std/env/fn.args.html)). `"hello world"` is one argument because the parent passed it as one, and `*` arrives as `*` because no shell is involved (on Unix a shell expands globs before the program starts). `--flag=1` is only text: `std` has no flag parser, so use `clap` ([guide](/build/clap/)). A missing argument is `None` from `nth`, not an index error. `args()` panics on an argument that is not valid UTF-8, and a Unix file name can hold any bytes; `args_os()` does not ([run below](#strings-that-are-not-string)).

## Time

Elapsed times change on every run, so these programs print comparisons, never the numbers.

### `Instant`: measuring

An `Instant` is a reading of a clock that is "monotonically nondecreasing", in the docs' words. You subtract two readings. It is `CLOCK_MONOTONIC` on Linux and `CLOCK_UPTIME_RAW` on macOS, and whether a system suspend counts "varies across platforms and Rust versions" ([docs](https://doc.rust-lang.org/std/time/struct.Instant.html)). `thread::sleep` sleeps for at least the time asked ([docs](https://doc.rust-lang.org/std/thread/fn.sleep.html), [Threads](/learn/threads/)), so the first check is safe:

<Snippet file="time-instant.rs" />

`Instant + Duration` builds a later instant without waiting, so the other lines do not depend on the clock. `duration_since` the wrong way round gives `0ns` today, and the docs add that "Future versions may reintroduce the panic in some circumstances". Say what you mean instead: `checked_duration_since` gives `None`, so you notice a mistake, and `saturating_duration_since` gives `0ns` on purpose.

### `SystemTime`: the wall clock

A `SystemTime` is the system clock, which a person can set, so two readings can come out in the wrong order and `duration_since` returns a `Result`. `UNIX_EPOCH` is 1970-01-01 00:00:00 UTC:

<Snippet file="time-system.rs" />

`std` has no calendar or time zones: "Sunday, 25 October" takes a crate. `chrono` and `time` are long established; `jiff` is newer, handles time zones, and its README compares it with both. [Finding and using crates](/start/using-crates/) shows how to add one.

### `Duration`: an amount of time

<Snippet file="time-duration.rs" />

`as_secs` cuts off the fraction (1.5 s is `1`), so read `subsec_millis` or `as_secs_f64`. A `Duration` has no `Display`, deliberately (docs); `{:?}` prints `1.5s`. It is never negative, unlike the durations of Go, Java, Kotlin, C#, C++ and Python (their sections run one), so a plain `-` that would go below zero panics:

<Snippet file="duration-sub.panic.rs" />

Use `checked_sub` or `saturating_sub`.

## Running other programs

`Command` runs another program. `output()` waits and captures what it printed:

<Snippet file="command-basic.rs" />

A program name is a file name, so `"echo hello"` is not found. On Unix, arguments arrive as they are: `$HOME`, `*` and `;` did nothing, because no shell reads them. For a shell's pipes or globs, run `sh -c "..."` yourself and take care with the string. A program that fails is `Ok(status)`; `Err` means it could not be started or its output could not be read. A name without a slash is looked up in `PATH`, as `execvp` does; with a slash it is a path:

<Snippet file="path-lookup.rs" />

`output()` gives the child an input already at its end ([docs](https://doc.rust-lang.org/std/process/struct.Command.html#method.output)). To feed it, pipe its stdin, write, and close. New here: `Stdio::piped()` asks for a pipe, `spawn` starts the child and returns at once, `child.stdin.take()` moves the pipe's write end out of the `Child` so you own it, and `try_wait` asks "finished?" without waiting (`None`: not yet).

<Snippet file="command-pipe.rs" />

`sort` cannot answer before its input ends, and the pipe stays open until `stdin` is dropped, so `try_wait` finds it running. `wait` and `wait_with_output` close a `stdin` still inside the `Child` ([docs](https://doc.rust-lang.org/std/process/struct.Child.html#method.wait)), but after `take()` it is yours to drop. Reading `sort`'s output before closing its input waits forever.

### How the child ended

`ExitStatus` wraps the wait status Unix gives the parent. `code()` is `Some` when the program exited (C's `WIFEXITED`, `WEXITSTATUS`); `signal()` is `Some` when a signal ended it (`WIFSIGNALED`, `WTERMSIG`), and then there is no exit code. `signal` and `into_raw` come from `ExitStatusExt`, an extension trait whose methods exist only after `use std::os::unix::process::ExitStatusExt`. `into_raw` is the number C's `system` returns. `Child::kill` is the one signal stable `std` can send:

<Snippet file="exit-status.rs" />

`exit 5` is raw 1280, 5 times 256: the exit code is shifted up one byte, while a signal number sits in the lowest bits.

### A deadline for a child

`std` has no timeout for a child: `wait` blocks until it exits. The loop is yours: `spawn`, `try_wait` every few milliseconds until `Some` or you give up, then `kill` and `wait`. This one counts polls, so it prints no times:

<Snippet file="child-timeout.rs" />

The `wait-timeout` crate does this for you. Go, Python, Java and Node build a deadline in; their sections run it.

## Strings that are not `String`

A `String` is always valid UTF-8 ([Strings](/learn/strings/)), but arguments, variable values and file names arrive as bytes that on Unix need not be. `OsString` and `OsStr` hold them ([Files and I/O](/learn/files-io/) uses them for paths). This program passes the bytes `caf` and `0xE9` (a lone byte, not UTF-8) as an argument and a variable, built with `OsStrExt` from `std::os::unix`:

<Snippet file="non-utf8.rs" />

`var` returns `NotUnicode`; `args()` and `vars()` panic while iterating, as their docs say. `args_os`, `var_os` and `vars_os` hand over the value, and `to_str()` or `to_string_lossy()` makes text of it. A tool that takes file names should use `args_os`.

## Why `set_var` is `unsafe`

The environment is one global for the whole process. The `set_var` docs say that, outside Windows, there is no thread-safe way to read it, since "most C libraries, including libc itself, do not advertise which functions read from the environment", and that in multi-threaded programs on those systems "the only sound option is to not use `set_var` or `remove_var` at all". So `unsafe` marks a promise: no other thread is running that could read or write the environment.

C programmers know this: glibc marks `setenv` "MT-Unsafe" ([setenv(3)](https://man7.org/linux/man-pages/man3/setenv.3.html)), and the string `getenv` returns "can be modified by a subsequent call to getenv(), putenv(3), setenv(3), or unsetenv(3)" ([getenv(3)](https://man7.org/linux/man-pages/man3/getenv.3.html)). `env::var` copies into an owned `String`, so no pointer goes stale. Go's `os.Setenv` and Python's `os.environ[k] = v` are plain functions. Go guards its own copy with a lock (its `syscall` source), which protects Go code, but no lock inside one runtime stops C code in the same process calling `getenv` on another thread. Java has no call to change its own environment (its section runs the map throwing). For your own settings, pass a parameter.

## Who closes the pipe

The child sees "end of input" when the parent's write end is closed, which is why `command-pipe.rs` drops `stdin`. Go, Python and Node write and close inside the call (a reader as `Stdin`, `input=`, the `input` option; their sections run each). Rust has no `input=`; you write and close yourself, as `run-script` does.

The `Stdio` docs add a trap: writing more than a pipe buffer's worth to the child's stdin without reading its stdout "may cause a deadlock" for a program that writes before it has read everything. The child's output pipe fills, so it stops reading, so the parent's write blocks. Such a program hangs, so the page does not run it. The docs' example avoids it by writing from a second thread ([Threads](/learn/threads/)) while the first reads.

`std` does not wait for a child on its own, even when the `Child` is dropped. On some systems a finished, unwaited child stays in the process table as a "zombie" (`Child` docs), so long-running programs call `wait`.

## What `std` leaves to crates

`ctrlc` and `signal-hook` catch Ctrl-C and other signals, which `std` cannot. `dotenvy` loads a `.env` file. `wait-timeout` gives a child a timeout, and Tokio covers timers in async code ([guide](/build/tokio/)).
