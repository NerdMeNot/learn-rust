## When you write a lifetime

A **lifetime** is how long a reference may be used: a region of the program, not a number, and it must fit inside the time the value it points at is alive ([Borrowing](/learn/borrowing/#how-long-a-borrow-lasts) showed where a region ends). The compiler works one out for every reference. You write one, like `'a`, only when a signature or a struct has to say which value a reference borrows from.

That is less often than the notation suggests. Code that keeps `String` and `Vec` in its structs writes few; parsers, tokenizers and other code that hands out pieces of its input write them every day. You will meet `'a`:

- on a function with two or more reference inputs that returns a reference ([`longest`](#naming-a-lifetime-a));
- on a struct that holds a reference, and on its methods that hand out pieces of it ([structs](#structs-that-hold-references));
- when a bound asks for `'static`, as `thread::spawn` and `Box<dyn Trait>` do ([`'static`](#static)).

<ForLang only="c cpp">
In C++, "lifetime" usually means an object's: from construction to destruction. In Rust it belongs to a *borrow*. The `'a` in `&'a str` is how long the reference may be used, not how long the string exists.
</ForLang>

## Naming a lifetime: `'a`

`'a` is a lifetime parameter: an apostrophe and a name, declared in angle brackets like the type parameter in [Generics](/learn/generics/) and written after the `&`.

<Snippet file="longest.rs" />

`'a` ties `a`, `b` and the result together: the result may be used only while both inputs are alive. At each call the compiler picks the stretch where both arguments are valid ([the Book](https://doc.rust-lang.org/book/ch10-03-lifetime-syntax.html) explains the choice).

**`'a` does not extend a lifetime.** The gotcha above has `'a` on every reference and still fails, because `s2` is dropped before `result` is used. The annotation describes how references relate. It cannot keep `s2` alive.

<ForLang only="c cpp">
In C and C++ the contract of `longest` lives in a comment: the signature returns a pointer or reference and does not say into which argument. With the shorter string as `s1`, the gotcha programs read freed memory, and AddressSanitizer says so:

<Snippet file="longest-short.crash.asan.c" />

<Snippet file="longest-short.crash.asan.cpp" />

Compilers catch only some shapes. The runner's g++ 14 and Apple clang 21 (run by hand, outside the runner) both compile the two programs above with `-Wall -Wextra` and no warning. Clang does warn about a `std::string_view` made from a temporary (`-Wdangling-gsl`), and it has an opt-in attribute, `[[clang::lifetimebound]]`, that marks a result as borrowing from a parameter and warns when a temporary is passed for it. `'a` is that annotation made mandatory, checked on every call, and able to say *which* parameter.
</ForLang>

| Written | Reads as |
|---|---|
| `&str` | a reference; the compiler works out the lifetime |
| `&'a str`, `&'a mut Vec<i32>` | a reference valid for `'a` |
| `fn f<'a>(x: &'a str) -> &'a str` | the result is valid as long as `x` is |
| `struct Parser<'a>` | a parser that borrows something for `'a` |
| `Parser<'_>` | `'_`: some lifetime, and I do not need its name |
| `&'static str` | a reference valid for the whole run of the program |

To read a signature that has `'a`, find the lifetime on the result and look for the same name on the inputs. Those are the values the caller must keep alive while it uses the result.

## Leaving them out: the elision rules

You wrote `fn first_word(text: &str) -> &str` in earlier lessons with no `'a`. The compiler fills the lifetimes in by three rules ([the Reference](https://doc.rust-lang.org/reference/lifetime-elision.html) states them), applied in this order to a function signature:

| Rule | Example | The compiler reads |
|---|---|---|
| 1. Every elided input lifetime is a separate parameter | `fn tail<'a>(text: &'a str, skip: &str) -> &'a str` | `fn tail<'a, 'b>(text: &'a str, skip: &'b str) -> &'a str` |
| 2. If the inputs have exactly one lifetime, the output gets it | `fn first_word(text: &str) -> &str` | `fn first_word<'a>(text: &'a str) -> &'a str` |
| 3. With `&self` or `&mut self`, the output gets the lifetime of `self` | `fn label(&self, prefix: &str) -> &str` | `fn label<'a, 'b>(&'a self, prefix: &'b str) -> &'a str` |

<Snippet file="elision.rs" />

Each function appears twice, as you write it and as the compiler reads it, and they behave the same. `skip` and `prefix` are dropped while `result` and `label` are still in use, which compiles because rules 1 and 3 keep those inputs out of the result's lifetime.

With two reference inputs and no `self`, no rule gives the output a lifetime, and you must write one. That is E0106, the error [Returning references](/learn/returning-references/#two-inputs-the-compiler-asks-which-one) walks through, with a table of which signatures compile. Its `help:` suggests the same `'a` on every reference, which is right for `longest`. It is the wrong fix when the result comes from only one input. Here the result comes from `text`, and tying it to `skip` as well makes the caller keep `skip` alive:

<Snippet file="tail-shared.fail.rs" />

Give each input the lifetime it needs, as `tail` did in the program above.

Rule 3 has a catch of its own. It ties the result to `self` even when the body returns another parameter:

<Snippet file="self-other.fail.rs" />

This error has no code. The `help:` is the fix: name the parameter's lifetime and put it on the result.

## `'static`

`'static` is a named lifetime you never declare: the whole run of the program. (`'_` is the only other lifetime that needs no declaration.) It appears in two ways that are easy to mix up.

<Snippet file="static.rs" />

- **A reference valid for the whole run**, `&'static str`. A string literal is one ([Returning references](/learn/returning-references/#string-literals-and-static-items) shows it, and the other ways to get one).
- **A bound**, `T: 'static`: "`T` holds no borrow that could end early". An owned `String` satisfies it. It does not mean the value lives forever: `Noisy` was dropped when `consume` returned. A reference to a local does not satisfy it:

<Snippet file="static-borrow.fail.rs" />

A `Box<dyn Trait>` in a signature means `Box<dyn Trait + 'static>`. To store a trait object that borrows, say so:

<Snippet file="box-dyn.rs" />

`std::thread::spawn` puts `'static` on its closure ([docs](https://doc.rust-lang.org/std/thread/fn.spawn.html)), which is why a closure that borrows a local needs `move` ([Threads](/learn/threads/)).

<ForLang only="c cpp">
`'static` is not C's storage class. A `&'static` reference points at data that lasts the whole run, such as a literal or a `static` item.
</ForLang>

## Lifetime errors and the usual fix

| Error | The compiler says | The usual fix |
|---|---|---|
| E0106 | missing lifetime specifier | Write the `'a` ([above](#leaving-them-out-the-elision-rules)), or return an owned value |
| E0597 | `x` does not live long enough | Declare the owner earlier so it lives as long as the borrow, or own the data |
| E0716 | temporary value dropped while borrowed | Give the temporary a name with `let` (example below) |
| E0505 | cannot move out of `x` because it is borrowed | Finish with the reference first, or do not move ([Borrowing](/learn/borrowing/)) |
| E0499 | cannot borrow `x` as mutable more than once at a time | End the first borrow earlier, or give the method's result the right `'a` ([above](#structs-that-hold-references)); see [Mutable borrows](/learn/mutable-borrows/) |
| E0502 | cannot borrow `x` as immutable because it is also borrowed as mutable | End the first borrow earlier, or restructure ([below](#where-a-borrow-really-ends)) |
| E0515 | cannot return reference to local variable `x` | Return an owned value ([Returning references](/learn/returning-references/)) |
| E0373 | closure may outlive the current function, but it borrows `x` | Add `move` ([Closures](/learn/closures/)) |
| no code | lifetime may not live long enough | The body returns more than the signature promises: [change one of them](#lifetime-bounds) |

E0597 marks three places: where the reference is made, where the owner is dropped, and where the reference is used last. A fix moves one of the three. Declare the owner earlier, use the reference before the owner goes, or stop borrowing and keep a copy. The first and third:

<Snippet file="excerpt-fixed.rs" />

E0716 can appear with no function in sight. `String::from("temporary")` has no name, so it is dropped at the end of the statement, and `as_str()` borrowed from it:

Bind the `String` with `let` first.

## When to own instead of borrow

A lifetime on a struct is a cost you pay in every type that holds it. Owning the data copies it once and removes the lifetime. The structs in the [Structs](/learn/structs/) lesson owned their fields, so they needed none.

<Snippet file="own-the-data.rs" />

`Line<'a>` could only be used while `raw` was alive. `OwnedLine` outlived `raw`, and could go into a `Vec`, be returned from any function, or move to another thread. (`map` builds each word and `collect` gathers them into a list; [Iterators](/learn/iterators/) covers both.) On a 64-bit target the borrowed `Word` is 16 bytes and the owned one 24, and the owned one needed a copy of every word.

Borrowing is not automatically the better choice. Borrow in a struct when it is a short-lived view over data you already hold, such as a parser or an iterator over one buffer. Own when the struct is stored, returned, sent to a thread, or kept in a collection. When a lifetime error blocks you, `.to_string()` or `.clone()` at the boundary is a fine first step.

<ForLang only="java kotlin csharp python typescript">
Owning is what your languages do on every call: the substring or slice in your parser was already a copy. In Rust it is a choice, so you can pick the view when it pays.
</ForLang>

<ForLang only="c cpp">
Returning by value is the C++ way to own. `std::shared_ptr` answers who owns the string, not whether a view into it is valid:

<Snippet file="shared-view.crash.asan.cpp" />

Rust's counting pointers, `Rc` and `Arc`, are in [Smart pointers](/learn/smart-pointers/#rct-several-owners); a lifetime counts nothing and is not stored (see `Excerpt` above).
</ForLang>

## Lifetime bounds

`'b: 'a` says `'b` lasts at least as long as `'a`. `T: 'a` is the same idea for a type: all the borrows inside `T` last at least as long as `'a`. A signature is a promise the body must keep: the compiler checks callers against the signature alone, and the body against the signature. A body that returns something the signature did not promise is an error:

<Snippet file="contract.fail.rs" />

The `help:` names the bound: a `&'b str` may be returned as a `&'a str` only if `'b` outlives `'a`.

<Snippet file="bound.rs" />

`Holder<'a, T>` did not need `T: 'a` written. The compiler works it out from the field `&'a T`.

## Where a borrow really ends

The borrow checker's current design, non-lexical lifetimes (NLL), ends a borrow at the last use of the reference, not at the end of its block ([Borrowing](/learn/borrowing/#how-long-a-borrow-lasts) has the run). One exception matters once structs hold references: if the value holding the borrow has a `Drop` impl, the drop at the end of its scope counts as a use.

<Snippet file="drop-ends-borrow.fail.rs" />

Without the `impl Drop` the same program compiles.

The checker is also not all-knowing. This function is fine at run time, but is rejected:

The [NLL design](https://rust-lang.github.io/rfcs/2094-nll.html) calls this "problem case #3", and the compiler used here still rejects it.
