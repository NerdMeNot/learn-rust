A **struct** groups several values under one name, each with a name of its own. It is how you make a type for a real thing in your program: a user, a point, a config. Outputs on this page come from Linux on 64-bit ARM with Rust 1.99.1; where a fact depends on the machine or the compiler version, the text says so.

## Derive: asking the compiler for standard behaviour

A new struct can't do much: it can't be printed, compared or copied. `#[derive(…)]` above a struct asks the compiler to write that code for you, using the fields. Each name in the list is a **trait**: a named ability a type can have. [Traits](/learn/traits/) come later; for now each one is a switch.

| Derive | What you get | Needs |
|---|---|---|
| `Debug` | `{:?}` and `{:#?}` printing | every field is `Debug` |
| `Clone` | `.clone()`, a full copy | every field is `Clone` |
| `Copy` | assignment copies instead of moving (needs `Clone` too) | every field is `Copy`, so no `String` or `Vec` |
| `PartialEq` | `==` and `!=`, field by field | every field is `PartialEq` |
| `Eq` | signals that every value is equal to itself | every field is `Eq`, so no `f64` |
| `PartialOrd`, `Ord` | `<`, `>` and sorting, field by field in the order you declared them | every field has it; `Ord` also excludes `f64` |
| `Hash` | use in a `HashSet`, or as a `HashMap` key (with `Eq`) | every field is `Hash` |
| `Default` | `Type::default()`, with `0`, `false` and `""` | every field has a default |

<Snippet file="derive.rs" />

`1.10 > 1.9` is true because the derived comparison looks at `major` first, then `minor`, as numbers. The `Partial` versions exist because `f64` has a value, `NaN` ("not a number"), that is not equal to itself, as the last line shows. A struct holding an `f64` can derive `PartialEq` but not `Eq`: that is a compile error (E0277). And `#[derive(Copy)]` on a struct with a `String` is refused (E0204), because a bitwise copy of a `String` would mean two owners of one heap block.

`Hash` plus `Eq` lets a struct be an item in a set, or a key in a [map](/learn/maps/) (covered later):

<Snippet file="derive-hash.rs" />

### Printing: `{:?}` and `{:#?}`

`{}` needs a trait called `Display`, which you write yourself ([Common traits](/learn/common-traits/#printing-debug-and-display), later). `{:?}` uses `Debug`, which the compiler can write for you. `{:#?}` is the same on many lines, which helps with nested structs:

## Passing structs to functions

A struct follows the borrowing rules you already know, as a whole. The signature tells the reader what the function may do: `&Account` reads it, `&mut Account` changes it, `Account` takes it over.

<Snippet file="borrow-struct.rs" />

Field access looks through a reference, so `a.owner` works whether `a` is an `Account` or a `&Account`. Passing the struct by value moves it, and the caller has nothing left:

<Snippet file="move-struct.fail.rs" />

The fix is the one from [Borrowing](/learn/borrowing/): take `&Order`, unless the function really needs to keep it.

## Structs that own data, and structs that borrow

Every struct so far *owns* its fields. A `String` field owns its text, a `Vec<String>` field owns its list, and when the struct goes away its fields are freed with it. This is the default, and the right choice for most structs.

A field can also be a reference, like `&str`, which borrows text owned by someone else. Rust must then know that the struct will not outlive that text. You write that down with a **lifetime**, which is the later lesson [Lifetimes](/learn/lifetimes/). Until then, the compiler asks for it:

<Snippet file="borrowed-field.fail.rs" />

The `'a` in the suggestion is a lifetime name. Don't worry about it yet. Use `String` and `Vec` fields until you meet lifetimes.

## Who can see the fields

By default, a field can be used only by code in the same **module**, or in modules nested inside it. A module is a named group of code (`mod shop { … }`; a file can be a module too). Mark a field `pub` to let code anywhere use it. Privacy is per field, and a struct can mix both kinds:

<Snippet file="private-field.fail.rs" />

Code inside `shop` can read `price_cents`:

<Snippet file="privacy.rs" />

Code outside the module can't build an `Item` with a literal either, because a literal must name every field, private ones included (E0451). The module offers a function like `make_item` instead. So a private field can be changed later without breaking code outside the module.

## Structs in your language

<ForLang only="go">

Go's `type User struct` and Rust's `struct User` are close relatives. The differences are in the defaults:

| In Go | In Rust |
|---|---|
| `User{Name: "ana"}`, the rest becomes zero | every field must be given; `..Default::default()` asks for zeros. Go's `*int` for "unset" is `Option<u32>` ([Option](/learn/option/)) |
| `var u User`, a zero value | `User::default()` after `#[derive(Default)]` |
| `NewUser(…)` by convention | `User::new(…)` by convention (next lesson) |
| each field exported by its capital letter, for the whole package | `pub` on each field you open; the unit is the module, which is like a package but several fit in one file and they nest (it has nothing to do with `go.mod`) |
| `shop.Item{Name: "x"}` compiles from another package, with unexported fields at zero | refused from outside the module (E0451): a function inside must build it |
| `loud := base; loud.Verbose = true` | `Config { verbose: true, ..base }`: moves `base`'s `String`; use `..base.clone()` to keep `base` |
| `b := a` copies the struct, but a slice, map or pointer inside it is shared | `let b = a;` moves; `a.clone()` copies everything, deeply |
| `f(u)` copies `u`, `f(&u)` may change it | `f(u)` moves; `f(&u)` reads; `f(&mut u)` changes |
| `type Meters float64` | `struct Meters(f64)` |
| `struct{}` | a unit struct |
| `u1 == u2`; `map[Point]bool` | `#[derive(PartialEq)]`; add `Eq, Hash` for a set or map key |
| `fmt.Printf("%+v", u)` | `println!("{u:?}")` or `{u:#?}` |
| embedding `User` inside `Admin` | a named field `user: User` |

A Rust struct reads like a C struct with designated initializers. The differences are in what the compiler fills in, who can see the fields, and where they go.

| In C or C++ | In Rust |
|---|---|
| `struct User u = {.name = "ana"};`, the rest is zero | every field must be given |
| `struct User u = {0};` or `User u{};` | `User::default()` after `#[derive(Default)]` |

## Size, alignment and padding

Every type has an **alignment**: a value of alignment `n` can only be stored at an address that is a multiple of `n`. A struct is laid out so that each field sits at an address that suits it, and the whole struct's size is a multiple of its alignment. The gaps this leaves are padding.

In what order do the fields go? Take `u8`, `u32`, `u8`, in that order:

<Snippet file="layout.rs" />

`CLayout` has the fields in the order written: `a` at 0, 3 bytes of padding so `b` can sit at 4, `c` at 8, and padding at the end to reach a multiple of 4. That is 12 bytes for 6 bytes of data. `Plain` is 8, because rustc put `b` first, then `a` and `c`, and the padding shrank.

<Memory
  title="The bytes inside one struct (not a stack)"
  stack={[
    { name: 'Plain', type: 'size 8', cells: ['b: 4 bytes', 'a: 1', 'c: 1', 'padding 2'], note: 'offsets: b 0, a 4, c 5' },
    { name: 'CLayout', type: 'size 12', cells: ['a: 1', 'padding 3', 'b: 4 bytes', 'c: 1', 'padding 3'], note: 'offsets: a 0, b 4, c 8' },
  ]}
  caption="The same three fields. The first row is what rustc 1.99.1 chose for the default layout. The second is `#[repr(C)]`, which fixes the order to the one you wrote."
/>

What is promised and what is only what happened here? The [Rust Reference](https://doc.rust-lang.org/reference/type-layout.html) says:

- **Promised, default layout:** fields do not overlap, each is aligned, and the size is a multiple of the alignment.
- **Not promised, default layout:** the order of the fields, so also the offsets and the 8 against 12. Those are rustc 1.99.1 on this machine. The compiler is free to reorder to save space, and here it did.
- **Promised with `#[repr(C)]`:** the order you wrote, with the padding C would add.

Use `#[repr(C)]` when another program expects exactly this layout, such as C code you call. For files and network messages, write the fields one at a time: padding bytes hold no meaningful value, and byte order is yours to choose. Otherwise leave the default.

For one struct, the saving is nothing. For ten million in a `Vec` it is 4 bytes each here, which is 40 MB. You never need to choose it, and your code should not depend on the field order or the size unless you wrote `#[repr(C)]`.
